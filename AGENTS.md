## Checks

`bun run check` is the full gate; run it before calling work done. It runs, in order and stopping at the first failure: `fmt:check` (oxfmt), `lint` (oxlint, type-aware), `knip` (dead files, exports and dependencies), `typecheck` (`tsc` per package, then `scripts/` through `scripts/tsconfig.json`, which has DOM types for the smokes' in-page callbacks), `depcheck` (dependency-cruiser, ADR 0003 layering) and `test` (`bun test`). Each is also a script of its own. `bun run fmt` rewrites formatting in place.

`bun test` always runs with coverage (`bunfig.toml`: `coverage = true`, test files excluded, `text` and `lcov` reporters; `coverage/` is gitignored). Two gates apply, and `bun run test` (so `check` and CI) runs both:

- Per file: `coverageThreshold` makes `bun test` exit non-zero when any covered file's line or function coverage is below it. Bun applies it per file, not to the "All files" total, and only reads the plural keys `lines`/`functions` (singular keys are silently ignored; an omitted key defaults to 0.9). It is a floor: the lowest per-file value measured, rounded down to a whole percent.
- Total: `scripts/check-coverage.ts` sums `coverage/lcov.info` and fails when total line or function coverage is below its `BASELINE` constants, the measured totals rounded down to a whole percent. Bun only reports files that tests load, so a new module no test imports does not lower the total.

Raise both as tests land, never lower them; if coverage genuinely drops, add tests instead.

### Git hooks

Git hooks come from lefthook (`lefthook.yml`) and are installed by `bun install` via the `prepare` script; it skips quietly outside a git checkout.

- pre-commit (staged files, parallel): `oxfmt --check`, `oxlint`, `gitleaks git --staged`. A format failure means run `bun run fmt` and re-stage.
- commit-msg: `commitlint` checks the message against Conventional Commits (`commitlint.config.js`).
- pre-push: `bun run check`.
- Prerequisite: [`gitleaks`](https://github.com/gitleaks/gitleaks) is a Go binary, not an npm dependency. Install it yourself (`brew install gitleaks` on macOS); pre-commit fails with an install hint when it is missing.

### CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`/`master`. Jobs: `check` (`bun install --frozen-lockfile`, then `bun run check`), `pr-title` (pull requests only; commitlint on the PR title, since squash merges use it as the commit message), `sherif` (`bunx sherif`, monorepo dependency consistency), `secrets` (gitleaks over the full history, config in `.gitleaks.toml`) and `audit` (`bun audit`, non-blocking until it exits 0; then drop `continue-on-error` in the workflow). The Bun version comes from `.bun-version`.

No server-side branch protection: the repo is private on GitHub's free plan, which does not offer protected branches or rulesets there, so CI reports but cannot block a merge or a push. The gates that block are local, in `lefthook.yml`: pre-commit (oxfmt, oxlint, gitleaks on staged files), commit-msg (commitlint) and pre-push (`bun run check`). Never skip them (`--no-verify`); a red CI run on `master` is fixed forward at once. Dependency updates are manual (`bun outdated`, then a normal commit through the same gates); there is no Renovate or Dependabot.

### Browser smokes

`bun run smoke:ui` runs `smoke:answer-ui`, `smoke:needs-you-ui`, `smoke:blocked-ui`, `smoke:answers`, `smoke:loop-ui`, `smoke:scroll-ui` and `smoke:channels-ui` in order against headless Chrome, a temporary web build, the whole-host test harness and the fake Claude CLI (`scripts/smoke-kit.ts`), and stops at the first failure with that smoke's exit status. `smoke:answers` runs the real `tomte-notify`, answers through the UI and asserts the arguments a fake `herdr` recorded (ADR-0008). `smoke:loop-ui` drives the double-loop chat mode with the fake CLI's `loop.json` (below). `smoke:scroll-ui` checks that the transcript (`packages/web/features/chat/scroller.tsx`) follows streamed replies and stops following only when the reader scrolls up. `smoke:channels-ui` drives the Channels page against a fake Telegram Bot API (`packages/host/src/testing/fake-telegram.ts`): token, link code, linking, Unlink. They are outside `bun run check` because they need Chrome; run them when the answer path, the relay, the sender, the double-loop chat mode, the transcript's scrolling or the Channels page changes. A failed smoke keeps its run directory (screenshots, host log, page console, recorded arguments) and prints its path. Prerequisites, flows and limits: `docs/smoke.md`.

## Double-loop chat mode

A per-bot second chat mode (`Bot.chatMode: "standard" | "double_loop"`, default `standard`; ADR-0011, spec `docs/plans/double-loop-chat.md`). One long-lived, fast **front** session (Haiku, thinking off, whatever the bot's model) answers every message and never blocks the composer; heavy work runs in background agents (`researcher`, `worker`) the front starts, steers (`SendMessage`), queues and stops (`TaskStop`). Each agent's result is posted as the bot's own message (a report). The chat shows only messages: the front's replies arrive whole (no streaming, a "typing…" line meanwhile), and neither its tool calls nor task rows are in the transcript; the Tasks tab follows the tasks. Switching mode starts a new session and is refused with 409 while tasks are queued or running.

The bot's `model` and `effort` (`Bot.model`, `Bot.effort`, saved in `bot.json`, set through `/api/model` and `/api/effort`) are what a standard bot's turns run on and what a double-loop bot's background tasks run on: the observer's PreToolUse hook writes them into every Agent call that names none, so a change reaches the next task without reopening the front.

- Host: `packages/host/src/loop/` (public surface `index.ts`): `front.ts` (`FrontSession`), `agents.ts` (agent definitions, `ProgressAttribution`, the in-process `loop` MCP server), `observe.ts` (SDK messages and hooks to store rows and `ServerEvent`s, including `rate_limit`), `tasks.ts` (registry and queue), `work-state.ts`, `store.ts` (`loop_tasks`, `loop_events`), `guard.ts` (worker path guard). Mode dispatch is in `host-server/chats.ts` (`send`, `deliver`, `reconfigure`, `replayOpen`, presence); the toggle route is `/api/bots/chat-mode`. Reports live only in `loop_events`: replay merges them with the CLI session file and strips the `<work_state>` block the app appends to every message the front receives.
- Web: the "Chat & model" page under the bot panel's Settings tab (`features/chat/settings.tsx`, composed through a slot in `app/routes/bot.lazy.tsx`) holds the mode switch, the model and the effort for both modes; the rate limits sit beside the context meter (`features/chat/rate-limit-meter.tsx`), the Tasks tab is `features/tasks` (also a slot). The reducer state is `chat.presence`, `chat.rateLimits` and the `task`, `task_status` and `report` items in `host/transcript.ts`; the double-loop transcript leaves the `task` items out.
- Rate limits: the front's `rate_limit_event` (status, utilization, reset) is forwarded as an ephemeral `rate_limit` event, kept per window for the account and sent again to a page that connects; only a double-loop bot's page shows it.
- Usage: the front's `result` messages go through the host's one `UsageMeter` (`ThreadEnv.meter`, passed by `openFront` to `FrontSession` and called in its `observe`), like every `Thread` turn, so the front session's `session_usage_marks` row follows its running totals, failed turns included. Nothing reads the front's own turn usage yet (it is a chat, not a run). A double-loop routine run never shares the front's session (its `ownSession` is a fresh id), so the run is charged its own difference and the front's mark is untouched by it. Test: `host-server/double-loop-usage.test.ts`.
- Routines: a double-loop bot's routine runs are always headless, whether its chat is open or not (ADR-0011 "Routine runs"): `routine-turns.ts` starts a job with `ownSession` through `runHeadless` and the parking delegate, so the run parks, resumes and expires exactly like a standard bot's headless run (`waiting`, ADR-0009, `routines/parking.ts`). The run has a session of its own (`routine_runs.session_id` is a fresh id, kept for every resume); the front never receives the routine prompt, a resume message or an expiry notice, and the run reports through its output and the Routines panel, not the front chat (no `routine` line, no last-message preview). It does not block the front or the composer: `RoutineTurns.headless` (what blocks a chat) is for runs in the bot's current session only, `headlessRun`/`Chats.runOf` also see own-session runs (run id and session id) so the run's waits, browser ones included, carry its id and its own session id, and the front's own waits are opened with `runId: null` so they never join a run.
- Fake CLI: `packages/host/src/testing/fake-claude.ts` reads an optional `loop.json` (`host.loopScript(...)` in tests) that scripts what it emits per user message: SDK messages, `stream_event` text, hook callbacks, in-process MCP calls, `can_use_tool` requests, waits on files (`host.allow(name)`) and crashes. The header of the file lists every step. A script's `match` is a substring of the whole message, work state included, so give scripts distinctive matches.
- Smoke: `bun run smoke:loop-ui` (`scripts/smoke-loop-ui.ts`, part of `smoke:ui`; `docs/smoke.md`).
- Routing eval (manual, real model): `bun run eval:loop-routing` runs 31 labelled cases, each a fresh front session over a seeded work state, with every tool call refused so no agent starts: about 31 front sessions and 52 requests on the front's small model, on the user's own Claude sign-in. It exits non-zero below 90%. Ask before running it. `--dry-run` prints the cases, work states and cost and starts nothing; `--cli <path> [--loop-json <file>]` uses another CLI, such as the fake one. Usage and cost are in the header of `scripts/eval-loop-routing.ts`. Record a run in the ADR's "Evaluation" note, and rerun it with a manual restart test when the managed CLI version in `harness/cli.ts` is bumped.
- Manual scenarios with the real CLI (not automated; record timings in the ADR): the v3 drive (start two tasks, ask for status, steer one, "after that" for a queued task, cancel one) and a host restart with two agents running, after which both resume under their ids and report.

## Channels

A channel delivers needs-you items and routine results to the owner outside the web UI and routes answers back (ADR-0010, spec `docs/plans/telegram-channel/spec.md`). Nothing in the answer path knows a channel's transport.

- Host: `packages/host/src/channels/` (public surface `index.ts`, private `store.ts` with `channel_links` and `channel_link_codes`). `Channel` is an adapter (`kind`, `start`, `stop`, `send`, `edit`); `createChannels({ db, onActivity })` holds the registry keyed by kind and the one transport-independent handler `Channels.receive(kind, inbound): Promise<Reply>`. An adapter is built by the composition root with `receive` passed in (`HostServerOptions.channelAdapters`), so a second adapter needs no change anywhere else. A message from the linked account calls `onActivity` once and goes to the handler set with `channels.handle(...)` (an empty reply until a later feature sets one); from anyone else only a code-shaped text does anything (a link attempt, counted like a pairing attempt: 10 failures kill the channel's codes, a new code restarts the count), and every other update gets no reply, changes nothing and is not counted. A `MessageRef` is an opaque string the adapter reads back to edit.
- Telegram (`channels/telegram/`, private to `channels`; `createTelegramChannel` is exported from `index.ts`): `api.ts` is the transport (`getMe`, `getUpdates`, `sendMessage`, `editMessageText`, `answerCallbackQuery`; its errors never carry the URL, which holds the token), `mapping.ts` is the pure half (`inboundOf`: update to `Inbound`, only private chats, no edits, no bots; `callsOf`: `Reply` to calls, an empty reply makes no call, so a stranger's button press gets no `answerCallbackQuery`; an edit always states its keyboard so a card can lose its buttons; text is plain, previews off, cut below 4096) and `channel.ts` is the adapter: one long-polling loop (`timeout=50`, `allowed_updates` `message` and `callback_query`), the offset in memory and advanced after an update is handled, errors back off 1 s to 30 s, 401 stops it (reported as "the bot token was rejected"), 409 is reported and retried, and a spaced, ordered sender that waits out a 429's `retry_after`. A webhook replaces only the loop. The host always runs it (`createHostServer` registers it before `channelAdapters`); `HostServerOptions.telegram` (`baseUrl`, `pollTimeoutSeconds`, `sendSpacingMs`, `backoffMs`) is what tests and smokes set.
- The bot token is the secret `channel-token:telegram` (`channelTokenSecretName` in `platform/secrets.ts`), set by `POST /api/channels/telegram/token` `{token}`: checked with `getMe` first (400 when Telegram rejects it, 502 when it cannot be asked, nothing stored either way), then stored and the loop restarted on it. No route, event or log returns it. Unlinking keeps it. `Channel` has optional `status()`, `linkUrl(code)` and `setToken(token)`; `/api/channels/list` carries each channel's `status` (`unconfigured`, `starting`, `running` with the bot's username, `failed` with a reason) and `/api/channels/link-code` the `https://t.me/<bot>?start=<code>` link.
- Link code: 12 base32 characters in groups of four, single use, 10 minutes, only the digest stored (the pairing code's rules, `device-auth/index.ts`). `/api/channels/list`, `/api/channels/link-code`, `/api/channels/unlink` and `/api/channels/telegram/token` are in `host-server/api/channels.ts`, dispatched by prefix like `/api/devices/`; schemas are in `packages/contract/src/api.ts`.
- Web: `packages/web/features/channels/`, the Channels section of Settings (`/settings/channels`, composed through a slot in `app/routes/settings.lazy.tsx`). The dialog is `PairingCodeDialog`'s twin; the section also has the token field and each channel's status line, and asks the host again every 3 s.
- Cards (ADR-0010, ticket `docs/plans/telegram-channel/issues/03-needs-you-cards.md`): `channels/cards/` (public `createCards({ db, channels, chat, sources, publicUrl, retryMs? })`, returning `sync`, `stop` and `receive`) sends each open needs-you item once to every linked channel as a card, edits it when the item closes anywhere, and routes buttons and words back. `types.ts` has `CardSource` (one per item kind: `kind`, button `prefix`, `open()`, `view(id)`, `press(id, arg)`, `reply(id, text)`); `compose.ts` builds the message (plain text cut at 3000 characters, one button per row, data `<prefix>:<id>:<arg>` of at most 64 bytes, a URL button to `<public URL>/bots/<id>?panel=<panel>` only when the public URL is not loopback http, a hint to reply when an action needs words); `store.ts` is `channel_cards` (V20: channel, item kind `event` or `wait`, item id, bot id, message ref, sent at, closed at; unique per channel, kind and item); `tracker.ts` reconciles it (`sync()` sends missing cards oldest first across sources and edits cards whose item is no longer open, each edit once since `closed_at` is set first; a failed send is retried after `retryMs`, doubling, and a failed edit is logged and dropped); `router.ts` routes a button by prefix and words (a reply goes to the card it replies to, one open card takes a plain message, several ask for a reply, none gets a hint about `@Name`; see "Talking to a bot" below). The host's source is `host-server/event-cards.ts` (kind `event`, prefix `a`, buttons from `itemActions` plus `Dismiss`, arg `d`); A notice (kind `notice`, source "Tomte": an auto-pause, an absence warning, an absence pause; cost-guards ticket 06) is an item like any other and goes out through this same source, with no special path: its card is its title and body, Dismiss only (`itemActions` has no actions for the kind) and a link to `?panel=settings&section=routines` of its bot instead of `work`. Words are never an answer to it: a reply to the card, or a plain message when it is the one open card, gets "A notice takes no reply. Use Dismiss." and reaches no bot. Dismiss closes it everywhere; a notice that closes as `resolved` (a routine resumed, the owner back) has its card edited to "Resolved". Every `Events` change, not only one with transcript rows, syncs the cards, because a notice leaves no transcript row. `channels` imports no feature, so the source is composed in `host-server/index.ts`, which calls `cards.sync()` on start, on link (`Channels.onLinked`), on `Events` `onOpened` and `onChange`, on every wait opening or closing (`waits.subscribe`) and when a bot is removed (`HostServerOptions.cards.retryMs` is for tests). Unlinking, or linking a different account, deletes that channel's `channel_cards`.
- Talking to a bot (ticket `docs/plans/chief-of-staff/issues/03-talk-to-any-bot-from-telegram.md`, spec `docs/plans/chief-of-staff/spec.md`, "Phone: `@Name` and replies"): the channel handler is still the card router; it gains one injected `chat` dependency (`CardChat` in `channels/cards/types.ts`: `send(botId, text, channel)` and `bots()`, newest first), composed in `host-server/phone-chat.ts` (`createPhoneChat`) and passed to `createCards` by `host-server/index.ts`, so `channels` still imports no feature. There is no implicit target: no bot is "the" bot of the phone. Words from the linked account are decided in this order: a Telegram reply to a card goes to that card's source; a message that starts with `@` and a bot's full name (`cards/mention.ts`, `leadingMention`: case-insensitive, runs of spaces collapsed, then a space, `:`, `,` or the end, longest name wins) goes to that bot with the name stripped (a bare name is asked for a message; an unknown name gets the list of the bots' names); otherwise one open card takes the words, several ask for a reply, and with none the owner gets "To talk to a bot, start with @ and its name, for example @<newest bot's name>." `chat.send` is `Chats.send(botId, text, text, [])` with no item id: it queues on a busy bot, reaches a double-loop front as a send, never answers a pending question or approval, and its `queued` and `refused` outcomes are replied as text.
- Origin and replies: `chat_origins` (`SCHEMA_V29`, `bots/origin-store.ts`: `setOrigin`, `getOrigin`, `deleteOrigin`; bot id, `web` or a channel's kind, time) records where the owner's latest message to a bot came from. `/api/send` sets `web`, a routed Telegram message sets `telegram` (neither for a refused send), `removeBot` deletes the row and it survives a restart. `ChatsDeps.botSaid(botId, text)` is called for a standard turn's final text, a double-loop front's reply and each report, never for a scheduled run's turn; `host-server/phone-chat.ts` (`forwardToOrigin`) passes it to `Channels.say(kind, { botId, botName, text })` while the origin is a channel. `say` sends plain text that starts with the bot's name, whole and never edited, with a link button to `<public URL>/bots/<id>` (none on a loopback http public URL), retried with the notices' backoff (`channels/replies.ts`; `deliver` is shared with `notify`) and logged when it still fails; it never rejects. Tests: the router's order and `@Name` cases in `channels/cards/cards.test.ts`, `say` in `channels/channels.test.ts`, a whole host in both chat modes in `host-server/phone-chat.test.ts`, the origin row in `host-server/bot-delete.test.ts`; `smoke:channels-ui` sends one `@Name` message through the fake Bot API and reads the reply.
- Run notices (ADR-0010, ticket `docs/plans/telegram-channel/issues/05-run-notices.md`): `Channels.notify(notice)` sends one plain message, with a URL button to `<public URL>/bots/<id>?panel=settings&section=routines` (none on a loopback http public URL), to the linked account of every channel that has one; no buttons, not tracked after sending. `Notice` (`channels/notices.ts`, a Zod union in the host, not the contract) is `run_failed` (`botId`, `routine`, `error` cut to about 300 characters, `interrupted`) `park_expired` (`botId`, `routine`, `wait`) and `routine_result` (`botId`, `routine`, `output`; ticket 06 below); a new kind is a new member and a new case in `noticeMessage`. A send that fails is tried again 4 times with a doubling wait (`ChannelsDeps.noticeRetryMs`, 2 s; `HostServerOptions.notices.retryMs` for tests) and then logged; `notify` never rejects, and `stop()` ends the retries. The run row stays the record. `createRoutines` takes `onRunEnded(end: RunEnd)`, called once when a run reaches `succeeded`, `failed` or `interrupted` after its row is final (a turn's end, a resumed run's last turn, an expired park, a session that ended a park, a run the last process left running, found by `start()`), never for a skipped run, for a run stopped by `remove()` (the cascade owns it) or for one stopped by shutdown (`stop()` leaves its row `running`, so the next start reports it as interrupted). `RunEnd` is `{ run, routine, expired }`: `expired` holds the titles (`waitTitle`, `waits/index.ts`) of the waits whose 24 hours ran out, so an expiry is told apart without reading the error text. `host-server/run-notices.ts` (`runNotice`) turns it into a notice: `failed` or `interrupted` always, `park_expired` instead of `run_failed` when `expired` is set, nothing for `succeeded` but a routine's result (below); `host-server/index.ts` sends it unless the bot is gone. The channels and their adapters are created before the routines so a park that expired while the host was down is reported by `waits.start()`'s sweep. Tests: `channels/notices.test.ts`, the `notify` block of `channels/channels.test.ts`, the `onRunEnded` tests of `routines/index.test.ts` and `host-server/run-notices.test.ts` (whole host, fake Bot API and fake CLI).
- Human-wait cards (ticket `04-human-wait-cards.md`): `host-server/wait-cards.ts` (kind `wait`, prefix `w`, `createWaitCards({ waits, chats, botName })`) turns each open row of `human_waits` (`Waits.list()`, `Waits.get(id)` for a closed one) into a card: a tool approval (tool, reason and the exact stored input as JSON), an `ask_user` question (its options) and a takeover (reason, link to `?panel=browser`, its own actions). Buttons are `w:<waitId>:<index>`, an index into the wait's stored actions or options, never their text. An approval whose input is over 2400 characters is cut with "…" and "Input too long to show here. Open the web UI to approve.", offers Deny only and refuses any other index at press time. A question about an external event has no card (the event's card answers it through `pendingAskFor`). A button or a reply answers through `Chats.answer` (questions and approvals, as `/api/answer`) or `Waits.answer` (takeovers, as `/api/waits/answer`), never `routines.resume`: the closing wait resumes a parked run itself. A reply denies an approval with the text as its note, answers a question with the text and is refused with "use the buttons" for a takeover. A closed wait's card is edited to "Answered: <label>", "Cancelled", "Expired" or "Timed out". Tests: `host-server/wait-cards.test.ts` (a whole host with the fake Bot API, the fake CLI and parked routine runs).
- Routine results (ADR-0010, ticket `docs/plans/telegram-channel/issues/06-routine-results.md`): a routine opts in with `notifyResult` (`routines.notify_result`, `SCHEMA_V21`, `ALTER TABLE ... ADD COLUMN` guarded by `PRAGMA table_info` like `SCHEMA_V15`, default off, so existing routines stay off; `Routine` in the contract, `RoutineInput`/`RoutinePatch`, `RoutineRecord`; the form's checkbox "Send the result to my phone" in `features/routines/`, which does not import the channels feature and is always enabled), the way `catchUp` travels. `runNotice` turns a `succeeded` run into a `routine_result` notice ("<routine>: <output>", output trimmed and cut to about 800 characters; "<routine> finished" when empty) only when the routine has the flag when the run ends: `createRoutines` re-reads the routine from the store in `ended()`, so switching it off, or deleting the routine, before the end sends nothing, and switching it on sends the result. A failed or interrupted run sends only its failure notice, flag or not. Scheduled, manual and resumed-from-park runs all end through `onRunEnded`, so each sends one. Tests: the `a routine that sends its result` block of `host-server/run-notices.test.ts` and `channels/notices.test.ts`; `smoke:channels-ui` creates a routine through the form and reads the result on the fake Bot API.
- Answers from a channel go through `Chats.send(botId, text, shown, mentions, eventId?, answer?)` (`host-server/chats.ts`), the one function `/api/send` also calls: a pending linked ask first, a queue when the bot is busy, the item closed when the message reaches the bot, for any bot whether or not the page shows it. It returns `SendOutcome`: `answered`, `queued`, `sent` or `refused` with a reason (the route answers a refusal with 409). The web UI's buttons for an item are `itemActions` in `@tomte/contract/item-actions`, shared by the page and the cards; an action with only a draft has no button on a card.
- Tests: `channels/channels.test.ts` (the interface and link, with a fake channel), `channels/telegram/mapping.test.ts` (the pure mapping), `host-server/channels.test.ts` (the HTTP routes on a whole host) and `host-server/telegram.test.ts` (the token route, polling, linking, strangers, 401/409/429 and offsets on a whole host against `testing/fake-telegram.ts`), `channels/cards/cards.test.ts` (the cards with a fake source and the fake channel), `host-server/event-cards.test.ts` (the event source, with a fake events object) and `host-server/needs-you-cards.test.ts` (cards, buttons, words and closing on a whole host against the fake Bot API; `FakeCall.messageId` is the id a sent card got). `testing/fake-channel.ts` is the fake adapter; `startHandoffHost` takes it through its fourth argument (`channelAdapters`, and `telegram` for the fake Bot API's URL). `testing/fake-telegram.ts` is a loopback fake Bot API with real long-poll behaviour that records every call (`outgoing()`, `texts()`); never use a real-looking token with it (`123:fake-token`). `bun run smoke:channels-ui` drives the Channels page against it (part of `smoke:ui`; `docs/smoke.md`).

## Bot creation

Every bot can propose a new bot (spec `docs/plans/chief-of-staff/spec.md`, ticket 01): `create_bot(name, purpose, memory?, chat_mode?)` on the bots endpoint (`handoffs/tools/create-bot.ts`), next to `list_bots` and `hand_off`, for every bot and every session kind (the standard thread, a headless routine run, the double-loop front; the MCP server is per request, so no extra wiring). `BotsToolContext` has `unattended()` and `createBot(spec)`. The tool's guards, in order: refused in a scheduled run; name at most 80 characters, purpose required and at most 400, memory at most 1200 (so the approval card stays under the size at which a channel card offers Deny only); refused when the host has 20 bots. `createBot(dataRoot, name, purpose, id, avatar, memory)` writes a non-blank memory seed to the new bot's memory file; `/api/bots/new` takes no seed. The new bot has the browser off, `chatMode` from `chat_mode` (default `standard`), and the owner's open chat does not move. `BOTS_INSTRUCTIONS` tells the bot to propose only when no bot fits, say why and wait for approval.

The permission is fixed: `ALWAYS_ASK_TOOLS` (`waits/index.ts`) holds `mcp__bots__create_bot`. `createCanUseTool` checks it before `approveAll`, a stored allowance and the `mcp__bots__` allow prefix, so a host that approves everything still raises the normal approval card (`human_waits`: the web UI, the linked channel and `wait-cards.ts` show the tool and the exact input). `approvalActions` leaves out `allow_always` for it, so none is offered and an answer naming it is refused (`/api/answer` 404). Where nobody watches (`HostDelegate.attended()` is false: a chat-hosted routine turn through `hostDelegate`, a headless run through `parkingDelegate`) it is denied at once, with no card and no wait. The double-loop front's bots lease is `attended` (`BotsEndpoint.lease(botId, { attended: true })`), like its routines lease, because its routine runs go headless in sessions of their own.

## Host binary

`bun run build:host [target…]` builds the web UI, then compiles `packages/host/src/main.ts` with `bun build --compile` into `dist/host/tomte-host-<os>-<arch>[.exe]` (gitignored) for `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64` and `windows-x64`; name targets to build only those. `scripts/build-host.ts` explains the x64 baseline, minify and sourcemap choices. The built web UI is embedded (`ui/assets.ts`); Vite, the Claude CLI and the browser engine are not.

`main.ts` is the one compiled entry and also runs from source: `[flags] [botId]` starts the server like `bun run ui`; `pair`, `install-cli`, `install-browser`, `browser-smoke`, `auth-status` and `auth-login` run the `host.ts` subcommands; `auth-status` and `auth-login` run the Claude CLI's `auth status` and `auth login` with the environment the host gives its bots' CLI children (in remote mode, which runs on Linux only and is refused on macOS and Windows (ADR-0006), the allowlist and `claude/` in the data root as `CLAUDE_CONFIG_DIR`); after a successful login, `auth-login` runs a fresh `auth status` and exits non-zero when it still reports signed out. Any message that names a command goes through `platform/launch.ts` (`hostCommand`, `serverCommand`), so it names the binary or `bun run host` depending on how the host was started.

`--sidecar` (local mode only) is how the desktop app runs the host: it reads one launch-token line from stdin and registers it as the device "This computer" (replacing the previous launch device), prints one `SidecarReady` JSON line with its client URL to stdout (everything human-readable goes to stderr), installs the managed Claude CLI into the data root when none resolves, installs the browser in the background when neither the bundled copy nor a managed one resolves (`browser/auto-install.ts`; until it is done the browser's unavailable reason says it is installing instead of naming `install-browser`, and a failed install is retried on the next status check), and shuts down gracefully, releasing the data-root lock, when stdin ends; without the flag the host never reads stdin. The shared shapes live in `@tomte/contract/sidecar`.

`bun run smoke:host [binary]` (default: this machine's build output) runs a built binary for real: it copies it outside the repo, installs the managed Claude CLI with `install-cli` (unless `CLAUDE_PATH` names one), starts it on a temporary data root, pairs with `pair`, creates a bot, checks the event stream, loads the embedded UI (every asset `index.html` references, with the CSP), checks what the client listener refuses, stops it with SIGTERM and removes everything. It needs network for the CLI install and runs only a binary built for the machine it runs on (for a Linux binary in a container, compile the script with `bun build --compile --target=bun-linux-arm64 scripts/smoke-host.ts` and run both binaries there).

## Desktop app

`packages/desktop/` (`@tomte/desktop`) is the Electron app. Its main process runs no host code (dependency-cruiser rule `desktop-only-to-contract`, ADR 0003): it spawns the host binary with `--sidecar`, writes a fresh launch token to its stdin, keeps the pipe open, waits for the ready line, sets the `tomte_session` cookie in its own session and loads the host's client URL. The window has context isolation and the sandbox on, no Node and no preload. Navigation is limited to the host's origin; other web URLs and every `window.open` go to the system browser or are denied (`navigation-policy.ts`). Quitting ends the sidecar's stdin and waits for the host to exit; if the app dies, the host sees EOF and stops itself. It keeps its own user-data folder, `Tomte Desktop` under the OS app-data folder, apart from the host's data root; `--user-data-dir` overrides it.

On macOS the main window has a hidden title bar with Window Controls Overlay (`window-chrome.ts`: `titleBarStyle: "hidden"`, `titleBarOverlay: { height: 56 }`), so the real close, minimize and zoom buttons sit beside the web app's own header and there is no separate OS title strip; Windows and Linux keep the default frame. The web UI is a sheet on a desk (the sidebar's `variant="inset"`; palette and `--sheet-shadow` in `tailwind.css`, after Nuphos's design tokens): the sidebar sits on the canvas and the content is one rounded sheet 8px inside the window, whose top row is the header (`AppBar` in `packages/web/components/page.tsx`, `h-10`). A bot's chat with its panel open beside it (1024px and wider) is two sheets instead, 8px apart: the shell's inset goes bare for a child marked `data-split` (`app/shell.tsx`) and `ChatView` (`features/chat/chat.tsx`) gives the chat and the panel each the sheet's background, corners and shadow. 8 + 40 + 8 is `TITLE_BAR_HEIGHT`, so the lights and the header share one centre line; change them together. The web app reads `navigator.windowControlsOverlay` (`packages/web/lib/window-controls-overlay.ts`) and sets `data-wco` on `<html>` (Electron's `display-mode: window-controls-overlay` media query is false, so CSS cannot gate on it); only then the header, the sidebar's top strip (`TitlebarStrip`, `data-titlebar`, 40px from y 8, level with the header) and the shell's 8px strip along the window's top edge are `-webkit-app-region: drag` and the controls inside them `no-drag` (`tailwind.css`). The lights sit over the sidebar's strip; when the sidebar is collapsed or the window is narrow the header pads left by `env(titlebar-area-x)`. In a browser tab and in fullscreen `env()` falls back to 0, so the page is unchanged. The desktop shell's own pages (`window.ts`) get the same drag strip through `env(titlebar-area-height)`. The Connections window keeps the standard title bar. A remote host serving an older web build has none of this CSS: the lights overlay the top-left of its UI and nothing in it is draggable until that host is updated.

Closing the window hides it (and the dock icon, on macOS); the app and the host keep running in the tray (`background.ts`). The tray (`tray.ts`, menu in `tray-menu.ts`) has a template icon (`packages/desktop/assets/trayTemplate.png` and `@2x`, drawn by `bun run icons:desktop`, copied next to the bundle by `build:desktop`), shows the host's state (starting, running, stopped) in its tooltip and first, disabled item, and offers one radio item per connection profile (the active one checked) and Manage Connections…, Open Tomte, Start at login, Restart host (only while stopped, with a fresh launch token) and Quit Tomte. The state comes from `supervisor.ts`, which follows the sidecar's `exited` promise. Every way of quitting (tray, app menu, Cmd+Q) ends in `app.quit()` and the `before-quit` handler in `main.ts`, which ends the host's stdin and waits for it (bounded, then kill) before exiting.

Start at login is a desktop setting in `settings.json` in the user-data folder (`{ "startAtLogin": boolean }`, Zod-parsed; a missing file is a first launch and means true, an unreadable one means false and is left alone). Every launch applies it to the OS through the `LoginItem` interface (`login-item.ts`); the tray checkbox changes the file and the login item (`start-at-login.ts`). The OS implementation (`electron-login-item.ts`) calls `app.setLoginItemSettings` and passes `--hidden`; an app the OS opened at login (`wasOpenedAtLogin`, or `--hidden`) starts with its window hidden. When `TOMTE_DESKTOP_LOGIN_ITEM_FILE` names a file, the login item is recorded there as `{ "openAtLogin": boolean }` instead and the OS is never asked: every smoke and test on a developer machine sets it, so nothing registers itself at login.

Needs-you banner (`desktop-banner.ts`, `needs-you-banner.ts`, `bots-stream.ts`): the main process follows the active connection's `/api/events` stream with the credentials it already holds (`Connections.credentials()`: the launch token's device for this computer, the profile's device token for a remote; the followed host changes with `onChange`) and parses only the `bots` slice with the contract schema; every other event is skipped unparsed. When the total `needsYou` across bots rises while the window is hidden, it shows one Electron `Notification` ("<bot>: N things need you", the bot's `needsYouSources` as body, the bot with the newest `needsYouAt`). A later rise while the window stays hidden closes it and shows a new one; showing the window closes it; clicking it reveals the window and loads `/bots/<id>` of the bot with the newest open item. The first slice of every stream is a baseline, never a rise. It is a main-process Electron notification, so the web page keeps getting no notification permission. The smoke replaces `Notification` with a recording stub and calls the click handler, so no OS banner or OS notification permission is involved.

Auto-update (`electron-updater`, the one npm dependency of the desktop package beyond Zod; it is bundled into `main.cjs`). A packaged app checks the update feed named by its own `app-update.yml` (this repository's GitHub Releases in a release build): the first check 30 s after start, then every 6 h, downloading in the background as soon as a newer release is found. The update installs when the app quits (electron-updater's quit handler, which the `quit` event of the app's own `app.exit(0)` reaches) or at once through the tray item "Restart to update to <version>", which appears only after a download. Both go through the one graceful quit: `before-quit` stops the sidecar and waits for it, and only then the installer runs (`installUpdateOrExit` in `main.ts`), so the host binary the update replaces is not running. If the install cannot start, the app logs it and relaunches itself instead of hanging. After the sidecar is ready the app reads its `/api/host-info` and logs whether the host's version equals `app.getVersion()` (`WARNING: the host reports version …` on a mismatch); this runs in a packaged app only. Pre-releases are offered only when the running version is itself a pre-release (`allowPrerelease`); electron-updater then follows the same pre-release channel (an `-rc.N` app moves to a newer `-rc.N` tag, never to the stable release; a stable install never sees a pre-release). Every build is on the metadata channel `latest` (`CHANNEL` in `scripts/desktop-kit.ts`): electron-builder would otherwise name a pre-release's metadata `rc-mac.yml`, which the release does not hold; electron-updater asks `rc-*.yml` first for a pre-release tag, gets a 404 and falls back to `latest-*.yml`. Failures (feed unreachable, bad metadata, a failed download, Squirrel.Mac refusing an unsigned app) are logged and never stop the app. The log is `logs/desktop.log` in the user-data folder (every line the desktop process logs, timestamped; the host's stays `logs/host.log`).

No update check runs when the app is not packaged, when `app-update.yml` is missing, when its feed is the local build's placeholder (a `.invalid` host; it is never contacted) or when `TOMTE_DESKTOP_UPDATES=off`. `createSmokeRun` (`scripts/desktop-smoke-kit.ts`) puts that off-switch in the environment of every smoke launch (a launch that wants updates passes `TOMTE_DESKTOP_UPDATES=on` as an extra). The logic is in `updates.ts` behind the small `UpdateEngine` interface (`createUpdater`: schedule, state, logging; fakes in `updates.test.ts`); `electron-update-engine.ts` is the electron-updater implementation, `desktop-log.ts` the log.

## Releasing

A release is a `v*` tag. Pushing one runs `.github/workflows/release.yml`: `verify` (the tag is `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-prerelease` and equals `v` + the host's `VERSION`), then `host` (a matrix that builds each of the five host binaries with `build:host <target>` on a native runner, runs `smoke:host` on it and uploads it as the artifact `release-host-<target>`; every target has a native runner, but `ubuntu-24.04-arm` is free for public repositories only), then `desktop` (a matrix on native runners, macOS, Windows and Linux: downloads the `release-host-*` artifacts for its OS, runs `package:desktop --host-dir hosts` with the version from `VERSION` and `GITHUB_REPOSITORY`, then `bun scripts/release.ts desktop` checks that the host inside every app, and inside the macOS update zip, is byte-identical to the host job's binary, that the update metadata names the release version and that every installer exists, copies exactly the installers, blockmaps and metadata out and uploads them as `release-desktop-<os>`; the macOS job packages arm64 and x64 together so there is a single `latest-mac.yml` and nothing for the artifact merge to collide on), then `publish` (the only job with `contents: write`: it merges every `release-*` artifact into one folder, writes `SHA256SUMS` over all of it with `scripts/release.ts checksums`, which fails unless all five host binaries and every supported installer and update metadata file are there, and creates the GitHub Release with `gh`, as a draft until every asset is uploaded; a tag with a pre-release suffix such as `-rc.1` makes a pre-release). A rerun of a failed publish replaces the assets of the Release that exists. Desktop installers join the same Release: a job that uploads artifacts named `release-*` and is added to `publish.needs` ends up in the Release and in `SHA256SUMS`.

The host's version is `VERSION` in `packages/host/src/harness/claude-access.ts` (no `package.json` carries a version). To cut a release:

1. Set `VERSION` to the version without the `v` (`0.2.0`, or `0.2.0-rc.1` for a pre-release; a pre-release suffix is part of `VERSION`), run `bun run check`, commit and merge to the default branch.
2. Tag that commit and push the tag: `git tag v0.2.0 && git push origin v0.2.0`.
3. Watch the `Release` run. A tag that does not match `VERSION` fails `verify` before anything is built; fix `VERSION` (or delete the tag), then tag again.
4. Check the Release: five `tomte-host-<os>-<arch>[.exe]` files, `install.sh` (its `DEFAULT_REPO` filled in with the repository), `tomte.service` and `SHA256SUMS`; `sha256sum --check SHA256SUMS` in the download folder passes. `deploy/install.sh` installs a release's Linux binary without `--url` (`--repo`, `--version`; see `deploy/README.md`).

Check a published Release offline with `bun scripts/release.ts verify-release <folder> <version>` (`scripts/release-verify.ts`, tests in `scripts/release-verify.test.ts`), on the folder `gh release download v0.2.0-rc.1 -R OWNER/REPO -D <dir>` filled (version without the `v`, e.g. `0.2.0-rc.1`). It reads only; it exits 1 and lists every problem, or exits 0 and prints "a complete, consistent release". It checks that the folder holds exactly the published files and nothing else (the five host binaries, every `SUPPORTED_DESKTOP` installer, its `.blockmap` (the `.deb` has none), `latest-mac.yml`, `latest.yml`, `latest-linux.yml`, `install.sh`, `tomte.service`, `SHA256SUMS`); that `SHA256SUMS` lists exactly those files, once each, and every sha256 matches; that `install.sh` has `DEFAULT_REPO="OWNER/REPO"` filled in; and that each `latest*.yml` names the version, lists the file the updater applies (the mac zips, the NSIS exe, the AppImage) and that every file it lists exists with the sha512 and size it states. It does not check signatures, that the host inside an installer is the release's (the workflow's `release.ts desktop` did), or that anything runs.

Run the two release steps locally with `bun scripts/release.ts tag v0.2.0` (prints `version=` and `prerelease=`; exits non-zero on a mismatch) `bun scripts/release.ts desktop <bundleDir> <hostDir> <outDir> <version> <arch>…` (the check and collection of one `package:desktop` run for this OS) and `bun scripts/release.ts checksums <folder> <version>` (the folder must hold the five binaries and every supported installer and metadata file); `scripts/release-kit.test.ts` and `scripts/desktop-kit.test.ts` cover the tag rules, the checksum format and the desktop host check.

Installers are released for macOS (arm64 and x64: dmg and zip), Windows x64 (NSIS) and Linux x64 (AppImage and deb); `SUPPORTED_DESKTOP` in `scripts/desktop-kit.ts` is the list and `publish` fails when any of its files is missing. linux-arm64 and Windows arm64 are host-only. Whether the macOS and Windows installers are signed depends on the signing secrets (next section); without them they are unsigned and unnotarized, macOS Gatekeeper and Windows SmartScreen warn on first launch, and macOS auto-update of an unsigned app is not expected to work. Linux packages are never signed. The Windows and Linux installers are built only by the workflow and have not been run anywhere yet. On Windows `smoke:host` terminates the host instead of sending SIGTERM and skips the graceful-exit and lock checks.

### Signing and notarization

Signing needs credentials only a person can create, so the release signs when the repository has them and stays unsigned when it has not. Nothing about it can be exercised locally (no workflow or script here ever signs on a developer machine: `bun scripts/signing.ts sign-host` refuses to run outside GitHub Actions, and `package:desktop` signs only with `--sign`, below).

The one local exception is an explicit opt-in route for a personal test build: `bun scripts/sign-local.ts plan|run|cleanup` (`bun run sign:local`; guide `docs/release/local-signing.md`) signs and notarizes an arm64 DMG, update zip and host on this Mac from a `.p12` and an App Store Connect key named in `TOMTE_LOCAL_*` environment variables, in a temporary keychain inside `--out`. `plan` prints every operation and runs nothing; `run` refuses in CI and without `--confirm-keychain-and-notary-upload`. It reaches `package-desktop.ts` through `--sign --local-keychain <file> --local-identity <sha1>`, which is mutually exclusive with the CI path (`CSC_LINK`); the CI workflow, `signing.ts` and its checks behave as described below (the macOS checks now live in `scripts/mac-verify.ts`, shared by both). It has been tested against fakes only; nothing in it has run against a real keychain or Apple's notary service.

The local route has two notary backends, exactly one per run: an API key (`TOMTE_LOCAL_API_KEY_*`, `notarytool`) or a saved profile of the Rork ASC CLI (`TOMTE_LOCAL_ASC_PROFILE`, optionally `TOMTE_LOCAL_ASC_BIN`; `scripts/asc-notary.ts`). With `asc` the packaging run is given `--local-notary asc --local-asc-profile <name> --local-asc-bin <path> --local-notary-record <file>`, electron-builder's own notarization is off (`notarize: false`) and an `afterSign` hook zips the signed app, runs `asc --profile <name> notarization submit --file <zip> --wait --output json`, staples with `xcrun stapler` and writes the submission to the record file; the route submits the DMG the same way. Both backends write `<out>/artifacts/NOTARIZATION.json` (submission ids, statuses, sha256). The CI route is unchanged. The asc output shape and exit codes are unobserved.

What the workflow does when a platform's secrets are all set (`scripts/signing.ts`, the decisions and checks in `scripts/signing-kit.ts`, covered by `scripts/signing-kit.test.ts` with fixtures and no certificates):

1. `verify` runs `signing.ts plan` with only whether each secret is set (never a value) and outputs `sign_mac` and `sign_windows`; the job summary lists each platform as signed or UNSIGNED.
2. `host` (macOS and Windows legs) runs `signing.ts sign-host` on the binary it just built, before `smoke:host`, so the smoke run starts the signed binary under the hardened runtime and the Release publishes it. macOS: a temporary keychain holds the certificate, `codesign --options runtime --timestamp --entitlements scripts/entitlements.mac.plist` signs with the Developer ID Application identity (it fails unless the certificate holds exactly one), and the keychain is deleted. Windows: `Set-AuthenticodeSignature` (SHA-256, timestamped by `http://timestamp.digicert.com`), chosen over `signtool` because it ships on every Windows image and needs no Windows SDK path.
3. `desktop` runs `package:desktop --sign`. electron-builder imports the same certificate into a keychain of its own (`CSC_LINK`), signs the app and its helpers with the hardened runtime and `scripts/entitlements.mac.plist`, notarizes with `notarytool` (App Store Connect API key) and staples the ticket, then builds the dmg and the update zip from the stapled app. It leaves the bundled host alone (`mac.signIgnore`, and `!tomte-host.exe` in `SIGNED_WIN.signExts` on Windows) because the host arrives already signed with the same certificate, and a second signature would break the byte-identity `release.ts desktop` checks. On Windows it signs the app, the uninstaller and the NSIS installer with the same PFX (`WIN_CSC_LINK`), and `SIGNED_WIN.signExts` in `signing-kit.ts` is `[".dll", "!tomte-host.exe"]`: electron-builder signs `.exe` by default and a positive `.dll` adds the libraries, which includes Chrome's; never add a positive `.exe` pattern, a positive match beats the `!` and the host would be re-signed. The same `.dll` also signs Electron's own top-level DLLs and anything in `app.asar.unpacked`, and cannot spare `D3DCompiler_47.dll`, which ends up with our signature in place of Microsoft's.
4. `Verify signing` (only when signed) runs `signing.ts verify` on the runner: macOS, for every arch's unpacked app and for the app inside its update zip: `codesign --verify --deep --strict`, `spctl --assess --type execute`, `xcrun stapler validate`, and the app's and the host's `codesign -dvv` must both be a Developer ID Application signature with the hardened runtime and a secure timestamp, the same leaf certificate and the same Team ID, with the host holding the entitlements, plus the browser parts listed under Desktop app above; Windows: `Get-AuthenticodeSignature` on the installer, the app exe, the host exe, `agent-browser.exe` and every `.exe` and `.dll` under `browser-engine\chrome` must all be `Valid`, timestamped and carry one certificate thumbprint. `release.ts desktop` then still checks that the host in every app is byte-identical to the one the host job uploaded.

`scripts/entitlements.mac.plist` grants `com.apple.security.cs.allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation` and nothing else; it is the one file for the Electron app, its helpers, Chrome and the Bun-compiled host (V8 and JavaScriptCore both JIT). `disable-library-validation` is there for Chrome: the pinned zip carries a Google-signed `libwidevinecdm.dylib` (and Chrome's component updater may fetch newer Google-signed CDMs), which a Chrome re-signed under our Team ID cannot load with library validation on; Chromium's own plugin-helper entitlements grant the same pair (`@electron/osx-sign`'s `default.darwin.plugin.plist`). electron-builder gives the one `entitlements` file to the main app and `entitlementsInherit` to everything else, so the host and Electron's helpers get it too, though the host does not need it. `MAC_ENTITLEMENT_KEYS` in `signing-kit.ts` is the list `signing.ts verify` requires on the host, Chrome and every helper app, so the plist and the check move together. If a signed binary needs more, the host job's smoke run (which runs the signed host) or the macOS smoke fails; add the entitlement there and to `MAC_ENTITLEMENT_KEYS`.

Secrets (repository secrets; each platform's set is all-or-nothing, and a partly set platform always fails the release):

| Secret                         | Content                                                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `MACOS_CERTIFICATE_P12`        | base64 of the Developer ID Application certificate with its private key, as a `.p12` holding exactly one identity |
| `MACOS_CERTIFICATE_PASSWORD`   | the `.p12`'s password                                                                                             |
| `APPLE_API_KEY_P8`             | the text of the App Store Connect API key (`AuthKey_<id>.p8`) used by `notarytool`                                |
| `APPLE_API_KEY_ID`             | that key's Key ID                                                                                                 |
| `APPLE_API_ISSUER`             | the issuer ID shown above the team keys list                                                                      |
| `WINDOWS_CERTIFICATE_PFX`      | base64 of the code signing certificate with its private key, as a `.pfx`                                          |
| `WINDOWS_CERTIFICATE_PASSWORD` | the `.pfx`'s password                                                                                             |

Secrets reach only the steps that need them, as environment variables of that step (`verify` gets only "set" or empty; the macOS and Windows host steps and the `Package` step get their own OS's), and no script prints a value or puts one on a command line it logs (`security import -P` does take the `.p12` password as an argument on the runner).

Fail closed: set the repository **variable** (not a secret) `TOMTE_REQUIRE_SIGNING` to `true` (`gh variable set TOMTE_REQUIRE_SIGNING --body true`). Then a release whose macOS or Windows secrets are missing fails in `verify`, before anything is built, and `package:desktop` itself refuses to run unsigned for macOS and Windows. Without the variable, a platform with no secrets is built unsigned as before and the job summary says UNSIGNED. A platform with some but not all secrets fails either way.

`bun run package:desktop --sign` is the same code path the workflow takes, for a person who really has the credentials in the environment (the secret names above, as environment variables); without `--sign` the credentials in the environment are ignored and removed. It exits non-zero before building when any secret of this OS is missing, and Linux ignores it.

What a person has to do once (this is the part of ticket 06 no script can do):

1. macOS, with a paid Apple Developer Program membership: create a **Developer ID Application** certificate (developer.apple.com, Certificates; only the Account Holder can; or Xcode, Settings, Accounts, Manage Certificates). In Keychain Access export the certificate together with its private key as a `.p12` with a strong password. Create an App Store Connect **team API key** (Users and Access, Integrations, Team Keys) with at least the Developer role, download the `.p8` (Apple shows it once), and note the Key ID and the Issuer ID.
2. Windows: obtain a code signing certificate (OV or EV) from a certificate authority and export it with its private key as a `.pfx`. Caveat: since June 2023 the CA/Browser Forum requires the private keys of newly issued code signing certificates to live on a hardware token or an HSM, so a new certificate usually cannot be exported to a `.pfx`; if yours cannot, this PFX path does not apply and `signHostWindows` in `scripts/signing.ts` and `SIGNED_WIN` in `scripts/package-desktop.ts` must change to your CA's cloud signing or Azure Trusted Signing before the Windows secrets mean anything. Decide that before buying the certificate.
3. Store them as repository secrets under the names above, for example `base64 -i certificate.p12 | gh secret set MACOS_CERTIFICATE_P12`, `gh secret set MACOS_CERTIFICATE_PASSWORD`, `gh secret set APPLE_API_KEY_P8 < AuthKey_XXXXXXXXXX.p8`, `gh secret set APPLE_API_KEY_ID`, `gh secret set APPLE_API_ISSUER`, `base64 -i certificate.pfx | gh secret set WINDOWS_CERTIFICATE_PFX`, `gh secret set WINDOWS_CERTIFICATE_PASSWORD`. Then delete the exported files.
4. Cut a pre-release (`v0.2.0-rc.1`, see above) and read the `verify` job summary: it must say macOS and Windows are signed. Once a signed release has passed, set `TOMTE_REQUIRE_SIGNING` to `true`.
5. Check the result the way a user meets it. macOS: download the `.dmg` in a browser on a Mac that has never seen the app (that sets the quarantine flag), open it and launch the app: no "cannot verify the developer" dialog. In a terminal, on the installed app: `spctl --assess --type execute --verbose=4 /Applications/Tomte.app` prints `accepted` and `source=Notarized Developer ID`, `xcrun stapler validate /Applications/Tomte.app` prints `The validate action worked!`, and `codesign -dvv /Applications/Tomte.app` and `codesign -dvv /Applications/Tomte.app/Contents/Resources/tomte-host` show the same `TeamIdentifier`. Windows: download `Tomte-Setup-<version>.exe` in Edge on a machine that has never seen it and run it: no "Windows protected your PC" block (an OV certificate may still warn until the file has reputation; that is not a signing failure), and `Get-AuthenticodeSignature .\Tomte-Setup-<version>.exe | Format-List` shows `Status : Valid` and the publisher; Properties, Digital Signatures on the installed `Tomte.exe` and `resources\tomte-host.exe` shows the same signer.
6. Whether the keychain items a bot created survive an update (the host's signature is what macOS ties them to) is the update check of ticket 07.
