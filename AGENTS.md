## Checks

`bun run check` is the full gate; run it before calling work done. It runs, in order and stopping at the first failure: `fmt:check` (oxfmt), `lint` (oxlint, type-aware), `knip` (dead files, exports and dependencies), `typecheck` (tsgo, per package), `depcheck` (dependency-cruiser, ADR 0003 layering) and `test` (`bun test`). Each is also a script of its own. `bun run fmt` rewrites formatting in place.

`bun test` always runs with coverage (`bunfig.toml`: `coverage = true`, test files excluded, `text` and `lcov` reporters; `coverage/` is gitignored). Two gates apply, and `bun run test` (so `check` and CI) runs both:

- Per file: `coverageThreshold` makes `bun test` exit non-zero when any covered file's line or function coverage is below it. Bun applies it per file, not to the "All files" total, and only reads the plural keys `lines`/`functions` (singular keys are silently ignored; an omitted key defaults to 0.9). It is a floor: the lowest per-file value measured, rounded down to a whole percent.
- Total: `scripts/check-coverage.ts` sums `coverage/lcov.info` and fails when total line or function coverage is below its `BASELINE` constants, the measured totals rounded down to a whole percent. Bun only reports files that tests load, so a new module no test imports does not lower the total.

Raise both as tests land, never lower them; if coverage genuinely drops, add tests instead.

### Git hooks

Git hooks come from lefthook (`lefthook.yml`) and are installed by `bun install` via the `prepare` script; it skips quietly outside a git checkout.

- pre-commit (staged files, parallel): `oxfmt --check`, `oxlint`, `gitleaks git --staged`. A format failure means run `bun run fmt` and re-stage.
- commit-msg: `commitlint` checks the message against Conventional Commits (`commitlint.config.js`).
- pre-push: `bun run check`.
- Prerequisite: [`gitleaks`](https://github.com/gitleaks/gitleaks) is a Go binary, not an npm dependency. Install it yourself (`brew install gitleaks` on macOS); pre-commit fails with an install hint when it is missing.

### CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`/`master`. Jobs: `check` (`bun install --frozen-lockfile`, then `bun run check`), `pr-title` (pull requests only; commitlint on the PR title, since squash merges use it as the commit message), `sherif` (`bunx sherif`, monorepo dependency consistency), `secrets` (gitleaks over the full history, config in `.gitleaks.toml`) and `audit` (`bun audit`, non-blocking until it exits 0; then drop `continue-on-error` in the workflow). The Bun version comes from `.bun-version`.

Branch protection is repo settings, not code. Once the repo is on GitHub, require the `check`, `secrets`, `pr-title` and `sherif` jobs (not `audit` while it is non-blocking) (replace `OWNER/REPO` and the branch):

```sh
gh api -X PUT repos/OWNER/REPO/branches/main/protection --input - <<'JSON'
{"required_status_checks":{"strict":true,"contexts":["check","secrets","pr-title","sherif"]},"enforce_admins":false,"required_pull_request_reviews":null,"restrictions":null}
JSON
```

### Browser smokes of the answer path

`bun run smoke:ui` runs `smoke:answer-ui`, `smoke:needs-you-ui`, `smoke:blocked-ui` and `smoke:answers` in order against headless Chrome, a temporary web build, the whole-host test harness and the fake Claude CLI (`scripts/smoke-kit.ts`), and stops at the first failure with that smoke's exit status. `smoke:answers` runs the real `claudebot-notify`, answers through the UI and asserts the arguments a fake `herdr` recorded (ADR-0008). They are outside `bun run check` because they need Chrome; run them when the answer path, the relay or the sender changes. A failed smoke keeps its run directory (screenshots, host log, page console, recorded arguments) and prints its path. Prerequisites, flows and limits: `docs/smoke.md`.

## Host binary

`bun run build:host [target…]` builds the web UI, then compiles `packages/host/src/main.ts` with `bun build --compile` into `dist/host/claudebot-host-<os>-<arch>[.exe]` (gitignored) for `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64` and `windows-x64`; name targets to build only those. `scripts/build-host.ts` explains the x64 baseline, minify and sourcemap choices. The built web UI is embedded (`ui/assets.ts`); Vite, the Claude CLI and the browser engine are not.

`main.ts` is the one compiled entry and also runs from source: `[flags] [botId]` starts the server like `bun run ui`; `pair`, `install-cli`, `install-browser`, `browser-smoke`, `auth-status` and `auth-login` run the `host.ts` subcommands; `auth-status` and `auth-login` run the Claude CLI's `auth status` and `auth login` with the environment the host gives its bots' CLI children (in remote mode, which runs on Linux only and is refused on macOS and Windows (ADR-0006), the allowlist and `claude/` in the data root as `CLAUDE_CONFIG_DIR`); after a successful login, `auth-login` runs a fresh `auth status` and exits non-zero when it still reports signed out. `credential-plugin <url>` is internal (the browser engine spawns the binary with it). Any message that names a command goes through `platform/launch.ts` (`hostCommand`, `serverCommand`), so it names the binary or `bun run host` depending on how the host was started.

`--sidecar` (local mode only) is how the desktop app runs the host: it reads one launch-token line from stdin and registers it as the device "This computer" (replacing the previous launch device), prints one `SidecarReady` JSON line with its client URL to stdout (everything human-readable goes to stderr), installs the managed Claude CLI into the data root when none resolves, installs the browser in the background when neither the bundled copy nor a managed one resolves (`browser/auto-install.ts`; until it is done the browser's unavailable reason says it is installing instead of naming `install-browser`, and a failed install is retried on the next status check), and shuts down gracefully, releasing the data-root lock, when stdin ends; without the flag the host never reads stdin. The shared shapes live in `@claudebot/contract/sidecar`.

`bun run smoke:host [binary]` (default: this machine's build output) runs a built binary for real: it copies it outside the repo, installs the managed Claude CLI with `install-cli` (unless `CLAUDE_PATH` names one), starts it on a temporary data root, pairs with `pair`, creates a bot, checks the event stream, loads the embedded UI (every asset `index.html` references, with the CSP), checks what the client listener refuses, stops it with SIGTERM and removes everything. It needs network for the CLI install and runs only a binary built for the machine it runs on (for a Linux binary in a container, compile the script with `bun build --compile --target=bun-linux-arm64 scripts/smoke-host.ts` and run both binaries there).

## Desktop app

`packages/desktop/` (`@claudebot/desktop`) is the Electron app. Its main process runs no host code (dependency-cruiser rule `desktop-only-to-contract`, ADR 0003): it spawns the host binary with `--sidecar`, writes a fresh launch token to its stdin, keeps the pipe open, waits for the ready line, sets the `claudebot_session` cookie in its own session and loads the host's client URL. The window has context isolation and the sandbox on, no Node and no preload. Navigation is limited to the host's origin; other web URLs and every `window.open` go to the system browser or are denied (`navigation-policy.ts`). Quitting ends the sidecar's stdin and waits for the host to exit; if the app dies, the host sees EOF and stops itself. It keeps its own user-data folder, `Claudebot Desktop` under the OS app-data folder, apart from the host's data root; `--user-data-dir` overrides it.

On macOS the main window has a hidden title bar with Window Controls Overlay (`window-chrome.ts`: `titleBarStyle: "hidden"`, `titleBarOverlay: { height: 56 }`), so the real close, minimize and zoom buttons sit in the web app's own 56px header (`AppBar` in `packages/web/components/page.tsx`, `h-14`; keep `TITLE_BAR_HEIGHT` equal to it) and there is no separate OS title strip; Windows and Linux keep the default frame. The web app reads `navigator.windowControlsOverlay` (`packages/web/lib/window-controls-overlay.ts`) and sets `data-wco` on `<html>` (Electron's `display-mode: window-controls-overlay` media query is false, so CSS cannot gate on it); only then the header and the sidebar's top strip (`TitlebarStrip`, `data-titlebar`) are `-webkit-app-region: drag` and the controls inside them `no-drag` (`tailwind.css`). The lights sit over the sidebar's strip; when the sidebar is collapsed or the window is narrow the header pads left by `env(titlebar-area-x)`. In a browser tab and in fullscreen `env()` falls back to 0, so the page is unchanged. The desktop shell's own pages (`window.ts`) get the same drag strip through `env(titlebar-area-height)`. The Connections window keeps the standard title bar. A remote host serving an older web build has none of this CSS: the lights overlay the top-left of its UI and nothing in it is draggable until that host is updated.

Closing the window hides it (and the dock icon, on macOS); the app and the host keep running in the tray (`background.ts`). The tray (`tray.ts`, menu in `tray-menu.ts`) has a template icon (`packages/desktop/assets/trayTemplate.png` and `@2x`, drawn by `bun run icons:desktop`, copied next to the bundle by `build:desktop`), shows the host's state (starting, running, stopped) in its tooltip and first, disabled item, and offers one radio item per connection profile (the active one checked) and Manage Connections…, Open Claudebot, Start at login, Restart host (only while stopped, with a fresh launch token) and Quit Claudebot. The state comes from `supervisor.ts`, which follows the sidecar's `exited` promise. Every way of quitting (tray, app menu, Cmd+Q) ends in `app.quit()` and the `before-quit` handler in `main.ts`, which ends the host's stdin and waits for it (bounded, then kill) before exiting.

Start at login is a desktop setting in `settings.json` in the user-data folder (`{ "startAtLogin": boolean }`, Zod-parsed; a missing file is a first launch and means true, an unreadable one means false and is left alone). Every launch applies it to the OS through the `LoginItem` interface (`login-item.ts`); the tray checkbox changes the file and the login item (`start-at-login.ts`). The OS implementation (`electron-login-item.ts`) calls `app.setLoginItemSettings` and passes `--hidden`; an app the OS opened at login (`wasOpenedAtLogin`, or `--hidden`) starts with its window hidden. When `CLAUDEBOT_DESKTOP_LOGIN_ITEM_FILE` names a file, the login item is recorded there as `{ "openAtLogin": boolean }` instead and the OS is never asked: every smoke and test on a developer machine sets it, so nothing registers itself at login.

Needs-you banner (`desktop-banner.ts`, `needs-you-banner.ts`, `bots-stream.ts`): the main process follows the active connection's `/api/events` stream with the credentials it already holds (`Connections.credentials()`: the launch token's device for this computer, the profile's device token for a remote; the followed host changes with `onChange`) and parses only the `bots` slice with the contract schema; every other event is skipped unparsed. When the total `needsYou` across bots rises while the window is hidden, it shows one Electron `Notification` ("<bot>: N things need you", the bot's `needsYouSources` as body, the bot with the newest `needsYouAt`). A later rise while the window stays hidden closes it and shows a new one; showing the window closes it; clicking it reveals the window and loads `/bots/<id>` of the bot with the newest open item. The first slice of every stream is a baseline, never a rise. It is a main-process Electron notification, so the web page keeps getting no notification permission. The smoke replaces `Notification` with a recording stub and calls the click handler, so no OS banner or OS notification permission is involved.

Auto-update (`electron-updater`, the one npm dependency of the desktop package beyond Zod; it is bundled into `main.cjs`). A packaged app checks the update feed named by its own `app-update.yml` (this repository's GitHub Releases in a release build): the first check 30 s after start, then every 6 h, downloading in the background as soon as a newer release is found. The update installs when the app quits (electron-updater's quit handler, which the `quit` event of the app's own `app.exit(0)` reaches) or at once through the tray item "Restart to update to <version>", which appears only after a download. Both go through the one graceful quit: `before-quit` stops the sidecar and waits for it, and only then the installer runs (`installUpdateOrExit` in `main.ts`), so the host binary the update replaces is not running. If the install cannot start, the app logs it and relaunches itself instead of hanging. After the sidecar is ready the app reads its `/api/host-info` and logs whether the host's version equals `app.getVersion()` (`WARNING: the host reports version …` on a mismatch); this runs in a packaged app only. Pre-releases are offered only when the running version is itself a pre-release (`allowPrerelease`); electron-updater then follows the same pre-release channel (an `-rc.N` app moves to a newer `-rc.N` tag, never to the stable release; a stable install never sees a pre-release). Every build is on the metadata channel `latest` (`CHANNEL` in `scripts/desktop-kit.ts`): electron-builder would otherwise name a pre-release's metadata `rc-mac.yml`, which the release does not hold; electron-updater asks `rc-*.yml` first for a pre-release tag, gets a 404 and falls back to `latest-*.yml`. Failures (feed unreachable, bad metadata, a failed download, Squirrel.Mac refusing an unsigned app) are logged and never stop the app. The log is `logs/desktop.log` in the user-data folder (every line the desktop process logs, timestamped; the host's stays `logs/host.log`).

No update check runs when the app is not packaged, when `app-update.yml` is missing, when its feed is the local build's placeholder (a `.invalid` host; it is never contacted) or when `CLAUDEBOT_DESKTOP_UPDATES=off`. `createSmokeRun` (`scripts/desktop-smoke-kit.ts`) puts that off-switch in the environment of every smoke launch (a launch that wants updates passes `CLAUDEBOT_DESKTOP_UPDATES=on` as an extra). The logic is in `updates.ts` behind the small `UpdateEngine` interface (`createUpdater`: schedule, state, logging; fakes in `updates.test.ts`); `electron-update-engine.ts` is the electron-updater implementation, `desktop-log.ts` the log.

- `bun run package:desktop [--out <dir>] [--version <semver>] [--arch <arm64|x64>]… [--host-dir <dir>] [--sign] [--update-url <loopback http URL>]` builds the host for this machine, bundles the main process and runs electron-builder (`scripts/package-desktop.ts`; asar on, unsigned unless `--sign`, never published) for the current OS only. It writes into `dist/desktop/Claudebot-<os>-<archs>/` (`<archs>` joined by `-`, e.g. `Claudebot-darwin-arm64-x64`): the installers (macOS `.dmg` and `.zip`, the zip being what electron-updater applies on macOS; Windows NSIS `Claudebot-Setup-<version>.exe`; Linux AppImage and `.deb`), their `.blockmap`s, the update metadata electron-updater reads (`latest-mac.yml`, `latest.yml`, `latest-linux.yml`) and the unpacked app (`mac-arm64/Claudebot.app`, `mac/Claudebot.app` on x64, `win-unpacked/`, `linux-unpacked/`). The host binary is copied in as the extra resource `claudebot-host` (`Contents/Resources/claudebot-host` on macOS), and the browser as `browser-engine` beside it, for the arch being packaged (`scripts/browser-bundle.ts`: the pinned agent-browser engine and the pinned full Chrome for Testing, about 200 MB zipped, SHA-256-checked and cached in `dist/browser-cache/`); the host looks for `browser-engine/` next to its own binary before the data root's managed install. Platforms without a pinned engine and Chrome fail packaging. Only the current OS can be built: electron-builder is not asked to cross-build, and the Windows and Linux targets have not been run in this repo yet.
  Signing is off unless `--sign` is passed (or `CLAUDEBOT_REQUIRE_SIGNING=true`; see Releasing, Signing and notarization): without it the script sets `CSC_IDENTITY_AUTO_DISCOVERY=false` and `mac.identity: null` before the first electron-builder call and unsets every signing, notarization and GitHub token variable, so a build never reads the keychain, whatever the environment holds. `publish` is `never`. `--version` (default: the host's `VERSION`) is the app version, hence the installers' names and the metadata. `--arch` (repeatable, default this machine's) packages several CPUs in one run, which is how the macOS release gets one `latest-mac.yml` listing both zips (electron-builder writes one metadata file per OS and run; arm64 files carry `arm64` in their names, the x64 ones do not, which is how electron-updater tells them apart); the other CPU's app is only packaged, not launched. `--host-dir <dir>` bundles the prebuilt `claudebot-host-<os>-<arch>[.exe]` files in `<dir>` (as `build:host` and the release workflow's artifacts name them) instead of building any, restoring the executable bit an uploaded artifact loses. The update provider baked into `app-update.yml` is this repository's GitHub Releases when `GITHUB_REPOSITORY` (`owner/repo`, set by GitHub Actions) is set; a local build has no repository coordinates and uses the placeholder `https://updates.invalid/claudebot` (reserved `.invalid`, never resolves), but when `CI` is set and `GITHUB_REPOSITORY` is not, packaging fails before anything is built (`updateProvider` in `scripts/desktop-kit.ts`), so a release never ships the placeholder. The `.deb` needs the project homepage, which comes from `GITHUB_REPOSITORY` too, so build it in CI.
  `--out <dir>` (default `dist/desktop`) puts the output under `<dir>/Claudebot-<os>-<arch>` instead; only that folder and the stage folder are replaced, never the rest of `<dir>`. Before it builds or deletes anything the script refuses (non-zero) when a running process's command line lies under that folder, so packaging never pulls an app out from under a copy someone is using; to rebuild while a copy runs, package elsewhere with `--out` (`scripts/process-guard.ts`).
- To smoke the installed artifact rather than the unpacked app (macOS), mount the dmg, copy the app out and pass it to a smoke: `hdiutil attach -nobrowse -readonly -mountpoint "$T/mnt" <dmg>`, `ditto "$T/mnt/Claudebot.app" "$T/app/Claudebot.app"`, `hdiutil detach "$T/mnt"`, then `bun run smoke:desktop "$T/app/Claudebot.app"` (the same for `:profiles` and `:titlebar`), with `T` a temp dir you own. The smokes default to the unpacked app.
- Signing and notarization of the macOS and Windows app: see Releasing, Signing and notarization below. The bundle also holds the browser (`Resources/browser-engine/agent-browser` and `Resources/browser-engine/chrome/…/Google Chrome for Testing.app` on macOS, `agent-browser.exe` and Chrome's `.exe` and `.dll` files on Windows), so a signed app needs those signed with our certificate too. Chrome for Testing is not Google-signed on macOS (the pinned build is ad-hoc/linker-signed everywhere except `Libraries/WidevineCdm/…/libwidevinecdm.dylib`, which carries Google's Team ID), and on Windows every file in the pinned zip is unsigned except Microsoft's `D3DCompiler_47.dll`. electron-builder (`@electron/osx-sign` on macOS) signs every binary under the app, deepest first, except the host (`mac.signIgnore`); the signing checks (`signing.ts verify`, `scripts/mac-verify.ts`, `scripts/win-verify.ts`) then require, for the app and for the app inside each update zip: macOS, the engine, Chrome's `.app` (also `--deep --strict`), its framework, every `Helpers/*.app` and other `Helpers/` file and every `.dylib` under `Libraries/` (found on disk at verify time, nothing hard-coded) to be a Developer ID Application signature with the hardened runtime, a secure timestamp and the app's Team ID and leaf certificate, with Chrome and the helper apps holding the entitlements; Windows, `agent-browser.exe` and every `.exe` and `.dll` under `browser-engine\chrome` to be `Valid`, timestamped and signed by the app's certificate thumbprint. A missing engine, Chrome `.app`, framework, Helper app or (on Windows) `chrome.exe` or DLL fails the check. All of this is checked against fixtures only (`scripts/mac-verify.test.ts`, `scripts/win-verify.test.ts`, `scripts/signing-kit.test.ts`, `scripts/local-signing.test.ts`); nothing has been signed or verified on a real bundle. Still unobserved: that `bun run smoke:desktop` passes on a signed app (it is what proves the host, engine and Chrome launch under the hardened runtime; a binary that crashes at launch only after signing is missing an entitlement), that osx-sign signs every file the check lists (it signs what `isbinaryfile` says is binary, which is broader than Mach-O), what electron-builder does with the engine's and Chrome's `.exe`/`.dll` files on a real Windows run (it only warns when signing one fails, so `verify` is what fails the release), and that signtool replaces rather than appends to `D3DCompiler_47.dll`'s Microsoft signature. A rejected notarization lists the offending files in `xcrun notarytool log <id>`.
- Every smoke refuses to start when a process already runs from the app bundle it would drive (the packaged app of a copy someone is using), and its final leftover sweep kills only pids it saw appear during its own run, never a process that was already there (`createSmokeRun`, `sweep` in `scripts/desktop-smoke-kit.ts`).
- `bun run smoke:desktop:titlebar [app]` (macOS only, needs `package:desktop` first) drives the packaged `.app` on the same kind of fresh temp root and checks the hidden title bar: the real traffic lights' frames (Accessibility, by the app's pid only) lie inside the 56px header, centred, with nothing under them, with the sidebar expanded and collapsed; every interactive header control is `no-drag` and the header and the sidebar strip are `drag`; a real mouse drag (`scripts/desktop-mouse.swift`, CGEvent, compiled into the temp root) moves the window and a real click on the sidebar trigger toggles it; the native minimize, fullscreen and close buttons are pressed through Accessibility (close hides to the tray with the host alive); fullscreen has no strip gap; the host-stopped page has a drag strip clear of the lights; the Connections window keeps its standard title bar; and the same web UI in plain Chromium has no inset and no drag region. It needs the Accessibility permission for the terminal that runs it (`desktop-mouse trusted prompt` shows the prompt once); without it the steps that need it fall back to Electron calls and say so. Screenshots (`screencapture -l<window id>`, that one window) and the log go to `.scratch/titlebar/`.
- `bun run smoke:desktop [app]` (macOS only) drives the packaged `.app` with `playwright-core`'s `_electron.launch` on a fresh temp root that holds the data root, the Electron user-data folder and the file-secrets key, and passes `--use-mock-keychain`, so nothing reaches the keychain or a default folder. It checks, over four launches: a first launch that installs the managed Claude CLI (needs network); the signed-in UI; the renderer's isolation; the navigation and `window.open` policy; the UI's OAuth connect reaching `shell.openExternal` against a loopback fixture provider (the call is a recording stub, plus, with `SMOKE_SYSTEM_BROWSER=1`, one real call to a loopback fixture that opens a tab in the default browser); `kill -9` of the app stopping the host, its Claude CLI child, the browser engine and Chrome; closing the window leaving the host running while a routine (a `once` schedule) fires; the tray's tooltip and menu, "Open Claudebot", killing the host alone and "Restart host"; the needs-you banner (events posted with a bot's event token while the window is hidden: one banner, replaced by a later rise, none while the window is visible, closed by showing the window, and its click revealing the window on the bot with the newest item), recorded through a stub of `desktop.banner.notifier.show` so no OS banner or OS notification permission is involved; Start at login on after the first launch, off after the tray checkbox and still off after a relaunch with `--hidden`; the tray's Quit and a graceful `app.quit()`; and `ps` showing nothing left after each end. It installs the managed browser engine into the temp root with `install-browser` (network) and drives a real engine and Chrome as a fixture bot over MCP with the bot's own bearer, without a model turn. Every launch gets `HOME` set to a short temp directory (the engine keeps Chrome, sockets and session state under `$HOME/.agent-browser`) and `CLAUDEBOT_DESKTOP_LOGIN_ITEM_FILE`, so no login item is registered. The tray is read from the main process (`process.mainModule.exports.desktop`) and its menu items are invoked by calling their `click` handlers; the menu bar itself is not clicked. It runs a fake Claude CLI after the first launch and never touches the real sign-in.
- `bun run smoke:desktop:profiles [app]` (macOS only, needs `package:desktop` first) drives the packaged `.app` the same way (shared helpers in `scripts/desktop-smoke-kit.ts`, including the temp `HOME` and the login-item file seam) against fixtures, not a real server: a second compiled host on loopback as the "remote", a host-info fixture for the API mismatch, a self-signed `https` fixture for the certificate error. It checks Add through the Connections window, the tray's connection items, the local host stopping and restarting with local and with a remote shown, the encrypted token in `profiles.json`, Connect, the navigation and OAuth policy on the new origin, Forget with revoke, the refused URLs, and startup on a saved active profile with and without its host.
- `bun run smoke:desktop:update <old.app> <feed-folder>` (macOS only) drives a packaged app against a feed served from this machine. Build both with `package:desktop --update-url http://127.0.0.1:<port>` (one port for both; `--update-url` bakes that loopback `http` feed into `app-update.yml` instead of GitHub Releases, is refused in CI and for anything but loopback `http`, and gives the build its own bundle id `dev.claudebot.desktop.updatefixture` instead of the production `dev.claudebot.desktop`): the old app at e.g. `--version 0.1.0-rc.1`, a newer run at `--version 0.1.0-rc.2` whose folder (it holds `latest-mac.yml` and the zip) is the feed; run packaging without `CI` set. It checks that with the off-switch the feed sees no request in 40 s, and that without it the app checks, finds the newer version, downloads the zip, logs the outcome, compares the host's version with its own and keeps running with its host. An unsigned app is refused by Squirrel.Mac after the download (logged as `update failed: Code signature … did not pass validation`), so the install itself is not exercised on macOS until signing exists. Squirrel keeps `~/Library/Caches/<bundle id>.ShipIt` under the real home, not the temp `HOME`: the smoke refuses an app whose bundle id is not the fixture id, records whether `~/Library/Caches/dev.claudebot.desktop.updatefixture.ShipIt` existed before, removes exactly that path afterwards and only when it created it, and fails if any `dev.claudebot.desktop*` cache entry (the user's installed app's) appeared or vanished; it never touches the production id's paths.

Connection profiles (`profiles.json` in the user-data folder; `connections.ts`, `profile-store.ts`): the built-in profile `local` is the sidecar and is never stored. A remote profile holds a name, an origin, the device id and the device token encrypted with `safeStorage`; it is refused when encryption is unavailable or, on Linux, the backend is `basic_text`, never stored in plaintext. A profile URL is a bare origin, `https:` except `http:` for loopback hosts, so a plain-HTTP private network (Tailscale with `--allow-plain-http`) is refused. Every request to a host goes through the default session's `net.fetch`, so Chromium's certificate checks apply and nothing bypasses TLS; mutating requests send the profile's `Origin` (ADR 0005) and no cookies. Add and every connect first read `/api/host-info` and compare `apiVersion` with `SUPPORTED_API` in `host-api.ts`. The Connections window is served from the privileged scheme `claudebot-desktop:` in an in-memory session partition (`connections-page.ts`, `connections-window.ts`), with no preload and its navigation pinned to that scheme; its forms post to the scheme and get a 303 carrying only a message id. The local profile is the supervisor's current sidecar, read at every use: when the host restarts, `localChanged()` signs in again with the new token and reloads if `local` is shown, and while the host is starting or stopped `local` shows DESK-03's starting and "host is not running" pages (a remote profile keeps working then). The tray and the application menu's Connections submenu share `connectionItems` (`connection-items.ts`); `setupConnections` (`desktop-connections.ts`) gives `main.ts` `list()`, `connect(id)`, `openConnections()`, `start()`, `localChanged()` and `onChange()`.

## Releasing

A release is a `v*` tag. Pushing one runs `.github/workflows/release.yml`: `verify` (the tag is `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-prerelease` and equals `v` + the host's `VERSION`), then `host` (a matrix that builds each of the five host binaries with `build:host <target>` on a native runner, runs `smoke:host` on it and uploads it as the artifact `release-host-<target>`; every target has a native runner, but `ubuntu-24.04-arm` is free for public repositories only), then `desktop` (a matrix on native runners, macOS, Windows and Linux: downloads the `release-host-*` artifacts for its OS, runs `package:desktop --host-dir hosts` with the version from `VERSION` and `GITHUB_REPOSITORY`, then `bun scripts/release.ts desktop` checks that the host inside every app, and inside the macOS update zip, is byte-identical to the host job's binary, that the update metadata names the release version and that every installer exists, copies exactly the installers, blockmaps and metadata out and uploads them as `release-desktop-<os>`; the macOS job packages arm64 and x64 together so there is a single `latest-mac.yml` and nothing for the artifact merge to collide on), then `publish` (the only job with `contents: write`: it merges every `release-*` artifact into one folder, writes `SHA256SUMS` over all of it with `scripts/release.ts checksums`, which fails unless all five host binaries and every supported installer and update metadata file are there, and creates the GitHub Release with `gh`, as a draft until every asset is uploaded; a tag with a pre-release suffix such as `-rc.1` makes a pre-release). A rerun of a failed publish replaces the assets of the Release that exists. Desktop installers join the same Release: a job that uploads artifacts named `release-*` and is added to `publish.needs` ends up in the Release and in `SHA256SUMS`.

The host's version is `VERSION` in `packages/host/src/harness/claude-access.ts` (no `package.json` carries a version). To cut a release:

1. Set `VERSION` to the version without the `v` (`0.2.0`, or `0.2.0-rc.1` for a pre-release; a pre-release suffix is part of `VERSION`), run `bun run check`, commit and merge to the default branch.
2. Tag that commit and push the tag: `git tag v0.2.0 && git push origin v0.2.0`.
3. Watch the `Release` run. A tag that does not match `VERSION` fails `verify` before anything is built; fix `VERSION` (or delete the tag), then tag again.
4. Check the Release: five `claudebot-host-<os>-<arch>[.exe]` files, `install.sh` (its `DEFAULT_REPO` filled in with the repository), `claudebot.service` and `SHA256SUMS`; `sha256sum --check SHA256SUMS` in the download folder passes. `deploy/install.sh` installs a release's Linux binary without `--url` (`--repo`, `--version`; see `deploy/README.md`).

Check a published Release offline with `bun scripts/release.ts verify-release <folder> <version>` (`scripts/release-verify.ts`, tests in `scripts/release-verify.test.ts`), on the folder `gh release download v0.2.0-rc.1 -R OWNER/REPO -D <dir>` filled (version without the `v`, e.g. `0.2.0-rc.1`). It reads only; it exits 1 and lists every problem, or exits 0 and prints "a complete, consistent release". It checks that the folder holds exactly the published files and nothing else (the five host binaries, every `SUPPORTED_DESKTOP` installer, its `.blockmap` (the `.deb` has none), `latest-mac.yml`, `latest.yml`, `latest-linux.yml`, `install.sh`, `claudebot.service`, `SHA256SUMS`); that `SHA256SUMS` lists exactly those files, once each, and every sha256 matches; that `install.sh` has `DEFAULT_REPO="OWNER/REPO"` filled in; and that each `latest*.yml` names the version, lists the file the updater applies (the mac zips, the NSIS exe, the AppImage) and that every file it lists exists with the sha512 and size it states. It does not check signatures, that the host inside an installer is the release's (the workflow's `release.ts desktop` did), or that anything runs.

Run the two release steps locally with `bun scripts/release.ts tag v0.2.0` (prints `version=` and `prerelease=`; exits non-zero on a mismatch) `bun scripts/release.ts desktop <bundleDir> <hostDir> <outDir> <version> <arch>…` (the check and collection of one `package:desktop` run for this OS) and `bun scripts/release.ts checksums <folder> <version>` (the folder must hold the five binaries and every supported installer and metadata file); `scripts/release-kit.test.ts` and `scripts/desktop-kit.test.ts` cover the tag rules, the checksum format and the desktop host check.

Installers are released for macOS (arm64 and x64: dmg and zip), Windows x64 (NSIS) and Linux x64 (AppImage and deb); `SUPPORTED_DESKTOP` in `scripts/desktop-kit.ts` is the list and `publish` fails when any of its files is missing. linux-arm64 and Windows arm64 are host-only. Whether the macOS and Windows installers are signed depends on the signing secrets (next section); without them they are unsigned and unnotarized, macOS Gatekeeper and Windows SmartScreen warn on first launch, and macOS auto-update of an unsigned app is not expected to work. Linux packages are never signed. The Windows and Linux installers are built only by the workflow and have not been run anywhere yet. On Windows `smoke:host` terminates the host instead of sending SIGTERM and skips the graceful-exit and lock checks.

### Signing and notarization

Signing needs credentials only a person can create, so the release signs when the repository has them and stays unsigned when it has not. Nothing about it can be exercised locally (no workflow or script here ever signs on a developer machine: `bun scripts/signing.ts sign-host` refuses to run outside GitHub Actions, and `package:desktop` signs only with `--sign`, below).

The one local exception is an explicit opt-in route for a personal test build: `bun scripts/sign-local.ts plan|run|cleanup` (`bun run sign:local`; guide `docs/release/local-signing.md`) signs and notarizes an arm64 DMG, update zip and host on this Mac from a `.p12` and an App Store Connect key named in `CLAUDEBOT_LOCAL_*` environment variables, in a temporary keychain inside `--out`. `plan` prints every operation and runs nothing; `run` refuses in CI and without `--confirm-keychain-and-notary-upload`. It reaches `package-desktop.ts` through `--sign --local-keychain <file> --local-identity <sha1>`, which is mutually exclusive with the CI path (`CSC_LINK`); the CI workflow, `signing.ts` and its checks behave as described below (the macOS checks now live in `scripts/mac-verify.ts`, shared by both). It has been tested against fakes only; nothing in it has run against a real keychain or Apple's notary service.

The local route has two notary backends, exactly one per run: an API key (`CLAUDEBOT_LOCAL_API_KEY_*`, `notarytool`) or a saved profile of the Rork ASC CLI (`CLAUDEBOT_LOCAL_ASC_PROFILE`, optionally `CLAUDEBOT_LOCAL_ASC_BIN`; `scripts/asc-notary.ts`). With `asc` the packaging run is given `--local-notary asc --local-asc-profile <name> --local-asc-bin <path> --local-notary-record <file>`, electron-builder's own notarization is off (`notarize: false`) and an `afterSign` hook zips the signed app, runs `asc --profile <name> notarization submit --file <zip> --wait --output json`, staples with `xcrun stapler` and writes the submission to the record file; the route submits the DMG the same way. Both backends write `<out>/artifacts/NOTARIZATION.json` (submission ids, statuses, sha256). The CI route is unchanged. The asc output shape and exit codes are unobserved.

What the workflow does when a platform's secrets are all set (`scripts/signing.ts`, the decisions and checks in `scripts/signing-kit.ts`, covered by `scripts/signing-kit.test.ts` with fixtures and no certificates):

1. `verify` runs `signing.ts plan` with only whether each secret is set (never a value) and outputs `sign_mac` and `sign_windows`; the job summary lists each platform as signed or UNSIGNED.
2. `host` (macOS and Windows legs) runs `signing.ts sign-host` on the binary it just built, before `smoke:host`, so the smoke run starts the signed binary under the hardened runtime and the Release publishes it. macOS: a temporary keychain holds the certificate, `codesign --options runtime --timestamp --entitlements scripts/entitlements.mac.plist` signs with the Developer ID Application identity (it fails unless the certificate holds exactly one), and the keychain is deleted. Windows: `Set-AuthenticodeSignature` (SHA-256, timestamped by `http://timestamp.digicert.com`), chosen over `signtool` because it ships on every Windows image and needs no Windows SDK path.
3. `desktop` runs `package:desktop --sign`. electron-builder imports the same certificate into a keychain of its own (`CSC_LINK`), signs the app and its helpers with the hardened runtime and `scripts/entitlements.mac.plist`, notarizes with `notarytool` (App Store Connect API key) and staples the ticket, then builds the dmg and the update zip from the stapled app. It leaves the bundled host alone (`mac.signIgnore`, and `!claudebot-host.exe` in `SIGNED_WIN.signExts` on Windows) because the host arrives already signed with the same certificate, and a second signature would break the byte-identity `release.ts desktop` checks. On Windows it signs the app, the uninstaller and the NSIS installer with the same PFX (`WIN_CSC_LINK`), and `SIGNED_WIN.signExts` in `signing-kit.ts` is `[".dll", "!claudebot-host.exe"]`: electron-builder signs `.exe` by default and a positive `.dll` adds the libraries, which includes Chrome's; never add a positive `.exe` pattern, a positive match beats the `!` and the host would be re-signed. The same `.dll` also signs Electron's own top-level DLLs and anything in `app.asar.unpacked`, and cannot spare `D3DCompiler_47.dll`, which ends up with our signature in place of Microsoft's.
4. `Verify signing` (only when signed) runs `signing.ts verify` on the runner: macOS, for every arch's unpacked app and for the app inside its update zip: `codesign --verify --deep --strict`, `spctl --assess --type execute`, `xcrun stapler validate`, and the app's and the host's `codesign -dvv` must both be a Developer ID Application signature with the hardened runtime and a secure timestamp, the same leaf certificate and the same Team ID, with the host holding the entitlements, plus the browser parts listed under Desktop app above; Windows: `Get-AuthenticodeSignature` on the installer, the app exe, the host exe, `agent-browser.exe` and every `.exe` and `.dll` under `browser-engine\chrome` must all be `Valid`, timestamped and carry one certificate thumbprint. `release.ts desktop` then still checks that the host in every app is byte-identical to the one the host job uploaded.

`scripts/entitlements.mac.plist` grants `com.apple.security.cs.allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation` and nothing else; it is the one file for the Electron app, its helpers, Chrome and the Bun-compiled host (V8 and JavaScriptCore both JIT). `disable-library-validation` is there for Chrome: the pinned zip carries a Google-signed `libwidevinecdm.dylib` (and Chrome's component updater may fetch newer Google-signed CDMs), which a Chrome re-signed under our Team ID cannot load with library validation on; Chromium's own plugin-helper entitlements grant the same pair (`@electron/osx-sign`'s `default.darwin.plugin.plist`). electron-builder gives the one `entitlements` file to the main app and `entitlementsInherit` to everything else, so the host and Electron's helpers get it too, though the host does not need it. `MAC_ENTITLEMENT_KEYS` in `signing-kit.ts` is the list `signing.ts verify` requires on the host, Chrome and every helper app, so the plist and the check move together. If a signed binary needs more, the host job's smoke run (which runs the signed host) or the macOS smoke fails; add the entitlement there and to `MAC_ENTITLEMENT_KEYS`.

Secrets (repository secrets; each platform's set is all-or-nothing, and a partly set platform always fails the release):

| Secret                         | Content                                                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `MACOS_CERTIFICATE_P12`        | base64 of the Developer ID Application certificate with its private key, as a `.p12` holding exactly one identity |
| `MACOS_CERTIFICATE_PASSWORD`   | the `.p12`'s password                                                                                             |
| `APPLE_API_KEY_P8`             | the text of the App Store Connect API key (`AuthKey_<id>.p8`) used by `notarytool`                                |
| `APPLE_API_KEY_ID`             | that key's Key ID                                                                                                 |
| `APPLE_API_ISSUER`             | the issuer ID shown above the team keys list                                                                      |
| `WINDOWS_CERTIFICATE_PFX`      | base64 of the code signing certificate with its private key, as a `.pfx`                                          |
| `WINDOWS_CERTIFICATE_PASSWORD` | the `.pfx`'s password                                                                                             |

Secrets reach only the steps that need them, as environment variables of that step (`verify` gets only "set" or empty; the macOS and Windows host steps and the `Package` step get their own OS's), and no script prints a value or puts one on a command line it logs (`security import -P` does take the `.p12` password as an argument on the runner).

Fail closed: set the repository **variable** (not a secret) `CLAUDEBOT_REQUIRE_SIGNING` to `true` (`gh variable set CLAUDEBOT_REQUIRE_SIGNING --body true`). Then a release whose macOS or Windows secrets are missing fails in `verify`, before anything is built, and `package:desktop` itself refuses to run unsigned for macOS and Windows. Without the variable, a platform with no secrets is built unsigned as before and the job summary says UNSIGNED. A platform with some but not all secrets fails either way.

`bun run package:desktop --sign` is the same code path the workflow takes, for a person who really has the credentials in the environment (the secret names above, as environment variables); without `--sign` the credentials in the environment are ignored and removed. It exits non-zero before building when any secret of this OS is missing, and Linux ignores it.

What a person has to do once (this is the part of ticket 06 no script can do):

1. macOS, with a paid Apple Developer Program membership: create a **Developer ID Application** certificate (developer.apple.com, Certificates; only the Account Holder can; or Xcode, Settings, Accounts, Manage Certificates). In Keychain Access export the certificate together with its private key as a `.p12` with a strong password. Create an App Store Connect **team API key** (Users and Access, Integrations, Team Keys) with at least the Developer role, download the `.p8` (Apple shows it once), and note the Key ID and the Issuer ID.
2. Windows: obtain a code signing certificate (OV or EV) from a certificate authority and export it with its private key as a `.pfx`. Caveat: since June 2023 the CA/Browser Forum requires the private keys of newly issued code signing certificates to live on a hardware token or an HSM, so a new certificate usually cannot be exported to a `.pfx`; if yours cannot, this PFX path does not apply and `signHostWindows` in `scripts/signing.ts` and `SIGNED_WIN` in `scripts/package-desktop.ts` must change to your CA's cloud signing or Azure Trusted Signing before the Windows secrets mean anything. Decide that before buying the certificate.
3. Store them as repository secrets under the names above, for example `base64 -i certificate.p12 | gh secret set MACOS_CERTIFICATE_P12`, `gh secret set MACOS_CERTIFICATE_PASSWORD`, `gh secret set APPLE_API_KEY_P8 < AuthKey_XXXXXXXXXX.p8`, `gh secret set APPLE_API_KEY_ID`, `gh secret set APPLE_API_ISSUER`, `base64 -i certificate.pfx | gh secret set WINDOWS_CERTIFICATE_PFX`, `gh secret set WINDOWS_CERTIFICATE_PASSWORD`. Then delete the exported files.
4. Cut a pre-release (`v0.2.0-rc.1`, see above) and read the `verify` job summary: it must say macOS and Windows are signed. Once a signed release has passed, set `CLAUDEBOT_REQUIRE_SIGNING` to `true`.
5. Check the result the way a user meets it. macOS: download the `.dmg` in a browser on a Mac that has never seen the app (that sets the quarantine flag), open it and launch the app: no "cannot verify the developer" dialog. In a terminal, on the installed app: `spctl --assess --type execute --verbose=4 /Applications/Claudebot.app` prints `accepted` and `source=Notarized Developer ID`, `xcrun stapler validate /Applications/Claudebot.app` prints `The validate action worked!`, and `codesign -dvv /Applications/Claudebot.app` and `codesign -dvv /Applications/Claudebot.app/Contents/Resources/claudebot-host` show the same `TeamIdentifier`. Windows: download `Claudebot-Setup-<version>.exe` in Edge on a machine that has never seen it and run it: no "Windows protected your PC" block (an OV certificate may still warn until the file has reputation; that is not a signing failure), and `Get-AuthenticodeSignature .\Claudebot-Setup-<version>.exe | Format-List` shows `Status : Valid` and the publisher; Properties, Digital Signatures on the installed `Claudebot.exe` and `resources\claudebot-host.exe` shows the same signer.
6. Whether the keychain items a bot created survive an update (the host's signature is what macOS ties them to) is the update check of ticket 07.

## Deploy kit

`deploy/` holds the kit that installs the host on a systemd Linux server (`install.sh`, `claudebot.service`, `Caddyfile`). `deploy/README.md` is the self-hoster's guide; keep it in step with the unit, the installer and `platform/config.ts`. The kit has no permanent tests. Check it with `systemd-analyze verify deploy/claudebot.service` (Linux only), `shellcheck deploy/install.sh` and `caddy validate --config deploy/Caddyfile --adapter caddyfile`. The real-server run is ticket 04 of spec 5.
