## Checks

`bun run check` is the full gate; run it before calling work done. It runs, in order and stopping at the first failure: `fmt:check` (oxfmt), `lint` (oxlint, type-aware), `knip` (dead files, exports and dependencies), `typecheck` (`tsc` per package, then `scripts/` through `scripts/tsconfig.json`, which has DOM types for the smokes' in-page callbacks), `depcheck` (dependency-cruiser, ADR 0003 layering) and `test` (`bun test`). Each is also a script of its own. `bun run fmt` rewrites formatting in place.

`bun test` always runs with coverage (`bunfig.toml`: `coverage = true`, test files excluded, `text` and `lcov` reporters; `coverage/` is gitignored). Two gates apply, and `bun run test` (so `check` and CI) runs both:

- Per file: `coverageThreshold` makes `bun test` exit non-zero when any covered file's line or function coverage is below it. Bun applies it per file, not to the "All files" total, and only reads the plural keys `lines`/`functions` (singular keys are silently ignored; an omitted key defaults to 0.9). It is a floor: the lowest per-file value measured, rounded down to a whole percent.
- Total: `scripts/check-coverage.ts` sums `coverage/lcov.info` and fails when total line or function coverage is below its `BASELINE` constants, the measured totals rounded down to a whole percent. Bun only reports files that tests load, so a new module no test imports does not lower the total.

Raise both as tests land, never lower them; if coverage genuinely drops, add tests instead.

### Git hooks

Git hooks come from lefthook (`lefthook.yml`) and are installed by `bun install` via the `prepare` script; it skips quietly outside a git checkout.

- pre-commit (staged files, parallel): `oxfmt --check`, `oxlint`, `gitleaks git --staged`. A format failure means run `bun run fmt` and re-stage.
- commit-msg: `commitlint` checks the message against Conventional Commits (`commitlint.config.js`).
- pre-push: `bun run check`.
- Prerequisite: [`gitleaks`](https://github.com/gitleaks/gitleaks) is a Go binary, not an npm dependency. Install it yourself (`brew install gitleaks` on macOS); pre-commit fails with an install hint when it is missing.

### CI

`.github/workflows/ci.yml` runs on every pull request and on pushes to `main`/`master`. Jobs: `check` (`bun install --frozen-lockfile`, then `bun run check`), `pr-title` (pull requests only; commitlint on the PR title, since squash merges use it as the commit message), `sherif` (`bunx sherif`, monorepo dependency consistency), `secrets` (gitleaks over the full history, config in `.gitleaks.toml`) and `audit` (`bun audit`, non-blocking until it exits 0; then drop `continue-on-error` in the workflow). The Bun version comes from `.bun-version`.

No server-side branch protection: the repo is private on GitHub's free plan, which does not offer protected branches or rulesets there, so CI reports but cannot block a merge or a push. The gates that block are local, in `lefthook.yml`: pre-commit (oxfmt, oxlint, gitleaks on staged files), commit-msg (commitlint) and pre-push (`bun run check`). Never skip them (`--no-verify`); a red CI run on `master` is fixed forward at once. Dependency updates are manual (`bun outdated`, then a normal commit through the same gates); there is no Renovate or Dependabot.

### Browser smokes

`bun run smoke:ui` runs `smoke:answer-ui`, `smoke:needs-you-ui`, `smoke:blocked-ui`, `smoke:answers`, `smoke:loop-ui`, `smoke:scroll-ui`, `smoke:channels-ui` and `smoke:files-ui` in order against headless Chrome, a temporary web build, the whole-host test harness and the fake Claude CLI (`scripts/smoke-kit.ts`), and stops at the first failure with that smoke's exit status. `smoke:answers` runs the real `tomte-notify`, answers through the UI and asserts the arguments a fake `herdr` recorded (ADR-0008). `smoke:loop-ui` drives the double-loop chat mode with the fake CLI's `loop.json` (below). `smoke:scroll-ui` checks that the transcript (`packages/web/features/chat/scroller.tsx`) follows streamed replies and stops following only when the reader scrolls up. `smoke:channels-ui` drives the Channels page against a fake Telegram Bot API (`packages/host/src/testing/fake-telegram.ts`): token, link code, linking, Unlink. `smoke:files-ui` picks files and folders in the Files section and the composer against a host with a 1 MiB per-file cap: renamed clashes, the tree kept, an over-cap refusal and attachments delivered to the bot. They are outside `bun run check` because they need Chrome; run them when the answer path, the relay, the sender, the double-loop chat mode, the transcript's scrolling, the Channels page or file uploads change. A failed smoke keeps its run directory (screenshots, host log, page console, recorded arguments) and prints its path. Prerequisites, flows and limits: `docs/smoke.md`.

## Double-loop chat mode

A per-bot second chat mode (`Bot.chatMode: "standard" | "double_loop"`, default `standard`; ADR-0011, spec `docs/plans/double-loop-chat.md`). One long-lived, fast **front** session (Haiku, thinking off, whatever the bot's model) answers every message and never blocks the composer; heavy work runs in background agents (`researcher`, `worker`) the front starts, steers (`SendMessage`), queues and stops (`TaskStop`). Each agent's result is posted as the bot's own message (a report). The chat shows only messages: the front's replies arrive whole (no streaming, a "typing…" line meanwhile), and neither its tool calls nor task rows are in the transcript; the Tasks section of the bot panel follows the tasks. Switching mode starts a new session and is refused with 409 while tasks are queued or running.

The bot's `model` and `effort` (`Bot.model`, `Bot.effort`, saved in `bot.json`, set through `/api/model` and `/api/effort`) are what a standard bot's turns run on and what a double-loop bot's background tasks run on: the observer's PreToolUse hook writes them into every Agent call that names none, so a change reaches the next task without reopening the front.

- Host: `packages/host/src/loop/` (public surface `index.ts`): `front.ts` (`FrontSession`), `agents.ts` (agent definitions, `ProgressAttribution`, the in-process `loop` MCP server), `observe.ts` (SDK messages and hooks to store rows and `ServerEvent`s, including `rate_limit`), `tasks.ts` (registry and queue), `work-state.ts`, `store.ts` (`loop_tasks`, `loop_events`), `guard.ts` (worker path guard). Mode dispatch is in `host-server/chats.ts` (`send`, `deliver`, `reconfigure`, `replayOpen`, presence); the toggle route is `/api/bots/chat-mode`. Reports live only in `loop_events`: replay merges them with the CLI session file and strips the `<work_state>` block the app appends to every message the front receives.
- Web: the model chip in the message box (`features/chat/model-chip.tsx`, in the composer before the attach button; its popover holds the chat mode as two radio cards, the model and the effort for both modes) is where a bot's mode and model are changed; the rate limits sit beside the context meter (`features/chat/rate-limit-meter.tsx`), the Tasks section of the bot panel is `features/tasks` (a slot of `BotPanel`, composed in `app/routes/bot.lazy.tsx`; a standard bot's Tasks section says background tasks need double-loop chat). The reducer state is `chat.presence`, `chat.rateLimits` and the `task`, `task_status` and `report` items in `host/transcript.ts`; the double-loop transcript leaves the `task` items out.
- Rate limits: the front's `rate_limit_event` (status, utilization, reset) is forwarded as an ephemeral `rate_limit` event, kept per window for the account and sent again to a page that connects; only a double-loop bot's page shows it.
- Usage: the front's `result` messages go through the host's one `UsageMeter` (`ThreadEnv.meter`, passed by `openFront` to `FrontSession` and called in its `observe`), like every `Thread` turn, so the front session's `session_usage_marks` row follows its running totals, failed turns included. Nothing reads the front's own turn usage yet (it is a chat, not a run). A double-loop routine run never shares the front's session (its `ownSession` is a fresh id), so the run is charged its own difference and the front's mark is untouched by it. Test: `host-server/double-loop-usage.test.ts`.
- Routines: a double-loop bot's routine runs are always headless, whether its chat is open or not (ADR-0011 "Routine runs"): `routine-turns.ts` starts a job with `ownSession` through `runHeadless` and the parking delegate, so the run parks, resumes and expires exactly like a standard bot's headless run (`waiting`, ADR-0009, `routines/parking.ts`). The run has a session of its own (`routine_runs.session_id` is a fresh id, kept for every resume); the front never receives the routine prompt, a resume message or an expiry notice, and the run reports through its output and the Routines panel, not the front chat (no `routine` line, no last-message preview). It does not block the front or the composer: `RoutineTurns.headless` (what blocks a chat) is for runs in the bot's current session only, `headlessRun`/`Chats.runOf` also see own-session runs (run id and session id) so the run's waits, browser ones included, carry its id and its own session id, and the front's own waits are opened with `runId: null` so they never join a run.
- Fake CLI: `packages/host/src/testing/fake-claude.ts` reads an optional `loop.json` (`host.loopScript(...)` in tests) that scripts what it emits per user message: SDK messages, `stream_event` text, hook callbacks, in-process MCP calls, `can_use_tool` requests, waits on files (`host.allow(name)`) and crashes. The header of the file lists every step. A script's `match` is a substring of the whole message, work state included, so give scripts distinctive matches.
- Smoke: `bun run smoke:loop-ui` (`scripts/smoke-loop-ui.ts`, part of `smoke:ui`; `docs/smoke.md`).
- Routing eval (manual, real model): `bun run eval:loop-routing` runs 31 labelled cases, each a fresh front session over a seeded work state, with every tool call refused so no agent starts: about 31 front sessions and 52 requests on the front's small model, on the user's own Claude sign-in. It exits non-zero below 90%. Ask before running it. `--dry-run` prints the cases, work states and cost and starts nothing; `--cli <path> [--loop-json <file>]` uses another CLI, such as the fake one. Usage and cost are in the header of `scripts/eval-loop-routing.ts`. Record a run in the ADR's "Evaluation" note, and rerun it with a manual restart test when the managed CLI version in `harness/cli.ts` is bumped.
- Manual scenarios with the real CLI (not automated; record timings in the ADR): the v3 drive (start two tasks, ask for status, steer one, "after that" for a queued task, cancel one) and a host restart with two agents running, after which both resume under their ids and report.

## Bot panel

The right-hand side of a bot's page: an activity rail on the desk and, beside the chat sheet, one section at a time (ADR-0004 "URL search params", ADR-0011). The sections, their titles, the rail's three groups (Work, Tasks, Browser; Files, Memory, Routines; Permissions, Events endpoint pinned to the bottom) and the upgrade of old links live in `packages/web/lib/bot-panel.ts` (`PANEL_SECTIONS`, `RAIL_GROUPS`, `PANEL_TITLES`, `upgradePanel`), because the router, the chat and the bots feature all need them and features may not import one another. The order never changes.

- URL: `/bots/<id>?panel=<section>`. Host links use it (`work`, `browser`, `routines`); `app/router.tsx` still folds a link made when the panel had tabs (`panel=settings&section=routines`, as already-sent phone messages carry) into `panel=<section>` (`settings` alone and the old `chat` page open `profile`). A closed panel is not in the URL: open or closed is `localStorage` (`tomte:panel`) for a wide window and per page for the sheet of a narrow one; a link that names a section opens the panel on it.
- State: `features/chat/use-panel.ts` (`usePanel`, `PanelControls`: `pick` toggles, `show` always opens, `close`, `toggle`) is owned by `ChatView`, which lays out the chat sheet, the panel sheet (`PANEL_ENTER`: fade plus a 2-unit slide from the right, 200 ms, `motion-safe`) and the rail on a wide window, and a Sheet over the chat below 1024px. A takeover request and the transcript's "show browser" and "show tasks" call `show`.
- Rail: `features/bots/activity-rail.tsx` (`ActivityRail`, vertical on the desk, horizontal as the sheet's switcher; `app/bot-rail.tsx` wires it to the panel and the chat's tasks). Marks: Work's needs-you count (`data-needs-you`), a live dot on Tasks while one runs and on Browser while it is on. Each icon's tooltip is a one-line live summary (`rail-hints.tsx`, each hint a component mounted only while its tooltip is open). Clicking the open section's icon closes the panel; Profile has no icon, the bot's avatar, name and purpose in the chat's top bar are its button (`data-testid="profile-button"`).
- Panel: `features/bots/bot-panel.tsx` (`BotPanel`: title row, close button, scrolling body marked `data-panel-section`). Work, Tasks, Browser, Memory, Routines and Events endpoint arrive as slots (`PanelSlots`); Files (`files-section.tsx`: folder path with copy, client-side search), Permissions and Profile (`profile-section.tsx`: the form, and Delete bot at the bottom) are the bots feature's own. Work's "Connect one" opens Events endpoint.
- Smokes find the rail by `getByRole("navigation", { name: /panel$/ })` and a section by `[data-panel-section]`.
- Files downloads: `GET /api/files/download?path=` (`host-server/api/files.ts`) streams a file as before; when the path names a folder inside the bot's files folder (the empty path is the whole folder, without the browser's scratch folder) it streams the folder as a zip instead, named `<folder>.zip` (the bot's name for the whole folder). `bots/files.ts` `archive(dir, rel, root, skip)` lists the folder (sorted, symlinks and `.DS_Store` left out, empty folders kept) and opens each file only when the archive reaches it through `openFileInside`; `platform/zip.ts` `zip(entries)` is the writer: store-only, no dependency, always ZIP64 (every size and offset 64-bit, sizes and CRC-32 in a data descriptor after each file, so nothing is read twice or held in memory and a file that changes size mid-stream still yields a valid archive). The Files section offers "Download as zip" in the folder bar and, in a file's menu, "Folder as zip" for the folder it sits in. A download is a copy: nothing syncs. Test: `host-server/files.test.ts` ("downloading a folder as a zip", read back with the system `unzip`; its 4 GiB member is written to disk as a sparse file).

## File uploads

The one way a file reaches a bot's files folder from a client, in the Files section and in the composer alike (spec `.scratch/client-host-split/spec.md`, phase 6; ADR-0005 "Amended" note). `POST /api/files/upload?path=<relative path>[&folder=<leading folders of path>]` takes the raw bytes as `application/octet-stream` (`host-server/api/upload.ts`; the boundary lets this one mutating `/api/*` route carry bytes instead of JSON, Host, Origin and device token still apply, `UPLOAD_PATH` in `boundary.ts`) and streams them into the open bot's files folder (`bots/upload.ts`, `writeUpload`: a pipeline into a file opened `wx`, never buffered). It answers `UploadResponse` (`{ path, renamedFrom? }`); there is no JSON upload and no base64 attach route.

- Paths: relative, `/`-separated, no empty, `.` or `..` segment, no backslash or NUL; anything else is 400 and writes nothing. Folders on the way are created one at a time and a symlink or a file in place of one is refused (400), so nothing is written through a link a bot made; the file itself is created exclusively, never over a symlink.
- Clashes: a taken name becomes `name 2`, `name 3`… before the extension, and `renamedFrom` is the requested path. With `folder`, a taken leading folder is renamed the same way instead of merged (the composer uses it so an attached folder is always a fresh one); the answer's path names the new folder and the caller sends the folder's other files under it.
- Cap: `HostConfig.maxUploadBytes`, per file, from `--max-upload-mib` / `TOMTE_MAX_UPLOAD_MIB` (whole MiB, at least 1; default 1024, 1 GiB). A declared `Content-Length` over it is refused before the body is read; a stream that goes over it is cut and its partial file removed; both answer 413 naming the cap and close the connection. `/api/info` carries `maxUploadBytes` so the page refuses an oversize file before sending it. A client that gives up mid-upload leaves no file.
- Web: `host/upload.ts` (`upload`, `uploadAll`: four files at a time), `lib/picked-files.ts` (what an input or a drop holds, folders walked with `webkitGetAsEntry`), the Files section's Upload files / Upload folder buttons and drop zone (`features/bots/files-upload.tsx`, which toasts each rename) and the composer's attach (`features/chat/api.ts` `attach`, uploads into `attachments/` when the message is sent; `ATTACHMENTS_DIR` is in the contract).
- Tests: `host-server/uploads.test.ts` (a 200 MB upload byte for byte, clashes, the `folder` rule, escaping paths, symlinks, the cap in both forms, content type and Origin), `host-server/attachments.test.ts` (sending with attachments), `platform/config.test.ts`; `smoke:files-ui` drives the page.

## Channels

A channel delivers needs-you items and routine results to the owner outside the web UI and routes answers back (ADR-0010, spec `docs/plans/telegram-channel/spec.md`). Nothing in the answer path knows a channel's transport.

- Host: `packages/host/src/channels/` (public surface `index.ts`, private `store.ts` with `channel_links` and `channel_link_codes`). `Channel` is an adapter (`kind`, `start`, `stop`, `send`, `edit`); `createChannels({ db, onActivity })` holds the registry keyed by kind and the one transport-independent handler `Channels.receive(kind, inbound): Promise<Reply>`. An adapter is built by the composition root with `receive` passed in (`HostServerOptions.channelAdapters`), so a second adapter needs no change anywhere else. A message from the linked account calls `onActivity` once and goes to the handler set with `channels.handle(...)` (an empty reply until a later feature sets one); from anyone else only a code-shaped text does anything (a link attempt, counted like a pairing attempt: 10 failures kill the channel's codes, a new code restarts the count), and every other update gets no reply, changes nothing and is not counted. A `MessageRef` is an opaque string the adapter reads back to edit.
- Telegram (`channels/telegram/`, private to `channels`; `createTelegramChannel` is exported from `index.ts`): `api.ts` is the transport (`getMe`, `getUpdates`, `sendMessage`, `editMessageText`, `answerCallbackQuery`; its errors never carry the URL, which holds the token), `mapping.ts` is the pure half (`inboundOf`: update to `Inbound`, only private chats, no edits, no bots; `callsOf`: `Reply` to calls, an empty reply makes no call, so a stranger's button press gets no `answerCallbackQuery`; an edit always states its keyboard so a card can lose its buttons; text is plain, previews off, cut below 4096) and `channel.ts` is the adapter: one long-polling loop (`timeout=50`, `allowed_updates` `message` and `callback_query`), the offset in memory and advanced after an update is handled, errors back off 1 s to 30 s, 401 stops it (reported as "the bot token was rejected"), 409 is reported and retried, and a spaced, ordered sender that waits out a 429's `retry_after`. A webhook replaces only the loop. The host always runs it (`createHostServer` registers it before `channelAdapters`); `HostServerOptions.telegram` (`baseUrl`, `pollTimeoutSeconds`, `sendSpacingMs`, `backoffMs`) is what tests and smokes set.
- The bot token is the secret `channel-token:telegram` (`channelTokenSecretName` in `platform/secrets.ts`), set by `POST /api/channels/telegram/token` `{token}`: checked with `getMe` first (400 when Telegram rejects it, 502 when it cannot be asked, nothing stored either way), then stored and the loop restarted on it. No route, event or log returns it. Unlinking keeps it. `Channel` has optional `status()`, `linkUrl(code)` and `setToken(token)`; `/api/channels/list` carries each channel's `status` (`unconfigured`, `starting`, `running` with the bot's username, `failed` with a reason) and `/api/channels/link-code` the `https://t.me/<bot>?start=<code>` link.
- Link code: 12 base32 characters in groups of four, single use, 10 minutes, only the digest stored (the pairing code's rules, `device-auth/index.ts`). `/api/channels/list`, `/api/channels/link-code`, `/api/channels/unlink` and `/api/channels/telegram/token` are in `host-server/api/channels.ts`, dispatched by prefix like `/api/devices/`; schemas are in `packages/contract/src/api.ts`.
- Web: `packages/web/features/channels/`, the Channels section of Settings (`/settings/channels`, composed through a slot in `app/routes/settings.lazy.tsx`). The dialog is `PairingCodeDialog`'s twin; the section also has the token field and each channel's status line, and asks the host again every 3 s.
- Cards (ADR-0010, ticket `docs/plans/telegram-channel/issues/03-needs-you-cards.md`): `channels/cards/` (public `createCards({ db, channels, chat, sources, publicUrl, retryMs? })`, returning `sync`, `stop` and `receive`) sends each open needs-you item once to every linked channel as a card, edits it when the item closes anywhere, and routes buttons and words back. `types.ts` has `CardSource` (one per item kind: `kind`, button `prefix`, `open()`, `view(id)`, `press(id, arg)`, `reply(id, text)`); `compose.ts` builds the message (plain text cut at 3000 characters, one button per row, data `<prefix>:<id>:<arg>` of at most 64 bytes, a URL button to `<public URL>/bots/<id>?panel=<panel>` only when the public URL is not loopback http, a hint to reply when an action needs words); `store.ts` is `channel_cards` (V20: channel, item kind `event` or `wait`, item id, bot id, message ref, sent at, closed at; unique per channel, kind and item); `tracker.ts` reconciles it (`sync()` sends missing cards oldest first across sources and edits cards whose item is no longer open, each edit once since `closed_at` is set first; a failed send is retried after `retryMs`, doubling, and a failed edit is logged and dropped); `router.ts` routes a button by prefix and words (a reply goes to the card it replies to, one open card takes a plain message, several ask for a reply, none gets a hint about `@Name`; see "Talking to a bot" below). The host's source is `host-server/event-cards.ts` (kind `event`, prefix `a`, buttons from `itemActions` plus `Dismiss`, arg `d`); A notice (kind `notice`, source "Tomte": an auto-pause, an absence warning, an absence pause; cost-guards ticket 06) is an item like any other and goes out through this same source, with no special path: its card is its title and body, Dismiss only (`itemActions` has no actions for the kind) and a link to `?panel=routines` of its bot instead of `work`. Words are never an answer to it: a reply to the card, or a plain message when it is the one open card, gets "A notice takes no reply. Use Dismiss." and reaches no bot. Dismiss closes it everywhere; a notice that closes as `resolved` (a routine resumed, the owner back) has its card edited to "Resolved". Every `Events` change, not only one with transcript rows, syncs the cards, because a notice leaves no transcript row. `channels` imports no feature, so the source is composed in `host-server/index.ts`, which calls `cards.sync()` on start, on link (`Channels.onLinked`), on `Events` `onOpened` and `onChange`, on every wait opening or closing (`waits.subscribe`) and when a bot is removed (`HostServerOptions.cards.retryMs` is for tests). Unlinking, or linking a different account, deletes that channel's `channel_cards`.
- Talking to a bot (ticket `docs/plans/chief-of-staff/issues/03-talk-to-any-bot-from-telegram.md`, spec `docs/plans/chief-of-staff/spec.md`, "Phone: `@Name` and replies"): the channel handler is still the card router; it gains one injected `chat` dependency (`CardChat` in `channels/cards/types.ts`: `send(botId, text, channel)` and `bots()`, newest first), composed in `host-server/phone-chat.ts` (`createPhoneChat`) and passed to `createCards` by `host-server/index.ts`, so `channels` still imports no feature. There is no implicit target: no bot is "the" bot of the phone. Words from the linked account are decided in this order: a Telegram reply to a card goes to that card's source; a message that starts with `@` and a bot's full name (`cards/mention.ts`, `leadingMention`: case-insensitive, runs of spaces collapsed, then a space, `:`, `,` or the end, longest name wins) goes to that bot with the name stripped (a bare name is asked for a message; an unknown name gets the list of the bots' names); otherwise one open card takes the words, several ask for a reply, and with none the owner gets "To talk to a bot, start with @ and its name, for example @<newest bot's name>." `chat.send` is `Chats.send(botId, text, text, [])` with no item id: it queues on a busy bot, reaches a double-loop front as a send, never answers a pending question or approval, and its `queued` and `refused` outcomes are replied as text.
- Origin and replies: `chat_origins` (`SCHEMA_V29`, `bots/origin-store.ts`: `setOrigin`, `getOrigin`, `deleteOrigin`; bot id, `web` or a channel's kind, time) records where the owner's latest message to a bot came from. `/api/send` sets `web`, a routed Telegram message sets `telegram` (neither for a refused send), `removeBot` deletes the row and it survives a restart. `ChatsDeps.botSaid(botId, text)` is called for a standard turn's final text, a double-loop front's reply and each report, never for a scheduled run's turn; `host-server/phone-chat.ts` (`forwardToOrigin`) passes it to `Channels.say(kind, { botId, botName, text })` while the origin is a channel. `say` sends plain text that starts with the bot's name, whole and never edited, with a link button to `<public URL>/bots/<id>` (none on a loopback http public URL), retried with the notices' backoff (`channels/replies.ts`; `deliver` is shared with `notify`) and logged when it still fails; it never rejects. Tests: the router's order and `@Name` cases in `channels/cards/cards.test.ts`, `say` in `channels/channels.test.ts`, a whole host in both chat modes in `host-server/phone-chat.test.ts`, the origin row in `host-server/bot-delete.test.ts`; `smoke:channels-ui` sends one `@Name` message through the fake Bot API and reads the reply.
- Run notices (ADR-0010, ticket `docs/plans/telegram-channel/issues/05-run-notices.md`): `Channels.notify(notice)` sends one plain message, with a URL button to `<public URL>/bots/<id>?panel=routines` (none on a loopback http public URL), to the linked account of every channel that has one; no buttons, not tracked after sending. `Notice` (`channels/notices.ts`, a Zod union in the host, not the contract) is `run_failed` (`botId`, `routine`, `error` cut to about 300 characters, `interrupted`) `park_expired` (`botId`, `routine`, `wait`) `routine_result` (`botId`, `routine`, `output`; ticket 06 below) and `host_problem` (`hostName`, `problem`; no bot, so its link goes to `/settings/models`, or `/settings/about` for a failed update; see "Claude access", host problems); a new kind is a new member and a new case in `noticeMessage`. A send that fails is tried again 4 times with a doubling wait (`ChannelsDeps.noticeRetryMs`, 2 s; `HostServerOptions.notices.retryMs` for tests) and then logged; `notify` never rejects, and `stop()` ends the retries. The run row stays the record. `createRoutines` takes `onRunEnded(end: RunEnd)`, called once when a run reaches `succeeded`, `failed` or `interrupted` after its row is final (a turn's end, a resumed run's last turn, an expired park, a session that ended a park, a run the last process left running, found by `start()`), never for a skipped run, for a run stopped by `remove()` (the cascade owns it) or for one stopped by shutdown (`stop()` leaves its row `running`, so the next start reports it as interrupted). `RunEnd` is `{ run, routine, expired }`: `expired` holds the titles (`waitTitle`, `waits/index.ts`) of the waits whose 24 hours ran out, so an expiry is told apart without reading the error text. `host-server/run-notices.ts` (`runNotice`) turns it into a notice: `failed` or `interrupted` always, `park_expired` instead of `run_failed` when `expired` is set, nothing for `succeeded` but a routine's result (below); `host-server/index.ts` sends it unless the bot is gone. The channels and their adapters are created before the routines so a park that expired while the host was down is reported by `waits.start()`'s sweep. - Human-wait cards (ticket `04-human-wait-cards.md`): `host-server/wait-cards.ts` (kind `wait`, prefix `w`, `createWaitCards({ waits, chats, botName })`) turns each open row of `human_waits` (`Waits.list()`, `Waits.get(id)` for a closed one) into a card: a tool approval (tool, reason and the exact stored input as JSON), an `ask_user` question (its options) and a takeover (reason, link to `?panel=browser`, its own actions). An approval whose input is over 2400 characters is cut with "…" and "Input too long to show here. Open the web UI to approve.", offers Deny only and refuses any other index at press time. A question about an external event has no card (the event's card answers it through `pendingAskFor`). ## Bot creation

Every bot can propose a new bot (spec `docs/plans/chief-of-staff/spec.md`, ticket 01): `create_bot(name, purpose, memory?, chat_mode?)` on the bots endpoint (`handoffs/tools/create-bot.ts`), next to `list_bots` and `hand_off`, for every bot and every session kind (the standard thread, a headless routine run, the double-loop front; the MCP server is per request, so no extra wiring). `BotsToolContext` has `unattended()` and `createBot(spec)`. The tool's guards, in order: refused in a scheduled run; name at most 80 characters, purpose required and at most 400, memory at most 1200 (so the approval card stays under the size at which a channel card offers Deny only); refused when the host has 20 bots. `createBot(dataRoot, name, purpose, id, avatar, memory)` writes a non-blank memory seed to the new bot's memory file; `/api/bots/new` takes no seed. The new bot has the browser off, `chatMode` from `chat_mode` (default `standard`), and the owner's open chat does not move. `BOTS_INSTRUCTIONS` tells the bot to propose only when no bot fits, say why and wait for approval.

The permission is fixed: `ALWAYS_ASK_TOOLS` (`waits/index.ts`) holds `mcp__bots__create_bot`. `createCanUseTool` checks it before `approveAll`, a stored allowance and the `mcp__bots__` allow prefix, so a host that approves everything still raises the normal approval card (`human_waits`: the web UI, the linked channel and `wait-cards.ts` show the tool and the exact input). `approvalActions` leaves out `allow_always` for it, so none is offered and an answer naming it is refused (`/api/answer` 404). Where nobody watches (`HostDelegate.attended()` is false: a chat-hosted routine turn through `hostDelegate`, a headless run through `parkingDelegate`) it is denied at once, with no card and no wait. The double-loop front's bots lease is `attended` (`BotsEndpoint.lease(botId, { attended: true })`), like its routines lease, because its routine runs go headless in sessions of their own.

Tests: `handoffs/create-bot.test.ts` (whole host: the card, its exact arguments and buttons, approve and deny, the seed, browser off, `chat_mode`, always-allow refused, the cap, argument refusals, a double-loop front, chat-hosted and headless routine runs, who has the tool, the card on the fake Bot API), `bots/bot-memory-seed.test.ts` (`createBot`'s seed) and `bots/can-use-tool.test.ts` (the fixed ask). ## Built-in Gmail

Gmail is a built-in integration: an in-process MCP server on the Gmail REST API, with the owner's own Google OAuth client (ADR 0012, spec `.scratch/gmail-native/spec.md`). The catalog entry (`integrations/catalog.ts`, id `gmail`) names `builtin: "gmail"`, not a URL; its row has the transport `{ type: "builtin", service: "gmail" }` (`BuiltinService` and `IntegrationTransport` in `@tomte/contract/events`), the server name `gmail` and so the tools `mcp__gmail__<tool>`. Calendar, Sheets, Docs and Drive stay on hosted MCP URLs. The hosted Gmail URL is gone; nothing aliases it.

- Host: `integrations/builtin.ts` (service table: `builtinTools`, `createBuiltinServer`, `BUILTIN_LOCKED_TOOLS`), `integrations/verbs.ts` (verb classes: default policy, annotations, lock), `integrations/google-oauth.ts` (PKCE authorization URL with `access_type=offline` and `prompt=consent`, code exchange, `refreshTokens`, `GrantRevoked`, `GoogleEndpoints`) and `integrations/gmail/` (`tools.ts` lists every tool, one group per file: `read-tools.ts`, `draft-tools.ts`, `organize-tools.ts`, `attachment-tools.ts`, `send-tools.ts`; `server.ts`, `client.ts` the REST client and `GmailError`, `mail-text.ts` the untrusted wrapper, HTML to text and the cut marker, `compose.ts` and `mime.ts` the message builder). A new tool is an entry in its group with a `verb`; its policy, annotations and lock follow the verb.
- Handoff: a connected, enabled built-in row gives `IntegrationsSource.session()` an SDK server instance in `builtinServers`, never in `mcpServers` (that is written into the CLI's `--mcp-config` file and must stay JSON). `bots/thread.ts` (standard threads and headless routine runs) and `loop/front.ts` merge it into `query()`'s `mcpServers`, with the same filter that keeps an integration from shadowing a host server name. `session(filesDir)` gives it the bot's files folder, where `get_attachment` saves a file.
- Sign-in and tokens: `connectOAuth` and `finishOAuth` branch on the builtin transport; the tokens and the shared client live in the integration's secret entry (`oauth`). `accessToken(id, rejected?)` in `integrations/index.ts` is read on every call, refreshes within `EXPIRY_MARGIN_MS` (or after a 401), and shares one in-flight refresh per integration. `invalid_grant`, a 401 after a refresh and a 403 `insufficientPermissions` call `needsSignIn(id)`: tokens dropped, the client kept, state `needs-auth`. Disconnect keeps the owner's client (for every own-client integration), Remove deletes the secret entry. At host start a built-in row's tools are upserted from its definition (an owner's policy is kept) and the catalog's auth replaces the row's.
- Send lock: `send_message` is the one tool of the `send` verb (Ask or Off, never Auto: `setPolicy` answers 400, a stored Auto reads as Ask). `createCanUseTool` (`bots/session-kit.ts`) asks for a locked tool whatever `approveAll` or an always-allowed rule says; its wait has Allow and Deny only (`approvalActions(tool, locked)` in `waits/index.ts`, and `allow_always` on it is refused with 404); an allow runs only the exact input shown (`canonicalInput`); for a draft send the host fetches the draft so the card shows its recipients, subject and body, and the send is refused if the draft changed since approval (`gmail/draft-content.ts`); a routine's send parks the run (ADR 0009). A custom integration cannot be named `host`, `browser`, `bots`, `routines` or `gmail` (the reserved names).

`harness/claude-access.ts` (`ClaudeAccess`) owns every Claude CLI child's environment and sign-in. `recheck(reason)` runs `auth status` and `--version` (cached once answered), one run at a time whoever asks, and keeps a `report()` (state, account: method, email, organization, plan; CLI version); `/api/providers` returns it with the custom provider (`gateway`, never its token) and a sign-in waiting for its code (`login`).

- Live status (`HostStatus`, `@tomte/contract/host-status`; the first phase of `.scratch/client-host-split/spec.md`): every host, local or remote, tells every page whether Claude is signed in without anyone opening Models. `claude.status()` is a `ClaudeStatus` (`state` `signed-in`, `signed-out` or `unknown`; `method` `subscription`, `long-lived-token` or `custom-provider`; `ignoredEnv`, the billing variables the host ignored (below); `checkedAt`), `claude.onChange(listener)` fires when the state or the method changes, not when a check finds the same, and an `unknown` answer (the CLI would not run or printed nothing parseable) never replaces a known state. `claude.start()` (called by `createHostServer`) checks at startup, every 10 minutes (`claudeRecheckMs` in `HostServerOptions` for tests), and when `.credentials.json` in the CLI's config directory (`claudeConfigDir`) changes (`fs.watch`, 200 ms debounce; in remote mode the host makes the directory so the watch can start, in local mode a missing one is retried on the timer; a macOS keychain sign-in leaves no file, so the timer is what sees it there). - Sign-in from the web UI (`harness/claude-login.ts`, `claude.login`): `POST /api/providers/claude/login` spawns `auth login` with piped stdio and answers the URL it prints (502 when none comes within 20 s); `/login/code` `{code}` writes the code to its stdin and answers `{ ok, status }` (409 with no sign-in waiting, 400 with the CLI's `Couldn't log in: …`); `/login/cancel` kills it. - Custom provider: `POST /api/providers/claude/gateway` `ClaudeGateway` (`baseUrl`, `auth` `bearer` or `api_key`, `token`) stores the secret `claude-gateway` (`claudeGatewaySecretName`), applies it to every later CLI child (inherited `ANTHROPIC_*` dropped first; the token goes on a descriptor, see "Credentials on descriptors") and reconfigures open chats; `/gateway/remove` deletes it. - Credentials on descriptors (ticket 16 of the client/host split; spec decision 7; owner decision 2026-11-19: pipe or socket descriptors only, never a regular file, which `/proc/<cli pid>/fd/N` can reopen where the sandbox is off). `ClaudeAccess.spawnSpec()` is the one source of what a CLI child starts with, a `SpawnSpec` (`harness/spawn.ts`: `env` and an optional `credential`): the credential is the custom provider's token or the long-lived token, never in `env`; `env` names the descriptor, always `CREDENTIAL_FD` (3), in `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` (long-lived token), `CLAUDE_CODE_API_KEY_FILE_DESCRIPTOR` (custom provider, `api_key`) or `CLAUDE_CODE_GATEWAY_TOKEN_FILE_DESCRIPTOR` with `CLAUDE_CODE_USE_GATEWAY=1` (custom provider, `bearer`; the CLI ignores that descriptor without the flag). - `spawnSpec()` is read inside the start gate (`Thread.open`, `FrontSession.open`, the sign-in probe), at the moment the start begins, so every start hands over the credential set then; a token set while a start waits for the gate is the one it uses. Plan usage and `--version` use `baseEnv()` and no credential.
- Long-lived token validation (ticket 20 of the client/host split; owner decisions in chs-16-q2): the CLI's `auth status` reports signed in for any string on `CLAUDE_CODE_OAUTH_TOKEN_FILE_DESCRIPTOR` (real CLI 2.1.328), so the host checks the token itself. Shape: `ClaudeLongLivedToken` (`@tomte/contract/api`) is `sk-ant-oat01-` then `[A-Za-z0-9_-]+` after trimming; the route answers 400 with a message that says to paste the `sk-ant-oat01-…` line `claude setup-token` prints at the end, not the browser code, and stores nothing and leaves the token in use alone; the Models page (`PasteToken`) runs the same schema before sending. Rejection: while the long-lived token is the method (no custom provider), `recheck("turn-auth-failure")` (every `isAuthFailure` path: `Thread.send`, the double-loop front's catch and its error `result`) marks it rejected in `ClaudeAccess`: `status()` is `signed-out` with `reason: "token-rejected"` (`ClaudeStatus.reason`, `HostProblem` `claude-signed-out` carries it too), `report()` reads signed out with no account, and no `auth status` answer undoes it; only `setLongLivedToken` with another token (or none) clears it, and under a custom provider the flag is ignored (not shown), returning when the provider is removed. `requireSignIn` (remote mode) refuses with a message naming Settings, Models. Because it is a `claude-signed-out` problem, the live status, the web banner ("Replace token"), the tray line ("Claude token rejected") and the one `host_problem` channel notice all fire without a new path; the notice and banner say the token was rejected. Persisted: `onTokenRejected(digest)` makes the host keep the SHA-256 of the token as the secret `claude-long-lived-token-rejected` (`claudeTokenRejectedSecretName`, never the token); at start `setLongLivedToken(token, storedDigest)` starts out rejected only for that same token, and the token and removal routes delete the secret, so a restart with the same bad token shows signed out at once and a new token never inherits it. Known gap: a turn that began under the old token and fails after the token was replaced would mark the new one rejected (it is cleared by saving it again). The fake CLI refuses one token with a `401 Invalid bearer token` result while `auth status` still says signed in (`invalid-token` file, `host.setInvalidToken`). Tests: `harness/claude-access.test.ts` (`a long-lived token a turn failed to authenticate with`), `host-server/claude-long-lived-token.test.ts` (shape, trimming, rejection, restart, replace, remove) and `host-server/host-problems.test.ts` (the channel message).
- Env deny, kept as defence in depth (owner decision 3): `claudeHarness` passes `sandbox.credentials.envVars` with `ANTHROPIC_AUTH_TOKEN` and `ANTHROPIC_API_KEY` (`GATEWAY_TOKEN_ENV`, `deny`) to every sandboxed session. Before the token moved to a descriptor, a probe on a Linux host in remote mode (managed CLI 2.1.328, sandbox on) found the custom provider's token in the shell's environment and in `/proc/<pid>/environ` of the sandbox's own wrapper process. The probe is `scripts/probe-credential-fd.ts` (runbook `docs/probe-credential-fd.md`; real CLI, so it is not part of `bun run check`). Test: `host-server/shell-isolation.test.ts`.
- Fake CLI: `--version`, `auth status` with an account and descriptor-driven methods (it reads the credential descriptor to the end at start-up and records it as `credential` in `launches.jsonl`, apart from `env`), an interactive `auth login` (`bad-code`, `host.completeLoginCallback()`); tests in `host-server/claude-provider.test.ts`.

## Host binary

`bun run build:host [target…]` builds the web UI, then compiles `packages/host/src/main.ts` with `bun build --compile` into `dist/host/tomte-host-<os>-<arch>[.exe]` (gitignored) for `darwin-arm64`, `darwin-x64`, `linux-x64`, `linux-arm64` and `windows-x64`; name targets to build only those. `scripts/build-host.ts` explains the x64 baseline, minify and sourcemap choices. The built web UI is embedded (`ui/assets.ts`); Vite, the Claude CLI and the browser engine are not.

`main.ts` is the one compiled entry and also runs from source: `[flags] [botId]` starts the server like `bun run ui`; `pair`, `install-cli`, `install-browser`, `browser-smoke`, `auth-status` and `auth-login` run the `host.ts` subcommands; `auth-status` and `auth-login` run the Claude CLI's `auth status` and `auth login` with the environment the host gives its bots' CLI children (in remote mode, which runs on Linux only and is refused on macOS and Windows (ADR-0006), the allowlist and `claude/` in the data root as `CLAUDE_CONFIG_DIR`); after a successful login, `auth-login` runs a fresh `auth status` and exits non-zero when it still reports signed out. Any message that names a command goes through `platform/launch.ts` (`hostCommand`, `serverCommand`), so it names the binary or `bun run host` depending on how the host was started.

Two more subcommands of `main.ts` are not `host.ts` ones: `version` prints `{"version","schemaVersion"}` as one JSON line (what the root update helper reads from the installed, the previous and the downloaded binary), and `apply-update` is the root update helper (see Update helper below).

The database is `tomte.db` in the data root, its schema version in `PRAGMA user_version` (`platform/db.ts`, `SCHEMA_VERSION`). A host opens a database at or below its version and migrates it; one above it is refused before anything is written (`DatabaseTooNew`: exit 2, a message naming both versions and saying to update the host or restore a matching backup), so an old binary never runs on a newer database. Tests: `platform/db.test.ts`, and a whole `main.ts` process in `host-server/sidecar.test.ts`.

`--sidecar` (local mode only) is how the desktop app runs the host: it reads one launch-token line from stdin and registers it as the device "This computer" (replacing the previous launch device), prints one `SidecarReady` JSON line with its client URL to stdout (everything human-readable goes to stderr), installs the managed Claude CLI into the data root when none resolves, installs the browser in the background when neither the bundled copy nor a managed one resolves (`browser/auto-install.ts`; until it is done the browser's unavailable reason says it is installing instead of naming `install-browser`, and a failed install is retried on the next status check), and shuts down gracefully, releasing the data-root lock, when stdin ends; without the flag the host never reads stdin. The shared shapes live in `@tomte/contract/sidecar`.

`bun run smoke:host [binary]` (default: this machine's build output) runs a built binary for real: it copies it outside the repo, installs the managed Claude CLI with `install-cli` (unless `CLAUDE_PATH` names one), starts it on a temporary data root, pairs with `pair`, creates a bot, checks the event stream, loads the embedded UI (every asset `index.html` references, with the CSP), checks what the client listener refuses, stops it with SIGTERM and removes everything. It needs network for the CLI install and runs only a binary built for the machine it runs on (for a Linux binary in a container, compile the script with `bun build --compile --target=bun-linux-arm64 scripts/smoke-host.ts` and run both binaries there).

## Desktop app

`packages/desktop/` (`@tomte/desktop`) is the Electron app. Its main process runs no host code (dependency-cruiser rule `desktop-only-to-contract`, ADR 0003): it spawns the host binary with `--sidecar`, writes a fresh launch token to its stdin, keeps the pipe open, waits for the ready line, sets the `tomte_session` cookie in its own session and loads the host's client URL. The window has context isolation and the sandbox on, no Node and no preload. Navigation is limited to the host's origin; other web URLs and every `window.open` go to the system browser or are denied (`navigation-policy.ts`). Quitting ends the sidecar's stdin and waits for the host to exit; if the app dies, the host sees EOF and stops itself. It keeps its own user-data folder, `Tomte Desktop` under the OS app-data folder, apart from the host's data root; `--user-data-dir` overrides it.

On macOS the main window has a hidden title bar with Window Controls Overlay (`window-chrome.ts`: `titleBarStyle: "hidden"`, `titleBarOverlay: { height: 56 }`), so the real close, minimize and zoom buttons sit beside the web app's own header and there is no separate OS title strip; Windows and Linux keep the default frame. The web UI is a sheet on a desk (the sidebar's `variant="inset"`; palette and `--sheet-shadow` in `tailwind.css`, after Nuphos's design tokens): the sidebar sits on the canvas and the content is one rounded sheet 8px inside the window, whose top row is the header (`AppBar` in `packages/web/components/page.tsx`, `h-10`). A bot's chat on a window 1024px and wider is two sheets instead (the chat and, while the panel is open, the panel), 8px apart, with the 40px activity rail bare on the desk at the window's right edge, its first icon level with the header's centre line (it sits clear of the native controls, which are at the left on macOS): the shell's inset goes bare for a child marked `data-split` (`app/shell.tsx`) and `ChatView` (`features/chat/chat.tsx`) gives the chat and the panel each the sheet's background, corners and shadow. 8 + 40 + 8 is `TITLE_BAR_HEIGHT`, so the lights and the header share one centre line; change them together. The web app reads `navigator.windowControlsOverlay` (`packages/web/lib/window-controls-overlay.ts`) and sets `data-wco` on `<html>` (Electron's `display-mode: window-controls-overlay` media query is false, so CSS cannot gate on it); only then the header, the sidebar's top strip (`TitlebarStrip`, `data-titlebar`, 40px from y 8, level with the header) and the shell's 8px strip along the window's top edge are `-webkit-app-region: drag` and the controls inside them `no-drag` (`tailwind.css`). The lights sit over the sidebar's strip at every stop (the rail is 76px for them); only on a narrow window, where the sidebar is a sheet, the header pads left by `env(titlebar-area-x)`. In a browser tab and in fullscreen `env()` falls back to 0, so the page is unchanged. The desktop shell's own pages (`window.ts`) get the same drag strip through `env(titlebar-area-height)`. The Connections window keeps the standard title bar. A remote host serving an older web build has none of this CSS: the lights overlay the top-left of its UI and nothing in it is draggable until that host is updated.

The sidebar is never hidden from `md` up (`components/ui/sidebar.tsx`): it has three stops, `rail` (76px, bot faces with the needs-you count on a corner and the name in a tooltip, icons for Integrations and Settings), `names` (208px, face, name and count) and `full` (320px, the whole rows). Dragging its edge (`SidebarRail`) follows the pointer and settles on the nearest stop; double-click, Enter or ⌘B goes to the rail and back, the arrow keys step between stops; the stop is kept in `localStorage` (`sidebar_stop`). The Sidebar's `data-stop` names the stop shown. Settings has no rail form (`minStop="names"`). On a phone the sidebar is a sheet and the header's `SidebarTrigger` (shown below `md` only) opens it.

Closing the window hides it (and the dock icon, on macOS); the app and the host keep running in the tray (`background.ts`). The tray (`tray.ts`, menu in `tray-menu.ts`) has a template icon (`packages/desktop/assets/trayTemplate.png` and `@2x`, drawn by `bun run icons:desktop`, copied next to the bundle by `build:desktop`), shows one disabled line per followed host (this computer: starting, running or stopped, from `supervisor.ts`; each server: connecting, connected or unreachable, from its event stream) in its tooltip and first items, each with the contract's `needsYou` count and its first problem ("This computer: running · 1 needs you", "my-vps: connected · 1 needs you · Claude signed out"; `host-lines.ts`, `hostLines` and `hostLineText`, pure, as is `trayMenu(hosts, …)`), and offers one radio item per connection profile (the active one checked) and Manage Connections…, Open Tomte, Start at login, Run this Mac's host (a checkbox: unchecked only when the host runs just while This computer is shown; see "This computer's host while a server is shown"), Restart host (only while stopped, with a fresh launch token; a paused host has none) and Quit Tomte. The local state comes from `supervisor.ts`, which follows the sidecar's `exited` promise. Every way of quitting (tray, app menu, Cmd+Q) ends in `app.quit()` and the `before-quit` handler in `main.ts`, which ends the host's stdin and waits for it (bounded, then kill) before exiting.

Start at login is a desktop setting in `settings.json` in the user-data folder (`{ "startAtLogin": boolean, "localHost"?: "always" | "while-shown" }`, Zod-parsed; a missing file is a first launch and means true, an unreadable one means false and is left alone). `settings.ts` `openSettings(file, log)` is its one reader and writer (`get()`, `update(patch)`: a patch never drops another key); `start-at-login.ts` and the local host policy below share one store. Every launch applies it to the OS through the `LoginItem` interface (`login-item.ts`); the tray checkbox changes the file and the login item (`start-at-login.ts`). The OS implementation (`electron-login-item.ts`) calls `app.setLoginItemSettings` and passes `--hidden`; an app the OS opened at login (`wasOpenedAtLogin`, or `--hidden`) starts with its window hidden. When `TOMTE_DESKTOP_LOGIN_ITEM_FILE` names a file, the login item is recorded there as `{ "openAtLogin": boolean }` instead and the OS is never asked: every smoke and test on a developer machine sets it, so nothing registers itself at login.

This computer's host while a server is shown (`local-policy.ts`, `supervisor.ts`, `local-host-question.ts`; spec `.scratch/client-host-split/spec.md`, phase 5, gap A; owner decision: always ask, no default). `settings.json`'s `localHost` is absent until the user answers; absent runs the host exactly as before, so nothing pauses before an answer. `always` keeps it running whatever the window shows; `while-shown` runs it only while This computer is the connection shown. `localWanted(setting, shown)` (pure) decides; `createLocalHostPolicy` joins it to `supervisor.want(running)` and gives the supervisor a wish only when it differs from the last one given, so a host that crashed is not started again by an unrelated change. `Supervisor.want(running)` replaces `start()`: calls run one after another (the latest wish wins, two hosts never overlap on the data root); `false` ends a running host or turns a stopped one into `paused` without launching; `true` launches from `paused` or `stopped`. `HostState` gains `paused`, distinct from `stopped` (a failure or crash): the tray line reads "This computer: paused" with no needs-you count and no problem (`hostLines` shows none for a local host that is not running), the window shows the starting page if This computer is shown while it is paused, and `followTargets` leaves it out. Pausing is a graceful stop of the sidecar, the same as quitting: nothing is deleted or moved, and a routine run in flight ends as interrupted. The host's own start-up applies each routine's `catchUp` to what came due while it was down, as after a restart; the app does nothing extra. At launch the host is wished by what the saved connection will show (`Connections.savedActive()`), then `connections.start()` runs; afterwards every change of the connection shown, of the setting and the window appearing goes through `policy.reconcile`/`refresh` in `main.ts`. The one-time question (a native `dialog.showMessageBox` over the window, "Keep bots on this Mac running while you use <server>?": Keep running = `always`, Pause while I use a server = `while-shown`, Ask me later = still unanswered) opens the first time a server profile is shown while the window is visible (a hidden window gets it when it appears), once at a time, and for a deferred one again only after This computer was shown and a server is shown after it. The tray's Run this Mac's host checkbox (checked unless `while-shown`) reads and changes the setting; a click is an answer. The smokes never open the dialog: `desktop-smoke-kit` sets `TOMTE_DESKTOP_LOCAL_HOST_QUESTION=off` (`LOCAL_HOST_QUESTION_ENV`: the question counts as "later") for every launch, and `smoke:desktop:profiles` step 8c replaces `desktop.localHostQuestion.ask` in the main process (as `smoke:desktop` replaces the notifier's `show`). Tests: `local-policy.test.ts`, `supervisor.test.ts`, `settings.test.ts`, `tray-menu.test.ts`, `host-lines.test.ts`; `smoke:desktop:profiles` step 8c answers "pause", sees the sidecar exit while the fixture remote is shown, the tray read paused, the host start again when This computer is shown, no second question and Run this Mac's host start it beside the server.

Following every host (`desktop-follow.ts`, `follow-hosts.ts`, `host-stream.ts`, `needs-you-banner.ts`; spec `.scratch/client-host-split/spec.md`, phase 5, decision 1): the main process follows the `/api/events` stream of this computer's host while it runs and of every paired profile at once, whichever one the window shows. `Connections.followTargets()` (`FollowTarget`: `id`, `name`, `origin`, token, from the launch token's device for this computer and each profile's device token; a profile whose token cannot be read is left out) replaced the single `credentials()`, and `desktop-follow.ts` syncs one stream per target on every `onChange` (a new origin or token, as after a host restart, restarts only that host's stream). `host-stream.ts` (`followHost`) parses the `bots` and `host-status` events with the contract schemas and skips every other event unparsed. `follow-hosts.ts` (`createFollowedHosts`) keeps each host's view (`connecting`, `open` or `down`, its latest bots and status; a down or reopened stream clears them) for the tray and feeds the banner. The banner (`needs-you-banner.ts`) keeps a baseline per host, and a host's first slice and first status are baselines, never rises. When a host's open items rise, or it gets a new problem, while the window is hidden it shows one Electron `Notification` that names the host ("<bot> (<host>): N things need you" with the bot's `needsYouSources` as body, the bot with the newest `needsYouAt`; "<host>: Claude signed out" for a problem). A later rise on any host replaces the banner instead of stacking another; showing the window, or that host's stream opening again, closes it. Clicking it reveals the window, switches to that host (`connections.connect(id, path)`, which also saves it as the connection to open at the next start) and loads `/bots/<id>` of the bot with the newest open item at that moment (the host's root for a problem). It is a main-process Electron notification, so the web page keeps getting no notification permission. The smoke replaces `Notification` with a recording stub and calls the click handler, so no OS banner or OS notification permission is involved; `smoke:desktop:profiles` step 3d raises a rise on the fixture remote while This computer is shown.

Downloads (`downloads.ts`, wired in `main.ts`): the window's session handles `will-download` for every file or folder zip the page downloads, from the local host or a remote one. It saves into the OS downloads folder (`app.getPath("downloads")`) without asking, never replacing a file (`name (1).zip`), and announces a completed download through the needs-you banner's `Notifier` ("Downloaded <name>", "Click to show it in Finder"); clicking it calls `shell.showItemInFolder`. A cancelled download says nothing, an interrupted one is announced as failed. The Connections window's own session is not handled. `smoke:desktop:profiles` step 3c drives a folder download from the fixture remote.

Auto-update (`electron-updater`, the one npm dependency of the desktop package beyond Zod; it is bundled into `main.cjs`). A packaged app checks the update feed named by its own `app-update.yml` (this repository's GitHub Releases in a release build): the first check 30 s after start, then every 6 h, downloading in the background as soon as a newer release is found. The update installs when the app quits (electron-updater's quit handler, which the `quit` event of the app's own `app.exit(0)` reaches) or at once through the tray item "Restart to update to <version>", which appears only after a download. Both go through the one graceful quit: `before-quit` stops the sidecar and waits for it, and only then the installer runs (`installUpdateOrExit` in `main.ts`), so the host binary the update replaces is not running. If the install cannot start, the app logs it and relaunches itself instead of hanging. After the sidecar is ready the app reads its `/api/host-info` and logs whether the host's version equals `app.getVersion()` (`WARNING: the host reports version …` on a mismatch); this runs in a packaged app only. Pre-releases are offered only when the running version is itself a pre-release (`allowPrerelease`); electron-updater then follows the same pre-release channel (an `-rc.N` app moves to a newer `-rc.N` tag, never to the stable release; a stable install never sees a pre-release). Every build is on the metadata channel `latest` (`CHANNEL` in `scripts/desktop-kit.ts`): electron-builder would otherwise name a pre-release's metadata `rc-mac.yml`, which the release does not hold; electron-updater asks `rc-*.yml` first for a pre-release tag, gets a 404 and falls back to `latest-*.yml`. Failures (feed unreachable, bad metadata, a failed download, Squirrel.Mac refusing an unsigned app) are logged and never stop the app. The log is `logs/desktop.log` in the user-data folder (every line the desktop process logs, timestamped; the host's stays `logs/host.log`).

No update check runs when the app is not packaged, when `app-update.yml` is missing, when its feed is the local build's placeholder (a `.invalid` host; it is never contacted) or when `TOMTE_DESKTOP_UPDATES=off`. `createSmokeRun` (`scripts/desktop-smoke-kit.ts`) puts that off-switch in the environment of every smoke launch (a launch that wants updates passes `TOMTE_DESKTOP_UPDATES=on` as an extra). The logic is in `updates.ts` behind the small `UpdateEngine` interface (`createUpdater`: schedule, state, logging; fakes in `updates.test.ts`); `electron-update-engine.ts` is the electron-updater implementation, `desktop-log.ts` the log.

- `bun run package:desktop [--out <dir>] [--version <semver>] [--arch <arm64|x64>]… [--host-dir <dir>] [--sign] [--update-url <loopback http URL>]` builds the host for this machine, bundles the main process and runs electron-builder (`scripts/package-desktop.ts`; asar on, unsigned unless `--sign`, never published) for the current OS only. It writes into `dist/desktop/Tomte-<os>-<archs>/` (`<archs>` joined by `-`, e.g. `Tomte-darwin-arm64-x64`): the installers (macOS `.dmg` and `.zip`, the zip being what electron-updater applies on macOS; Windows NSIS `Tomte-Setup-<version>.exe`; Linux AppImage and `.deb`), their `.blockmap`s, the update metadata electron-updater reads (`latest-mac.yml`, `latest.yml`, `latest-linux.yml`) and the unpacked app (`mac-arm64/Tomte.app`, `mac/Tomte.app` on x64, `win-unpacked/`, `linux-unpacked/`). The host binary is copied in as the extra resource `tomte-host` (`Contents/Resources/tomte-host` on macOS), and the browser as `browser-engine` beside it, for the arch being packaged (`scripts/browser-bundle.ts`: the pinned agent-browser engine and the pinned full Chrome for Testing, about 200 MB zipped, SHA-256-checked and cached in `dist/browser-cache/`); the host looks for `browser-engine/` next to its own binary before the data root's managed install. Platforms without a pinned engine and Chrome fail packaging. Only the current OS can be built: electron-builder is not asked to cross-build, and the Windows and Linux targets have not been run in this repo yet.
  Signing is off unless `--sign` is passed (or `TOMTE_REQUIRE_SIGNING=true`; see Releasing, Signing and notarization): without it the script sets `CSC_IDENTITY_AUTO_DISCOVERY=false` and `mac.identity: null` before the first electron-builder call and unsets every signing, notarization and GitHub token variable, so a build never reads the keychain, whatever the environment holds. `publish` is `never`. `--version` (default: the host's `VERSION`) is the app version, hence the installers' names and the metadata. `--arch` (repeatable, default this machine's) packages several CPUs in one run, which is how the macOS release gets one `latest-mac.yml` listing both zips (electron-builder writes one metadata file per OS and run; arm64 files carry `arm64` in their names, the x64 ones do not, which is how electron-updater tells them apart); the other CPU's app is only packaged, not launched. `--host-dir <dir>` bundles the prebuilt `tomte-host-<os>-<arch>[.exe]` files in `<dir>` (as `build:host` and the release workflow's artifacts name them) instead of building any, restoring the executable bit an uploaded artifact loses. The update provider baked into `app-update.yml` is this repository's GitHub Releases when `GITHUB_REPOSITORY` (`owner/repo`, set by GitHub Actions) is set; a local build has no repository coordinates and uses the placeholder `https://updates.invalid/tomte` (reserved `.invalid`, never resolves), but when `CI` is set and `GITHUB_REPOSITORY` is not, packaging fails before anything is built (`updateProvider` in `scripts/desktop-kit.ts`), so a release never ships the placeholder. The `.deb` needs the project homepage, which comes from `GITHUB_REPOSITORY` too, so build it in CI.
  `--out <dir>` (default `dist/desktop`) puts the output under `<dir>/Tomte-<os>-<arch>` instead; only that folder and the stage folder are replaced, never the rest of `<dir>`. Before it builds or deletes anything the script refuses (non-zero) when a running process's command line lies under that folder, so packaging never pulls an app out from under a copy someone is using; to rebuild while a copy runs, package elsewhere with `--out` (`scripts/process-guard.ts`).

- Signing and notarization of the macOS and Windows app: see Releasing, Signing and notarization below. Chrome for Testing is not Google-signed on macOS (the pinned build is ad-hoc/linker-signed everywhere except `Libraries/WidevineCdm/…/libwidevinecdm.dylib`, which carries Google's Team ID), and on Windows every file in the pinned zip is unsigned except Microsoft's `D3DCompiler_47.dll`. electron-builder (`@electron/osx-sign` on macOS) signs every binary under the app, deepest first, except the host (`mac.signIgnore`); the signing checks (`signing.ts verify`, `scripts/mac-verify.ts`, `scripts/win-verify.ts`) then require, for the app and for the app inside each update zip: macOS, the engine, Chrome's `.app` (also `--deep --strict`), its framework, every `Helpers/*.app` and other `Helpers/` file and every `.dylib` under `Libraries/` (found on disk at verify time, nothing hard-coded) to be a Developer ID Application signature with the hardened runtime, a secure timestamp and the app's Team ID and leaf certificate, with Chrome and the helper apps holding the entitlements; Windows, `agent-browser.exe` and every `.exe` and `.dll` under `browser-engine\chrome` to be `Valid`, timestamped and signed by the app's certificate thumbprint. A missing engine, Chrome `.app`, framework, Helper app or (on Windows) `chrome.exe` or DLL fails the check. All of this is checked against fixtures only (`scripts/mac-verify.test.ts`, `scripts/win-verify.test.ts`, `scripts/signing-kit.test.ts`, `scripts/local-signing.test.ts`); nothing has been signed or verified on a real bundle. Still unobserved: that `bun run smoke:desktop` passes on a signed app (it is what proves the host, engine and Chrome launch under the hardened runtime; a binary that crashes at launch only after signing is missing an entitlement), that osx-sign signs every file the check lists (it signs what `isbinaryfile` says is binary, which is broader than Mach-O), what electron-builder does with the engine's and Chrome's `.exe`/`.dll` files on a real Windows run (it only warns when signing one fails, so `verify` is what fails the release), and that signtool replaces rather than appends to `D3DCompiler_47.dll`'s Microsoft signature. A rejected notarization lists the offending files in `xcrun notarytool log <id>`.
- Every smoke refuses to start when a process already runs from the app bundle it would drive (the packaged app of a copy someone is using), and its final leftover sweep kills only pids it saw appear during its own run, never a process that was already there (`createSmokeRun`, `sweep` in `scripts/desktop-smoke-kit.ts`).

Connection profiles (`profiles.json` in the user-data folder; `connections.ts`, `profile-store.ts`): the built-in profile `local` is the sidecar and is never stored. A remote profile holds a name, an origin, the device id and the device token encrypted with `safeStorage`; it is refused when encryption is unavailable or, on Linux, the backend is `basic_text`, never stored in plaintext. A profile URL is a bare origin, `https:` except `http:` for loopback hosts, so a plain-HTTP private network (Tailscale with `--allow-plain-http`) is refused. The local profile is the supervisor's current sidecar, read at every use: when the host restarts, `localChanged()` signs in again with the new token and reloads if `local` is shown, and while the host is starting or stopped `local` shows DESK-03's starting and "host is not running" pages (a remote profile keeps working then). The tray and the application menu's Connections submenu share `connectionItems` (`connection-items.ts`); `setupConnections` (`desktop-connections.ts`) gives `main.ts` `list()`, `connect(id)`, `openConnections()`, `start()`, `localChanged()` and `onChange()`.

## Releasing

A release is a `v*` tag. Pushing one runs `.github/workflows/release.yml`: `verify` (the tag is `vMAJOR.MINOR.PATCH` or `vMAJOR.MINOR.PATCH-prerelease` and equals `v` + the host's `VERSION`), then `host` (a matrix that builds each of the five host binaries with `build:host <target>` on a native runner, runs `smoke:host` on it and uploads it as the artifact `release-host-<target>`; every target has a native runner, but `ubuntu-24.04-arm` is free for public repositories only), then `desktop` (a matrix on native runners, macOS, Windows and Linux: downloads the `release-host-*` artifacts for its OS, runs `package:desktop --host-dir hosts` with the version from `VERSION` and `GITHUB_REPOSITORY`, then `bun scripts/release.ts desktop` checks that the host inside every app, and inside the macOS update zip, is byte-identical to the host job's binary, that the update metadata names the release version and that every installer exists, copies exactly the installers, blockmaps and metadata out and uploads them as `release-desktop-<os>`; the macOS job packages arm64 and x64 together so there is a single `latest-mac.yml` and nothing for the artifact merge to collide on), then `publish` (the only job with `contents: write`: it merges every `release-*` artifact into one folder, writes `SHA256SUMS` over all of it with `scripts/release.ts checksums`, which fails unless all five host binaries and every supported installer and update metadata file are there, and creates the GitHub Release with `gh`, as a draft until every asset is uploaded; a tag with a pre-release suffix such as `-rc.1` makes a pre-release). A rerun of a failed publish replaces the assets of the Release that exists. Desktop installers join the same Release: a job that uploads artifacts named `release-*` and is added to `publish.needs` ends up in the Release and in `SHA256SUMS`.

The host's version is `VERSION` in `packages/host/src/harness/claude-access.ts` (no `package.json` carries a version). To cut a release:

1. Set `VERSION` to the version without the `v` (`0.2.0`, or `0.2.0-rc.1` for a pre-release; a pre-release suffix is part of `VERSION`), run `bun run check`, commit and merge to the default branch.
2. Tag that commit and push the tag: `git tag v0.2.0 && git push origin v0.2.0`.
3. Watch the `Release` run. A tag that does not match `VERSION` fails `verify` before anything is built; fix `VERSION` (or delete the tag), then tag again.
4. Check the Release: five `tomte-host-<os>-<arch>[.exe]` files, `install.sh` (its `DEFAULT_REPO` filled in with the repository), `tomte.service`, `release.json`, `SHA256SUMS` and `SHA256SUMS.sig`; `sha256sum --check SHA256SUMS` in the download folder passes. `deploy/install.sh` installs a release's Linux binary without `--url` (`--repo`, `--version`; see `deploy/README.md`), after checking the signature. The first release needs the owner's one-time key setup (`docs/release/signing.md`).

Check a published Release offline with `bun scripts/release.ts verify-release <folder> <version>` (`scripts/release-verify.ts`, tests in `scripts/release-verify.test.ts`), on the folder `gh release download v0.2.0-rc.1 -R OWNER/REPO -D <dir>` filled (version without the `v`, e.g. `0.2.0-rc.1`). It reads only; it exits 1 and lists every problem, or exits 0 and prints "a complete, consistent release". It checks that the folder holds exactly the published files and nothing else (the five host binaries, every `SUPPORTED_DESKTOP` installer, its `.blockmap` (the `.deb` has none), `latest-mac.yml`, `latest.yml`, `latest-linux.yml`, `install.sh`, `tomte.service`, `release.json`, `SHA256SUMS`, `SHA256SUMS.sig`); that `SHA256SUMS` lists exactly those files (its signature excepted), once each, and every sha256 matches; that `SHA256SUMS.sig` verifies against the public key pinned in this checkout's `deploy/install.sh`; that `release.json` is a manifest of the version; that `install.sh` has `DEFAULT_REPO="OWNER/REPO"` filled in and pins that same key; and that each `latest*.yml` names the version, lists the file the updater applies (the mac zips, the NSIS exe, the AppImage) and that every file it lists exists with the sha512 and size it states. It does not check the macOS or Windows code signatures (`signing.ts verify` does), that the host inside an installer is the release's (the workflow's `release.ts desktop` did), or that anything runs.

Run the two release steps locally with `bun scripts/release.ts tag v0.2.0` (prints `version=` and `prerelease=`; exits non-zero on a mismatch) `bun scripts/release.ts desktop <bundleDir> <hostDir> <outDir> <version> <arch>…` (the check and collection of one `package:desktop` run for this OS) and `bun scripts/release.ts checksums <folder> <version>` (the folder must hold the five binaries and every supported installer and metadata file); `scripts/release-kit.test.ts` and `scripts/desktop-kit.test.ts` cover the tag rules, the checksum format and the desktop host check.

Installers are released for macOS (arm64 and x64: dmg and zip), Windows x64 (NSIS) and Linux x64 (AppImage and deb); `SUPPORTED_DESKTOP` in `scripts/desktop-kit.ts` is the list and `publish` fails when any of its files is missing. linux-arm64 and Windows arm64 are host-only. Whether the macOS and Windows installers are signed depends on the signing secrets (next section); without them they are unsigned and unnotarized, macOS Gatekeeper and Windows SmartScreen warn on first launch, and macOS auto-update of an unsigned app is not expected to work. Linux packages are never signed. The Windows and Linux installers are built only by the workflow and have not been run anywhere yet. On Windows `smoke:host` terminates the host instead of sending SIGTERM and skips the graceful-exit and lock checks.

### Signed releases

Every release also publishes `release.json` (`{ version, shellApi, schemaVersion }`, the contract's `ReleaseManifest`: the host's `SHELL_API` range and database `SCHEMA_VERSION`), listed in `SHA256SUMS`, and `SHA256SUMS.sig`, the raw 64-byte Ed25519 signature of `SHA256SUMS` (ticket 10 of the client/host split, spec decisions 3 and 8). `publish` runs, after the installer step, `release.ts manifest release <version>`, `checksums`, `sign release` (the only step that sees the repository secret `RELEASE_SIGNING_KEY`, a PEM Ed25519 private key; it fails when the secret is missing or is not the pair of the pinned public key) and `verify-release`; `verify` runs `release.ts signing-ready` first, so a release without the secret or without a pinned key fails before anything is built. The public key is pinned in `deploy/install.sh` as `RELEASE_PUBLIC_KEY="<base64 of the 32 raw bytes>"` and nowhere else (no trust on first use); it is empty in the source tree until the owner generates the key pair and pins it, and while it is empty `install.sh` refuses to install from a release, `verify-release` refuses and the workflow fails. `install.sh`'s one routine `download_verified_release` (sourceable: `source install.sh` runs nothing else) checks the signature with `openssl pkeyutl -verify -rawin` (OpenSSL 3 or newer) and every file against the signed sums; the root update helper of ticket 12 reuses it. The owner's one-time key generation, secret and pin steps, the file formats and key rotation are in `docs/release/signing.md`. Tests use a throwaway key from `scripts/release-test-kit.ts`: `scripts/release-kit.test.ts`, `scripts/release-verify.test.ts` and `scripts/install-verify.test.ts` (the bash routine, sourced).

### Signing and notarization

Signing needs credentials only a person can create, so the release signs when the repository has them and stays unsigned when it has not. Nothing about it can be exercised locally (no workflow or script here ever signs on a developer machine: `bun scripts/signing.ts sign-host` refuses to run outside GitHub Actions, and `package:desktop` signs only with `--sign`, below).

The one local exception is an explicit opt-in route for a personal test build: `bun scripts/sign-local.ts plan|run|cleanup` (`bun run sign:local`; guide `docs/release/local-signing.md`) signs and notarizes an arm64 DMG, update zip and host on this Mac from a `.p12` and an App Store Connect key named in `TOMTE_LOCAL_*` environment variables, in a temporary keychain inside `--out`. `plan` prints every operation and runs nothing; `run` refuses in CI and without `--confirm-keychain-and-notary-upload`. It reaches `package-desktop.ts` through `--sign --local-keychain <file> --local-identity <sha1>`, which is mutually exclusive with the CI path (`CSC_LINK`); the CI workflow, `signing.ts` and its checks behave as described below (the macOS checks now live in `scripts/mac-verify.ts`, shared by both). It has been tested against fakes only; nothing in it has run against a real keychain or Apple's notary service.

The local route has two notary backends, exactly one per run: an API key (`TOMTE_LOCAL_API_KEY_*`, `notarytool`) or a saved profile of the Rork ASC CLI (`TOMTE_LOCAL_ASC_PROFILE`, optionally `TOMTE_LOCAL_ASC_BIN`; `scripts/asc-notary.ts`). With `asc` the packaging run is given `--local-notary asc --local-asc-profile <name> --local-asc-bin <path> --local-notary-record <file>`, electron-builder's own notarization is off (`notarize: false`) and an `afterSign` hook zips the signed app, runs `asc --profile <name> notarization submit --file <zip> --wait --output json`, staples with `xcrun stapler` and writes the submission to the record file; the route submits the DMG the same way. Both backends write `<out>/artifacts/NOTARIZATION.json` (submission ids, statuses, sha256). The CI route is unchanged. The asc output shape and exit codes are unobserved.

What the workflow does when a platform's secrets are all set (`scripts/signing.ts`, the decisions and checks in `scripts/signing-kit.ts`, covered by `scripts/signing-kit.test.ts` with fixtures and no certificates):

1. `verify` runs `signing.ts plan` with only whether each secret is set (never a value) and outputs `sign_mac` and `sign_windows`; the job summary lists each platform as signed or UNSIGNED.
2. `host` (macOS and Windows legs) runs `signing.ts sign-host` on the binary it just built, before `smoke:host`, so the smoke run starts the signed binary under the hardened runtime and the Release publishes it. macOS: a temporary keychain holds the certificate, `codesign --options runtime --timestamp --entitlements scripts/entitlements.mac.plist` signs with the Developer ID Application identity (it fails unless the certificate holds exactly one), and the keychain is deleted. Windows: `Set-AuthenticodeSignature` (SHA-256, timestamped by `http://timestamp.digicert.com`), chosen over `signtool` because it ships on every Windows image and needs no Windows SDK path.
3. `desktop` runs `package:desktop --sign`. electron-builder imports the same certificate into a keychain of its own (`CSC_LINK`), signs the app and its helpers with the hardened runtime and `scripts/entitlements.mac.plist`, notarizes with `notarytool` (App Store Connect API key) and staples the ticket, then builds the dmg and the update zip from the stapled app. It leaves the bundled host alone (`mac.signIgnore`, and `!tomte-host.exe` in `SIGNED_WIN.signExts` on Windows) because the host arrives already signed with the same certificate, and a second signature would break the byte-identity `release.ts desktop` checks. On Windows it signs the app, the uninstaller and the NSIS installer with the same PFX (`WIN_CSC_LINK`), and `SIGNED_WIN.signExts` in `signing-kit.ts` is `[".dll", "!tomte-host.exe"]`: electron-builder signs `.exe` by default and a positive `.dll` adds the libraries, which includes Chrome's; never add a positive `.exe` pattern, a positive match beats the `!` and the host would be re-signed. The same `.dll` also signs Electron's own top-level DLLs and anything in `app.asar.unpacked`, and cannot spare `D3DCompiler_47.dll`, which ends up with our signature in place of Microsoft's.
4. `Verify signing` (only when signed) runs `signing.ts verify` on the runner: macOS, for every arch's unpacked app and for the app inside its update zip: `codesign --verify --deep --strict`, `spctl --assess --type execute`, `xcrun stapler validate`, and the app's and the host's `codesign -dvv` must both be a Developer ID Application signature with the hardened runtime and a secure timestamp, the same leaf certificate and the same Team ID, with the host holding the entitlements, plus the browser parts listed under Desktop app above; Windows: `Get-AuthenticodeSignature` on the installer, the app exe, the host exe, `agent-browser.exe` and every `.exe` and `.dll` under `browser-engine\chrome` must all be `Valid`, timestamped and carry one certificate thumbprint. `release.ts desktop` then still checks that the host in every app is byte-identical to the one the host job uploaded.

`scripts/entitlements.mac.plist` grants `com.apple.security.cs.allow-jit`, `allow-unsigned-executable-memory` and `disable-library-validation` and nothing else; it is the one file for the Electron app, its helpers, Chrome and the Bun-compiled host (V8 and JavaScriptCore both JIT). `disable-library-validation` is there for Chrome: the pinned zip carries a Google-signed `libwidevinecdm.dylib` (and Chrome's component updater may fetch newer Google-signed CDMs), which a Chrome re-signed under our Team ID cannot load with library validation on; Chromium's own plugin-helper entitlements grant the same pair (`@electron/osx-sign`'s `default.darwin.plugin.plist`). electron-builder gives the one `entitlements` file to the main app and `entitlementsInherit` to everything else, so the host and Electron's helpers get it too, though the host does not need it. `MAC_ENTITLEMENT_KEYS` in `signing-kit.ts` is the list `signing.ts verify` requires on the host, Chrome and every helper app, so the plist and the check move together. If a signed binary needs more, the host job's smoke run (which runs the signed host) or the macOS smoke fails; add the entitlement there and to `MAC_ENTITLEMENT_KEYS`.

Secrets (repository secrets; each platform's set is all-or-nothing, and a partly set platform always fails the release):

| Secret                         | Content                                                                                                           |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `MACOS_CERTIFICATE_P12`        | base64 of the Developer ID Application certificate with its private key, as a `.p12` holding exactly one identity |
| `MACOS_CERTIFICATE_PASSWORD`   | the `.p12`'s password                                                                                             |
| `APPLE_API_KEY_P8`             | the text of the App Store Connect API key (`AuthKey_<id>.p8`) used by `notarytool`                                |
| `APPLE_API_KEY_ID`             | that key's Key ID                                                                                                 |
| `APPLE_API_ISSUER`             | the issuer ID shown above the team keys list                                                                      |
| `WINDOWS_CERTIFICATE_PFX`      | base64 of the code signing certificate with its private key, as a `.pfx`                                          |
| `WINDOWS_CERTIFICATE_PASSWORD` | the `.pfx`'s password                                                                                             |

Secrets reach only the steps that need them, as environment variables of that step (`verify` gets only "set" or empty; the macOS and Windows host steps and the `Package` step get their own OS's), and no script prints a value or puts one on a command line it logs (`security import -P` does take the `.p12` password as an argument on the runner).

Fail closed: set the repository **variable** (not a secret) `TOMTE_REQUIRE_SIGNING` to `true` (`gh variable set TOMTE_REQUIRE_SIGNING --body true`). Then a release whose macOS or Windows secrets are missing fails in `verify`, before anything is built, and `package:desktop` itself refuses to run unsigned for macOS and Windows. Without the variable, a platform with no secrets is built unsigned as before and the job summary says UNSIGNED. A platform with some but not all secrets fails either way.

`bun run package:desktop --sign` is the same code path the workflow takes, for a person who really has the credentials in the environment (the secret names above, as environment variables); without `--sign` the credentials in the environment are ignored and removed. It exits non-zero before building when any secret of this OS is missing, and Linux ignores it.

What a person has to do once (this is the part of ticket 06 no script can do):

1. macOS, with a paid Apple Developer Program membership: create a **Developer ID Application** certificate (developer.apple.com, Certificates; only the Account Holder can; or Xcode, Settings, Accounts, Manage Certificates). In Keychain Access export the certificate together with its private key as a `.p12` with a strong password. Create an App Store Connect **team API key** (Users and Access, Integrations, Team Keys) with at least the Developer role, download the `.p8` (Apple shows it once), and note the Key ID and the Issuer ID.
2. Windows: obtain a code signing certificate (OV or EV) from a certificate authority and export it with its private key as a `.pfx`. Caveat: since June 2023 the CA/Browser Forum requires the private keys of newly issued code signing certificates to live on a hardware token or an HSM, so a new certificate usually cannot be exported to a `.pfx`; if yours cannot, this PFX path does not apply and `signHostWindows` in `scripts/signing.ts` and `SIGNED_WIN` in `scripts/package-desktop.ts` must change to your CA's cloud signing or Azure Trusted Signing before the Windows secrets mean anything. Decide that before buying the certificate.
3. Store them as repository secrets under the names above, for example `base64 -i certificate.p12 | gh secret set MACOS_CERTIFICATE_P12`, `gh secret set MACOS_CERTIFICATE_PASSWORD`, `gh secret set APPLE_API_KEY_P8 < AuthKey_XXXXXXXXXX.p8`, `gh secret set APPLE_API_KEY_ID`, `gh secret set APPLE_API_ISSUER`, `base64 -i certificate.pfx | gh secret set WINDOWS_CERTIFICATE_PFX`, `gh secret set WINDOWS_CERTIFICATE_PASSWORD`. Then delete the exported files.
4. Cut a pre-release (`v0.2.0-rc.1`, see above) and read the `verify` job summary: it must say macOS and Windows are signed. Once a signed release has passed, set `TOMTE_REQUIRE_SIGNING` to `true`.
5. Check the result the way a user meets it. macOS: download the `.dmg` in a browser on a Mac that has never seen the app (that sets the quarantine flag), open it and launch the app: no "cannot verify the developer" dialog. In a terminal, on the installed app: `spctl --assess --type execute --verbose=4 /Applications/Tomte.app` prints `accepted` and `source=Notarized Developer ID`, `xcrun stapler validate /Applications/Tomte.app` prints `The validate action worked!`, and `codesign -dvv /Applications/Tomte.app` and `codesign -dvv /Applications/Tomte.app/Contents/Resources/tomte-host` show the same `TeamIdentifier`. Windows: download `Tomte-Setup-<version>.exe` in Edge on a machine that has never seen it and run it: no "Windows protected your PC" block (an OV certificate may still warn until the file has reputation; that is not a signing failure), and `Get-AuthenticodeSignature .\Tomte-Setup-<version>.exe | Format-List` shows `Status : Valid` and the publisher; Properties, Digital Signatures on the installed `Tomte.exe` and `resources\tomte-host.exe` shows the same signer.
6. Whether the keychain items a bot created survive an update (the host's signature is what macOS ties them to) is the update check of ticket 07.

## Update helper

A remote host replaces its own binary through a root helper while the service user can only ask (ADR-0014, spec `.scratch/client-host-split/spec.md` decision 3). The service user writes `<dataRoot>/updates/request.json` (`UpdateRequest` in `@tomte/contract/update`: `{kind: "apply", id, version}` or `{kind: "rollback", id, restoreSnapshot?: true}`, strict, a version never a URL or path, `restoreSnapshot` only ever the literal `true`) and reads `result.json` (`UpdateResult`: `updated`, `unchanged`, `rolled-back` with `snapshotRestored`, `refused`, `reverted` with the reason, `rolledBackTo` and `snapshotRestored`, `failed`; every one carries `running` and `previous`, the `{version, schemaVersion}` of the installed and the kept binary, as their own `version` subcommand reports them); `snapshotName(version)` is `pre-<version>.db` in the same folder. `tomte-update.path` (`PathExists` on the request) starts `tomte-update.service`, a root oneshot running `tomte-host apply-update`.

- Code: `packages/host/src/update-helper/` (public `index.ts`: `applyUpdate({ uid, rootUid?, confPath?, deps? })`). It imports only `platform/` and the contract (dependency-cruiser rule `update-helper-runs-as-root`). `conf.ts` parses `/etc/tomte/update.conf` (`KEY=value`: `REPO`, `PUBLIC_KEY`, `DATA_ROOT`, `SERVICE`, `SERVICE_USER`, `BIN`, `ENV_FILE`, `RELEASE_BASE_URL`, optional `STATE_DIR`) and builds the loopback host-info URL from the service's env file; `verify.ts` is `install.sh`'s `download_verified_release` in WebCrypto (signature of `SHA256SUMS`, then every file against it, `release.json` must name the version); `apply.ts` is the `Updater` (journal, lock, swap, health gate, rollback) behind the `Deps` seam (`systemd`, `service` user, `download`, `versionOf`, `hostVersion`, `sleep`, `now`, `journaled` for crash injection); `system.ts` is the real `Deps` (`systemctl`, `runuser`, `fetch`, `<binary> version`).
- Inputs: the request and `update.conf` only. It refuses to run unless the uid is root and the conf is a regular file owned by root that no one else can write; `request.json` is opened with `O_NOFOLLOW`, read up to 4 KiB and deleted, and a request id is handled once (`last-request` in the helper's state directory, `/var/lib/tomte-update`, which also holds the lock, the step journal `journal.json` and the staging folder). Files in the service user's directories (the result, the restored database) are written as that user through `runuser`.
- Order: verify, check the downloaded binary reports the version and schema named, copy the current binary to `tomte-host.prev`, rename the new one over `tomte-host`, restart, health gate (7 stable seconds of `is-active` plus host-info on the target version, within 90 s), else roll back (snapshot restored when `updates/pre-<version>.db` exists, `.prev` back, same gate). The journal steps are `requested`, `saving-previous`, `swapping`, `restarting`, `rolling-back`, `finished`; the next run finishes a dead run's step before it reads a new request. A release with an older schema than the installed binary's is refused, and so is a rollback to a binary that cannot open the database.
- `conf.ts` is `platform/update-conf.ts` (`parseUpdateConf`, `hostInfoUrl`, `DEFAULT_CONF_PATH`), shared with `upkeep`, so the helper's own folder keeps only what runs as root.
- `install.sh` writes `update.conf` (the pinned `RELEASE_PUBLIC_KEY` from its own constant, the repository from `--repo`) and the two units only for a release install (`--url` installs get none: updates are "unmanaged"); it enables the path unit only when the installed binary answers `version`. The host side that acts (`Upkeep.run`, `RunGate`, the snapshot, the request, the result) is "Updating from the UI" below; what the host reports of its own update is "Update status".

### Update status

`HostStatus.update` (`UpdateStatus`, `@tomte/contract/host-status`) comes from `Upkeep` (`packages/host/src/upkeep/`, public `index.ts`: `createUpkeep`; `feed.ts` private; it imports only `platform/` and the contract, rule `upkeep-imports-platform-and-contract`). `bundled`: the sidecar (`--sidecar`), which never asks the feed. `unmanaged` with a reason: no readable, valid `update.conf` (default `/etc/tomte/update.conf`, world-readable, root-owned) for this host's data root, read again at every check so an install after start is noticed. Otherwise the feed is asked on start and every 6 h (`HostServerOptions.upkeep`: `confPath`, `checkEveryMs`, `fetch`, for tests): `GET {RELEASE_BASE_URL}/{REPO}/releases/latest/download/release.json` (GitHub redirects it to the latest stable release's asset; a pre-release never appears as `latest`, so a pre-release host is told nothing until a stable release is newer), parsed as `ReleaseManifest` with its version checked as a `ReleaseVersion`. The manifest is informational only: it is not signed, and the helper verifies the signed sums before installing anything. `current` (`checkedAt`, 0 until the feed has answered) or `available` (`version`, `notesUrl` = `{base}/{repo}/releases/tag/v{version}`, `raisesShellApi`: the release's shell API minimum or maximum is above this host's). An unreachable feed or a bad answer changes nothing and is logged (`[upkeep]`). `onChange` fires on any change, a later `checkedAt` included, and the composition root broadcasts the `host-status` event. About's Updates card (`features/settings/updates.tsx`, text in `update-line.ts`) shows it and offers the actions in "Updating from the UI". Tests: `upkeep/index.test.ts` (against `testing/fake-release-feed.ts`, a release directory served like GitHub's), `host-server/upkeep.test.ts` (whole host and event stream), `features/settings/update-line.test.ts`.

### Updating from the UI

`Upkeep.run(action)` (`UpdateAction`, `@tomte/contract/update`; `POST /api/updates/run`, `host-server/api/updates.ts`, which answers the `UpdateStatus` it leaves and 409 with the reason when the action does not apply: `UpdateRefused`) is the one entry point: `check`; `apply` with `when: "idle"` or `"now"` (always the version the status offers; from `failed` it retries that version; `now` also ends a drain of either kind early); `rollback` `{when, restoreSnapshot}` (see "Manual rollback"); `cancel`; `auto` `{enabled}`. Decisions 4 and 5 of `.scratch/client-host-split/spec.md` and ADR-0014 are the contract.

- Idle: `RunGate` (`upkeep/run-gate.ts`, `createRunGate`, interface in the same file, re-exported by `upkeep/index.ts`) is closed first. `active()` is `Chats.active()`: chats with a turn, a queued message, a double-loop front's presence or a task running or queued, plus `RoutineTurns.pending()` (headless runs and routine turns waiting for their bot). Work accepted before the close finishes (messages already queued behind a turn still run); nothing new starts, whichever way it arrives: `Chats.send` answers `refused` with `UPDATING` (`"Updating, back in a minute"`, `@tomte/contract/update`; `/api/send` turns it into 409, a phone message gets it as text; an answer to a question a turn waits on is still `answered`, since it ends work) and `routines.testRun` throws `Conflict(UPDATING)`. A host delivery (`Chats.deliver`: external events, handoff messages, wait and browser notices) is held in memory while the gate is closed and starts no turn; `Chats.releaseHeld()` delivers it when the gate reopens, and a process that is replaced first loses it (events stay open items, `handoffs.redeliverOpen()` redelivers handoffs at start). An answer that would resume a parked routine run (`routines.waitClosed`) leaves the run `waiting` with its answers stored and undelivered; `resumeAnswered()` (part of `routines.catchUp()` and of `start()`) resumes it when the gate reopens or the host starts. A scheduled routine's `fire` returns without claiming the occurrence, so it follows `catchUp` after a restart, or when the gate reopens: `RunGate.open()` calls `routines.catchUp()` (the due-occurrence half of `reconcile`). The gate counts by polling (`pollMs`, a second) while closed, not by hooks at every place work ends, so a missed hook cannot leave a drain waiting for ever; `onChange` reports each new count. `UpdateStatus` is `draining` (`version`, `running`, `since`, `overdue`) until the count is zero, `overdue` flips once after 30 minutes (`drainOverdueMs`) and the drain stays `draining`: the About card then offers Update now.
- Request: at zero (at once for `now`, which interrupts: a running routine's row is left `running`, so the next start reports it as interrupted and never runs it again) the status is `applying` and Upkeep takes the snapshot (`snapshotDatabase(db, <dataRoot>/updates/pre-<version>.db)`: `VACUUM INTO` a `.partial` file, mode 0600, renamed) and deletes every older `pre-*.db`, so only the latest snapshot is kept, writes the pending request id and version to `updates/upkeep.json` and then `updates/request.json` (`upkeep/requests.ts`, `createUpdateRequests`: every file written whole through a rename), and polls `result.json` (`resultPollMs`, a second) for that request id for at most 10 minutes (`applyTimeoutMs`). The gate stays closed through `applying`. A snapshot or request write that throws fails the update before any request exists.
- Result: `unchanged` clears the pending id, reopens the gate and goes `current` (then a feed check); `updated` and `rolled-back` mean the helper is replacing this process, so the process that wrote the request keeps waiting with the gate closed (nothing new starts in the time left) and the process that starts after it reads the result in `start()` and goes `current`; `reverted`, `refused` and `failed` (and the 10-minute timeout) are `failed` (`version`, `reason`, `rolledBackTo`), reopen the gate and keep the pending id, so the new process the helper brings back after a rollback reads the same failure in `start()` and shows it again after any restart, until `cancel` acknowledges it or a new apply replaces it. A feed check never replaces `draining`, `applying` or `failed`. A process that starts with a pending id and no matching result is `applying` with the gate closed until the helper answers (the helper writes the result after its health gate, so the new host is up first).
- Problem: `problemsOf(claude, update)` adds `update-failed` (`version`, `rolledBackTo`) while the status is `failed`; `updateFailedText` (contract) is its one wording ("Update to 0.4.2 failed, rolled back to 0.4.1"), used by the web banner (`app/host-problems.tsx`, "Details" to Settings, About), the tray line and the one `host_problem` channel message (`host-alerts.ts` also syncs on `upkeep.onChange`; the link goes to `/settings/about`).
- Auto-update: `auto {enabled}` is kept in `updates/upkeep.json` (`autoUpdate`, off by default) and is `HostStatus.autoUpdate` (default false when a host omits it). With it on, a feed check that finds an update (and turning it on while one is on offer) applies it when idle. It is refused on the sidecar and an unmanaged host; `onChange` fires when the setting changes, so every page sees it.
- Web: `features/settings/updates.tsx` (`UpdatesCard`: Check for updates; Update when idle and Update now, the latter behind a confirm that says running work stops; Cancel while draining and Update now once `overdue`; Try again when idle and Dismiss after a failure; the automatic-update switch).
- Tests: `upkeep/index.test.ts` (a fake helper writes `result.json` into a temp data root: idle drain then apply, cancel, overdue, now, results, restart recovery, timeout, snapshot failure, auto), `upkeep/run-gate.test.ts`, `platform/db.test.ts` (snapshot), the gate tests of `routines/index.test.ts`, `host-server/update-from-ui.test.ts` (whole host: refusals while draining, the request after the turn, a reverted result told once on the fake Bot API, cancel, now, auto), `host-server/host-alerts.test.ts`, `features/settings/update-line.test.ts`.
- Only the latest snapshot `pre-<version>.db` is kept.

### Manual rollback

About offers the one earlier binary the helper still keeps (`tomte-host.prev`), through the same drain and helper as an update (ticket 14, decision 4).

- Offer: `Upkeep.rollbackOffer()` is composed into `HostStatus` by `createHostStatus` as `rollbackTo` (the earlier version opens the current database) or `restoreTo` `{version, snapshotAt}` (it cannot, and the pre-update snapshot exists); never both, and neither while an update or rollback is draining, applying or failed, on the sidecar or an unmanaged host, or when the helper's last result (`result.json`) is about another version than this host's. The schema comparison comes from that result's `running` and `previous`, which the helper reads from the binaries themselves (`<binary> version`), the same source it judges a rollback by; `release.json` is not used, because it is the feed's unsigned answer and the host has no copy of the previous release. `previous.schemaVersion === running.schemaVersion` is `rollbackTo`; older is `restoreTo` (when `updates/pre-<running version>.db` is a regular file; `snapshotAt` is its mtime); newer is never offered.
- Action: `{op: "rollback", when: "idle" | "now", restoreSnapshot}`. `restoreSnapshot` must be true exactly when the status offers `restoreTo`: a restore asked for without it, a restore nobody needs, or anything while an update is under way is a 409 (`UpdateRefused`) that writes nothing and leaves the gate open. A rollback takes no new snapshot (it would delete the one a restore needs), leaves the automatic-update setting alone (the release it leaves is skipped instead, see "Skipping the release that was rolled back"), and the request carries `restoreSnapshot: true` only for the confirmed restore. `draining`, `applying` and `failed` carry `rollback: true`; a failed rollback (a `refused` or `failed` result, or no result in 10 minutes) is only dismissed, and its banner reads "Rollback to 0.4.1 failed" (`updateFailedText`).
- Helper: a rollback is refused (nothing touched) when no `.prev` exists, it does not run, its schema is older than the database's and the request does not confirm, or the request confirms and the schema is not older (a restore would only lose changes) or `pre-<installed version>.db` is not a regular file. The snapshot is chosen by the helper from its own layout (`snapshotName` of the installed version, written into the journal as a file name), never named by the request; a crash after `rolling-back` restores again. The old binary is never started on a newer database: ticket 04's `DatabaseTooNew` refuses it, and the helper's health gate would report it.
- Web: `features/settings/updates.tsx` shows "Roll back to <version>" (a confirm; keeps data) or "Restore <version> and its database…" (its own destructive confirm and an always-visible note, `restoreWarning` in `update-line.ts`: the snapshot's date and that every change since is lost). Both only while the update status is `current` or `available`.
- Skipping the release that was rolled back (ticket 21, owner decision chs-14-q1): when a rollback's result is `rolled-back`, the process the helper starts keeps the result's `from` (a `ReleaseVersion`, nothing else) as `skipped` in `updates/upkeep.json` (the service user's file, beside `autoUpdate` and `pending`; `setPending` and `setSkipped` each rewrite the whole state so neither drops the other). `statusFor(..., skipped)` reports the feed's newest release, when it is exactly the skipped one, as `current` with `skipped: {version, notesUrl, raisesShellApi}` instead of `available`, so no offer and no automatic apply (`applyAvailable` only acts on `available`); `autoUpdate` is untouched. A check forgets the skip when the feed names a release newer than it, or when this host runs it again. `apply` on a `current` status with `skipped` installs that release (the explicit install; a failed one keeps the skip, a successful one ends it); a `refused`, `failed` or `reverted` rollback skips nothing. Web: the Updates card's line says the version is skipped because it was rolled back, and "Install <version> anyway" (the same `apply` when idle) sits beside the rollback button. Tests: `upkeep/index.test.ts` ("skipping the release that was rolled back"), `features/settings/update-line.test.ts`.
- Tests: `upkeep/index.test.ts` ("rolling back"), `update-helper/apply.test.ts` (a confirmed restore, refusals, a crash after `rolling-back`), `host-server/update-from-ui.test.ts` (whole host: offers, an unconfirmed restore writes nothing), `features/settings/update-line.test.ts`. `scripts/smoke-update-helper.sh` has the rollback paths (not run: it needs a VM, root and OrbStack).
