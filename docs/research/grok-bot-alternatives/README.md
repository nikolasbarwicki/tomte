## 0. TL;DR

1. **The category is converging on one shape**: a long-lived "computer" (container, VM or a user's Mac) that runs the agent's tools, a control plane that owns schedules, secrets and approvals, and the user's own Claude or ChatGPT subscription as the model. Seven of nine run the vendor CLI (`claude`, `codex`) on that computer as the brain, or can.
2. **Laptop-off is solved the same way everywhere**: move the always-on part to a server or vendor cloud box. Three variants: a Postgres/Redis scheduler on a server (Rakazo, agentes.chat, Nuphos), an in-process timer on the box plus a vendor cron that wakes a sleeping box (OpenBot, MausBot), or a vendor cloud scheduler (Reason). Turnstone is the only one that can't, until its Cloud ships.
3. **Subscription use in the cloud is a device-code login performed on the cloud machine**, then the CLI refreshes its own token. No project documents or tests OpenAI ToS risk for this. Only OpenBot (`docs/provider-terms.md`) and Rakazo (docs discourage Claude OAuth) rate Anthropic ToS risk, and agentes.chat has an ADR warning against rotating subscriptions.
4. **Secret handling is the biggest spread.** Only Rakazo (brokered by default) and Reason (opt-in brokered mode) keep secrets from the agent's shell. Everyone else exposes secrets as env vars or files the agent can read, and several store them in plaintext (Rerun, OpenBot agent keys, MausBot CLI-entered keys).
5. **Isolation is mostly weak.** Per-agent OS users exist only in agentes.chat `--system` mode. Per-workspace containers are the norm. OpenBot, Nuphos shared Boxes, Rakazo Team computers, MausBot desktop and the agentes.chat default share one OS user across agents.
6. **Scheduler quality varies widely.** Best-specified: Rakazo (Postgres lease and fence, coalesced catch-up flagged late) and agentes.chat (outbox with retry, 12 h missed rule, auto-pause after 5 failures). Weakest: Rerun (at-most-once, silent skip) and Nuphos (missed run notified but never re-run, no retry found).
7. **Nobody has documented an end-to-end scheduled run on a ChatGPT subscription.** Every "yes" in Part 11 is built from documented pieces plus the absence of anything that blocks it.
8. **Licenses split the field**: permissive (Rakazo and MausBot Apache-2.0, Nuphos Apache-2.0 per its notes), copyleft (agentes.chat AGPL-3.0-only, Rerun AGPL-3.0), source-available noncommercial (OpenBot, PolyForm Noncommercial), closed (Reason's agent, Turnstone).
9. **Pricing converges on $15-$50 for a hosted box, with models never resold** (BYO subscription or key). Rakazo, MausBot and Nuphos tiers are $15/$49/$99, $15/$49/$99 and $20/$50/$100. Rerun and Reason are higher per seat and sell credits.

Observations:

- **Grok Bot is the reference product.** Importers exist: agentes.chat imports from Grok Bot, ChatGPT dots, OpenBot, OpenMausBot, Hermes Agent, OpenClaw and Paperclip. Turnstone has an MCP server and a x.ai link import to recreate Grok Bots. Nuphos ships a `grok-bot-export` skill. Reason's Network messages Grok Bot routines. Migration tooling is a competitive feature in this segment.
- **Three tiers of audience**: personal (Rakazo, MausBot, OpenBot, Turnstone), SMB ops (Rerun, agentes.chat), engineering teams (Nuphos, Reason).
- **Only agentes.chat treats multi-user chat as the primary interface.** Everyone else is a single-player assistant with optional team sharing, or Slack as one channel among several.

**Design axis 1: loop on the server vs loop on the box.**

- _Loop on the server, box as tool target_ (Rakazo; agentes.chat with an API key; Reason `[INFERENCE]`): the control plane sees every tool call, so budget, approval, redaction and audit are enforceable centrally and the box can be thrown away. Subscription use is harder because the vendor CLI is the thing that holds the subscription login.
- _Loop on the box, CLI is the brain_ (MausBot, OpenBot, Nuphos, Rerun with CLI providers, agentes.chat with a plan): subscription use is natural and cheap, but the control plane only interposes where tools are exposed (MCP bridge). Secrets and approvals depend on CLI permission modes.
- agentes.chat supports both and states the trade-off: "The executor on the machine is the brain. Our side is the interface and the guard" (ADR 0029).

**Design axis 2: where state lives.** Postgres (Rakazo, agentes.chat), SQLite (OpenBot, MausBot, Rerun engine), MongoDB (Nuphos), JSON files (MausBot `routines.json`), plain files on the Mac (Turnstone). Tooling that already needs Postgres (queue, lease, vector memory) gets a coherent story from it: Rakazo and agentes.chat run queue and scheduler on it with no Redis.

### 4.2 Cross-product facts

- **Cloud ChatGPT = device-code login performed on the cloud machine.** Applies to Nuphos, MausBot, OpenBot, agentes.chat, Rerun and Rakazo hosted. After that the CLI (or server code in Rakazo) refreshes the token itself. Model calls then originate from a datacenter IP. **No project documents or tests OpenAI ToS or IP risk for this.**
- **Refresh failure is unattended-run failure.** agentes.chat is the most explicit: the Codex access token lasts 10 days, refresh after 8 (`CODEX_REFRESH_AFTER_MS`, `accounts.ts:451-452`), and the runner serializes CLIs on one sign-in because "two processes on one sign-in race on its refresh token" (`accounts.ts:380`). A refused sign-in fails the turn with `not_logged_in`. Any product that copies `auth.json` per turn (agentes.chat) or runs several CLIs on one login risks the same race.
- **A separate device login for the cloud box, not a copy of the laptop's `~/.codex`,** avoids clashing with the laptop's refresh token `[INFERENCE, agentes.chat]`. Plan limits stay shared with daytime use.
- **Fallback policy differs and matters at 3 am.**
  - Rakazo: per-bot and per-routine fallback chain.
  - MausBot: moves to a backup AI on a plan limit; waits out Claude usage-limit resets (≤12 h).
  - OpenBot: up to 8 backups; `limitPolicy` `wait` or `skip`.
  - agentes.chat: waits or uses a model fallback if an API key exists; never switches subscription accounts; background runs never fall back to the API brain.
  - Reason: falls back to other accounts or credits. This can spend credits unexpectedly.
  - Nuphos: no fallback found.
  - Rerun: marks the credential rejected.
- **Anthropic ToS is the sharp edge.** Rakazo ships the OAuth code and discourages it. OpenBot rates risk by mode. agentes.chat avoids storing claude.ai credentials server-side by design. Rerun mirrors the client ID with no warning. This is the part of the category most likely to change on a vendor policy update.

### 7.2 What this shows

- **Brokering vs exposure.** Only Rakazo (default) and Reason (opt-in) keep a secret from the agent's shell. agentes.chat is the most thorough at limiting damage (E2E request, redaction, URL scanning) but openly says it reduces rather than prevents. Everyone else is "hand the agent the secret".
- **Key management.** KMS appears in agentes.chat Cloud (private module), Rakazo (optional), and Nuphos (for signing only). Env-var master keys are the norm in self-host.
- **Plaintext at rest** is a real finding in three products: Rerun (all secrets), OpenBot (agent API keys), MausBot (CLI-entered keys and MCP headers).
- **Subscription tokens are the worst-protected secret in every CLI-on-box product** because they sit as `auth.json` or `.credentials.json` in a directory the agent can read. agentes.chat is the only one using a file descriptor to keep the Claude token away from child commands.
- **Vendor visibility** is not equal. MausBot Cloud, Nuphos Cloud, Rerun Cloud and Turnstone Cloud can all read credentials or transcripts in some form. Turnstone says so explicitly ("Turnstone's service can decrypt them").
- **Telemetry**: agentes.chat telemetry is on by default (`TELEMETRY=off` disables; sends daily anonymous counts to telemetry.agentes.chat via Cloudflare). Reason sends traces to PostHog (session replay), Axiom, Sentry. Nuphos sends traces to Braintrust and conversation data to model providers.

### 8.2 Observations

- **Runs while away need explicit design decisions**: missed-run policy, retry, overlap, and approval behaviour. Rakazo, agentes.chat and MausBot decided all four explicitly. Rerun and Nuphos left gaps.

- **Scheduler failure mode of compose self-host**: Nuphos's `docker compose` path has no Redis, so cron triggers never start; only Helm or hosted works.

Patterns:

- **Hosted-box pricing clusters at $15 to $50 entry and $49 to $100 mid.** Metering is hours of compute (Rakazo, MausBot), vCPUs (Nuphos), seats or people (agentes.chat, Reason), or credits (Rerun, Reason, Turnstone).
- **Models are not resold by the open-source cohort** (MausBot, OpenBot, Nuphos, agentes.chat); Rakazo sells credits at cost; Rerun, Reason and Turnstone sell credits.
- **Monetization levers in open repos**: hosted convenience (all), Cloud-only integrations (Rerun, Linkup/Treg), enterprise features (Rakazo SSO/SCIM/audit; MausBot `enterprise/` folder), a work license (OpenBot), template marketplace (Rerun).
- **License as a moat**: AGPL (agentes.chat, Rerun) discourages competing hosted forks; PolyForm Noncommercial (OpenBot) forbids commercial use outright. Apache-2.0 (Rakazo, MausBot, Nuphos) permits competitors, with trademark protection at Nuphos and agentes.chat.

### 12.4 Limits worth knowing

## 13. Scenario: nightly scrape to CSV on a ChatGPT subscription, laptop off

The test case: every night at 03:00, log into a site, scrape a table, write a CSV, and have it ready in the morning, using the user's ChatGPT plan with the laptop closed.

### 13.1 Verdicts

| Product            | Hosted plan                                 | Self-host on a VPS                                                                     | Key caveats                                                                                                                                                                |
| ------------------ | ------------------------------------------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Rakazo             | **Yes** (Standard $15/mo)                   | Yes                                                                                    | Needs Auto or Always-allow approvals. A failed run gets one retry and the owner is notified. Nightly cost is probably 1-3 h/month of the 25 h `[my estimate]`              |
| MausBot Cloud      | **Yes**, with caveats                       | Yes                                                                                    | The free desktop app alone: no. Default Full access means nothing waits for approval. Single auto-retry. Moves to a backup AI on a plan limit                              |

A Worker cron wakes the server; a failed wake means a missed run. Full access by default                                             |
| Nuphos Cloud       | Yes (not shown in docs)                     | **Partly**: Helm + Redis works; Compose has no Redis, so cron never fires              | $20/mo flat. No retry  |

**No project documents or tests a scheduled run on a ChatGPT subscription end to end.** Every "yes" is built from documented pieces plus the absence of code that blocks it. agentes.chat is the closest: ADR 0053 says a routine "thinks with its agent's own brain (Claude Code, Codex or the API), never forced onto the API".

### 13.2 Common failure modes

1. **CAPTCHA, 2FA or bot wall** on the target site. No product solves captchas; a human has to be present or the run fails.
2. **Expired site cookies** requiring a takeover. agentes.chat routines can't call `request_secret`, so the login has to be prepared in an interactive run.
3. **Expired OpenAI refresh token** (`not_logged_in`); runs fail until the user signs in again.
4. **Plan limit shared with daytime Codex use**; the run waits or is missed past the reset (agentes.chat), or falls back (Rakazo, MausBot, OpenBot, Reason).
5. **Datacenter IP blocks.** agentes.chat Cloud computers run in the EU and report their egress IP; geo-restricted sites may block it.
6. **Approval pauses.** Any write that needs a card (email send, connected-app write) waits until morning.
7. **Codex sandbox has no network** in agentes.chat routines (`brain-codex.ts`), so web access must go through the product's browser and fetch tools `[INFERENCE]`.

### 13.3 Where the CSV lands

Covered per product in the F5 sections of each notes file. In short: chat attachment, Drive or Files tab, a public link (Reason, Rerun, OpenBot), Slack, or git. Gmail send generally waits for approval.

## 14. Per-product profiles

Compact: strengths, weaknesses, and the one design choice most worth studying.

### Rakazo

- **Strengths**: the best-specified scheduler; brokered secrets with exact-origin checks; 13 sandbox backends behind one supervisor; wide trigger set; Apache-2.0; hosted plan with a clear BYO-model story.
- **Weaknesses**: Team computers share an OS user; "command variables" deliberately expose secrets; Claude OAuth discouraged on ToS grounds; self-hosters configure their own Composio or Pipedream; some channels (iMessage/SMS, WhatsApp, Telegram) are self-host only.
- **Study**: `routine-coalescing.ts` and `routine-lateness.ts` (catch-up flagged late); `secret_request` broker.

### MausBot

- **Strengths**: largest community; strongest cloud sandbox (Fly VM per customer plus bubblewrap per turn plus egress gate); per-bot computer choice; plain-code pre-checks before AI turns; careful browser-secret handling (`browser-secret-hold.ts`); portable teams.
- **Weaknesses**: desktop default is Full access with no OS sandbox; plaintext keys in `config.json`; provisioning and billing are in a private repo (`openmaus-cloud`); Gmail polled every 15 min; no Telegram or WhatsApp.
- **Study**: inherited-pipe-FD secret passing (`cloud-secrets.ts`); cloud sleep/wake (`cloud-power.ts`).

### OpenBot

- **Strengths**: fast release cadence; clear provider-terms analysis; multi-provider with up to 8 fallbacks; native Slack, Discord, Telegram and WhatsApp; Cloudflare Worker wakes sleeping boxes; password manager integrations.
- **Weaknesses**: no per-agent isolation at all; default danger-full-access and no approvals; plaintext agent keys; PolyForm Noncommercial license; Slack requires the vendor relay; prompt injection documented as unmitigated.
- **Study**: `docs/provider-terms.md` (rare in this field); worker-cron wake design.

### Nuphos

- **Strengths**: multiplayer sessions; DevOps depth with keyless federated cloud identity; sealed WORM audit journal; runtime portability across five agent CLIs via ACP; large test suite.
- **Weaknesses**: very new; Compose self-host has no cron; one team per self-host install; shared Boxes share one Unix user and unauthenticated VNC; Claude and Codex logins unencrypted in the container; cron UTC; no catch-up.
- **Study**: `credentials-mcp.ts` per-turn scoped tokens; `byos/` federation; `journal/sealer.ts`.

### Rerun

- **Strengths**: clear SMB focus; template marketplace; the product's own API is one MCP endpoint; `docs/INSTALL.md` is written for AI assistants; approval queue UX.
- **Weaknesses**: plaintext secrets; at-most-once scheduling with silent skips; mirrors vendor OAuth client IDs with no ToS warning; README denylist not found in code; AGPL plus Supabase dependency for self-host; cloud hosting unpublished.
- **Study**: approval-queue UX; `tools/bot-wall.ts`.

### agentes.chat

- **Strengths**: the most rigorous governance (per-agent budget before each call, hashed approvals, E2E secret requests, injection hardening ADR 0117); Postgres-only infra; per-agent Linux users; the 170+ ADR trail is itself a research resource; importers from competitors.
- **Weaknesses**: default runner shares one OS user; OS sandbox only proposed; many features Beta; Codex "in testing"; Gmail and others depend on Composio; ~2 GB image; provisioner and KMS private; telemetry on by default.
- **Study**: `packages/engine/src/routines.ts`, `routine-firing.ts`, `outbox.ts`; ADR 0027 (secrets), 0053 (unattended work), 0117 (injection).

### Reason Machines

- **Strengths**: fresh VM per run; egress allowlist proxy and optional brokered secrets; cross-agent Network (open source); multi-subscription aggregation; PR-centric output.
- **Weaknesses**: closed; no self-host of the agent; no free tier; sandbox and browser internals undocumented; silent fallback to paid credits; $50 entry.
- **Study**: Vault + brokered placeholder swap; Network's `ask_user` approval.

### Turnstone

- **Strengths**: the only polished consumer native Mac app; mid-conversation model switching; Brain as plain files; iMessage from the user's own number; MCP server for importing Grok Bots.
- **Weaknesses**: closed; Mac only; nothing runs while the Mac is off until Cloud ships; cloud credentials decryptable by the vendor; local isolation is only a folder boundary; many details undocumented.
- **Study**: review cards for schedule, skill and brain changes; migration tooling.

### SuperBot

- **Strengths**: smallest working design in the category (one Rust binary, SQLite, 4-method `Adapter` trait for three harnesses); harness-neutral tools as shell CLIs; per-Bot screen with live view and takeover from day one; clean restart rule (interrupted runs reported, never re-run); MIT; documented reconstruction of Grok Bot internals.
- **Weaknesses**: no permission model, isolation, secret store or approvals; one shared bearer token lets any Bot drive the whole API as any other Bot or as the user; the host's env, including the login password, reaches every Bot; no missed-run handling; single-password auth; one test; one day old.
- **Study**: `adapters/mod.rs` (CLI-per-harness seam); `runner.rs:447-456` (choice cards from a fenced block); `grok-bot-internals/` for their Grok Bot claims.

## 16. Anti-patterns and risks found

| #   | Anti-pattern                                                                                 | Seen in                                                                                                                                                        | Consequence                                                                                                     |
| --- | -------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| A1  | Plaintext secrets at rest (0600 files or JSON config)                                        | Rerun (all); OpenBot (agent keys); MausBot (CLI-entered keys, MCP header values, `mcp-oauth.json`)                                                             | Any process as that user, or a backup, reads everything                                                         |
| A2  | Shared OS user across agents                                                                 | OpenBot; Nuphos shared Boxes; Rakazo Team computers; agentes.chat default; MausBot desktop                                                                     | One injected agent reads another's credentials and sessions                                                     |
| A3  | Unauthenticated VNC on a shared display                                                      | Nuphos shared Boxes (documented)                                                                                                                               | Cross-session screen access                                                                                     |
| A4  | Default Full access with no approvals                                                        | MausBot desktop; OpenBot; Nuphos trigger conversations                                                                                                         | Autonomous actions on injected content; unattended runs never pause                                             |
| A5  | Silent failure (debug-log skip, missed-only notification)                                    | Rerun (budget latch or busy); Nuphos (missed run reported, never re-run; failed jobs only logged)                                                              | The user finds out when the data is missing                                                                     |
| A6  | At-most-once with no retry                                                                   | Rerun                                                                                                                                                          | Any crash or restart at fire time loses the run                                                                 |
| A7  | Scheduler dependency missing in the default self-host path                                   | Nuphos Compose (no Redis, cron never starts)                                                                                                                   | "Works" in a demo; schedules silently dead in production                                                        |
| A8  | UTC-only cron with manual DST conversion                                                     | Nuphos                                                                                                                                                         | Twice-a-year schedule drift                                                                                     |
| A9  | Mirroring a vendor's OAuth client ID with no warning                                         | Rerun ("an undocumented flow we mirror")                                                                                                                       | Breaks without notice; ToS exposure shifted to the user                                                         |
| A10 | Shared subscription login across a team                                                      | Nuphos shared computer; OpenBot "High" risk rating                                                                                                             | Likely against consumer-plan terms                                                                              |
| A11 | Vendor can decrypt cloud credentials                                                         | Turnstone (explicit); Nuphos, MausBot, Rerun Cloud `[INFERENCE]`                                                                                               | Trust in the vendor is part of the threat model                                                                 |
| A12 | Third-party connector holder sees all data                                                   | Composio users (Rakazo, MausBot, Rerun, agentes.chat, Nuphos partly, Turnstone)                                                                                | Connector data and tokens leave your boundary                                                                   |
| A13 | Silent fallback to paid credits                                                              | Reason                                                                                                                                                         | Unexpected spend when a subscription runs out                                                                   |
| A14 | A README claim not backed by code                                                            | Rerun's shell denylist, not found in the repo                                                                                                                  | Users assume a control that may not exist                                                                       |
| A15 | Self-host divergence                                                                         | Cloud-only features (Rerun Linkup/Treg, template library; Rakazo hosted-only channels; MausBot provisioning private; agentes.chat provisioner and KMS private) | Self-host is not the same product                                                                               |
| A16 | Vendor relay required for a core channel                                                     | OpenBot Slack via the Signal relay                                                                                                                             | Self-host still depends on the vendor                                                                           |
| A17 | A laptop as the only agent computer with no fallback                                         | agentes.chat (silent `missed` after 12 h; no API fallback by design)                                                                                           | Nothing runs; the user sees nothing at night except a notification                                              |

### 17.2 Open questions to answer before deciding

Product and users

1. Who is the first user: an individual, a small team, an SMB, or developers? Part 2 shows the competitors split four ways and rarely cross.
2. Is the use case dominated by connector-only work or by sandbox work? Part 12.1 shows most non-dev templates need no sandbox.
3. Must it keep running with the laptop off? If yes, where does the always-on part live and who pays for it?
4. Is the product the chat itself (agentes.chat) or an assistant that lives in other chat apps?

Models and ToS 5. Is subscription use a must-have? If so, which providers, and who accepts the ToS risk? Do you document it? 6. Do you hold the token (server-side OAuth) or leave it with the vendor CLI on the user's box? The first is easier to operate and more exposed. 7. What happens on a plan limit at 3 am: wait, skip, fall back to API, or fall back to another account? Do you tell the user?

Isolation and secrets 8. What is the unit of isolation: customer, workspace, agent, run? What shares an OS user? 9. Will agents ever see raw secrets? If not, you need an egress proxy and a per-host allowlist. 10. How is a login performed once and kept: human takeover, vault, imported profile? 11. How do you handle prompt injection from mail, web pages and files? What does a trigger from outside text get to do?

Scheduling and operations 12. Which scheduler store do you already depend on (Postgres, Redis, none)? 13. Per routine, what happens on missed, failed, overlapping and over-budget runs? Is it visible to the user? 14. Can an agent create a schedule? Can a scheduled run? 15. What is the policy on approvals while the user is away: wait, expire, deny, auto-approve within rules?

Distribution and business 16. Self-host parity: which parts of the cloud would stay private, and what does that do to trust? 17. Which license fits the business model (see Part 10)? 18. What do you meter and what do you leave to the user's own model account? 19. How will users move in: importers, MCP, Grok Bot export?
