# 0009: Double-loop chat mode is a per-bot second chat mode, run by a long-lived front session and background agents

Status: accepted. Relates to [ADR-0002](0002-bot-handoffs-are-async-a2a-tasks-on-a-host-endpoint.md) (handoff results arrive through `deliver()`), [ADR-0003](0003-feature-modules-and-dependency-rules.md) (the new host feature module) and [ADR-0004](0004-web-feature-modules-and-host-store.md) (web feature modules and the host store). The spec is `docs/plans/double-loop-chat.md`; the prototype is `../double-loop/v3`, its design `../double-loop/docs/double-loop-design.md` (§ "v3 as built") and its plan `../double-loop/docs/v3-plan.md`.

## Context

A bot's chat is turn-based: `Thread` holds one SDK `query()` per bot, `Chat.busy` allows one turn at a time, and a message sent mid-turn is queued and drained into the next turn. Heavy work (research, file edits) therefore blocks the conversation for minutes.

The prototype in `../double-loop/v3` showed another shape on the same Claude Agent SDK: one long-lived, fast **front** session answers every message within seconds, and heavy work runs in **background agents** the front starts, steers and stops. Its runs show front replies in 0.7 to 3.4 s with an agent running, a steer changing a running agent's scope, three agents in parallel, a `kill -9` with two agents running followed by a resume, and a worker's file tools refused outside its workspace. They also show tasks that fail to start and a stop that misses its id, which the port must handle.

## Options

Only the decisions with a real alternative are listed; the rest are taken from the spec as written.

- **Toggle scope.** Per bot, or a global `HostConfig` flag. A global flag forces one mode on every bot, cannot be flipped from the UI, and would also need a new-bot field.
- **Switching modes.** Continue the CLI session in the other mode, or start a new session. The modes use different system prompts, agent definitions and session shapes; continuing mixes them.
- **Task log.** SQLite tables, or JSONL per bot as in v3. The host already has a migration mechanism and `bot_activity` and `handoffs` as precedents.

## Decision

The double-loop chat mode is added as a second mode beside the unchanged standard chat, with these decisions:

1. **Toggle scope: per bot.** `Bot.chatMode: "standard" | "double_loop"`, default `"standard"`, carried on `BotSummary` and stored in `bot.json` (`StoredBot`, preserved by `save()` as `browser` is). Rejected: a global `HostConfig` flag.
2. **Switching starts a new session.** It calls `newSession` and is refused with 409 while double-loop agents are running or queued; the UI says to stop the running tasks first.
3. **Durable task log in SQLite.** Tables `loop_tasks` and `loop_events` (migration `SCHEMA_V14`), keyed by bot and session: task lifecycle, progress, activity, steers and reports. Reports never enter the front's CLI session, so `replay()` cannot rebuild them from the session file; in double-loop mode replay merges the session file with `loop_events` by timestamp. Rejected: JSONL per bot.
4. **Replay strips app-written blocks.** User messages in the front session end with `<work_state>…</work_state>`, and synthetic app messages (queue dispatch, restart notice, task notifications) are `isSynthetic`. Replay drops both, so the transcript shows what the user typed and what the bot said.
5. **Front tool set.** `Agent`, `SendMessage`, `TaskStop`, `mcp__loop__queue_task`, `mcp__loop__cancel_queued`, `mcp__host__remember` and `rewrite_memory`. No `ask_user`: a blocking ask would stall the never-blocking front, so the front asks in chat. As in v3 the main thread runs as a `front` agent whose tool list is that set, and the session's `tools` hold every agent's tools, because subagents only see what the session has.
6. **Agent types.** `researcher`: WebSearch, WebFetch, `record_progress`. `worker`: the bot's own capabilities (file tools in the bot's workspace, Bash under the bot's isolation profile, the bot's integration MCP tools, `mcp__host__ask_user`, `record_progress`). Browser tools stay off agents: the browser session is one per bot and parallel agents would fight over its tabs. Handoff tools (`mcp__bots__*`) stay on the front, so a handoff result returns through `deliver()` into the front.
7. **Permissions keep Claudebot's rules.** `Thread.canUseTool` and the `HostDelegate` are reused. A background agent's approval or `ask_user` raises the normal approve/ask card, a needs-you item; that agent waits while the front and the other agents continue. v3's `permissionMode: "dontAsk"` is not ported, because a human is present. v3's PreToolUse path guard stays as defence in depth for the worker.
8. **`deliver()` in double-loop mode** pushes a synthetic message (`isSynthetic: true`, `priority: "next"`) into the front instead of queueing a turn. This covers handoff results, external events, browser waits and routine prompts. Routine runs on a double-loop bot without a chat use the standard headless runner (`runHeadless`) unchanged.
9. **No composer queue.** In double-loop mode `/api/send` always answers `outcome: "sent"`; `queued`, `dequeued` and `/api/send/cancel` do not apply. Answers to needs-you items (`eventId`) keep their path: a linked ask is answered directly, otherwise the message goes to the front.
10. **Presence instead of a per-turn "is working…".** `BotSummary.status` is `working` while the front's turn or any agent runs. The transcript shows one presence line: "typing…" while the front streams, "working…" while agents run. Front text streams through `text_start` and `delta`; reports appear whole. The contract carries the presence as one ephemeral `presence{state: "idle" | "typing" | "working"}` `ServerEvent`, never in the replayed history; a page connecting is sent the current state.

**What a task is.** A background task is what the front starts with the Agent tool; its result is a report, posted to the chat as the bot's own message, after which the front adds one line about what is still running. The app writes a work state into every message the front receives, and findings are attributed to tasks by the app, not by the agent.

**Architecture.** A new host feature module `packages/host/src/loop/` with a public surface of `index.ts` only, wired in the composition root `host-server/index.ts`. `loop` is added to `MODULES` in `.dependency-cruiser.cjs` when its code lands.

| File            | Owns                                                                                                                                      |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `front.ts`      | `FrontSession`: shaped like `Thread`, but a pump consumes the query iterator for the session's whole life, not per turn                   |
| `agents.ts`     | agent definitions and prompts, `ProgressAttribution`, the in-process `loop` MCP server (`record_progress`, `queue_task`, `cancel_queued`) |
| `observe.ts`    | SDK messages and hooks → store rows and `ServerEvent`s through a callback the chat supplies                                               |
| `tasks.ts`      | task registry folded from the log, app queue (`after`), dispatch and re-dispatch                                                          |
| `work-state.ts` | `workState()`, pure                                                                                                                       |
| `store.ts`      | SQLite access for `loop_tasks` and `loop_events`                                                                                          |

Chat mode dispatch lives in `host-server/chats.ts` (`send`, `deliver`, `reconfigure`, `drop`, `newSession`, `replayOpen`, `isWorking`). New `ServerEvent`s: `task`, `task_status` (ephemeral, not in history) and `report{taskId, text}`.

**Risk handling.**

- **`TaskStop` is a shell tool here.** `SHELL_TOOLS` in `harness/index.ts` contains it, and `isolation.shell === "disabled"` denies it session-wide, so an isolated double-loop bot could never stop an agent. In double-loop mode `TaskStop` is removed from the session-wide deny list, and a PreToolUse hook refuses `TaskStop` when its `task_id` is not a background agent the store knows. `shell-isolation.test.ts` pins the list and is updated as a contract test.
- **Nothing closes a front with running agents.** Closing the front kills every agent. Idle close (`idleMs`), `configStale` after `reconfigure()`, and integration token expiry defer until no agent runs. The front's pump never closes on a send error, unlike `Thread.send`.
- **Busy semantics stay.** Standard `busy`, `inbox` and `drain` are untouched; a double-loop chat bypasses them rather than overloading them.
- **Context growth.** Reports stay out of the front's context, as in v3; auto-compaction handles the rest and `compacted` events already render.
- **Subscription limits.** Parallel agents share the user's 5-hour and weekly limits. `rate_limit_event` (status, utilization, reset) is surfaced next to the context meter when the bot is in double-loop mode.
- **CLI-version drift.** Background tool filtering, task events and `SendMessage` resume have changed across recent Claude Code versions. The managed CLI version is pinned in `harness/cli.ts`; rerun the routing eval and a manual restart test when bumping it.

**Defaults.** Front: `claude-haiku-5-5` with `thinking: {type: "disabled"}`, whatever model the bot is set to (the bot's model and effort drive its background agents); other models at `effort: "low"`. Agents: `claude-sonnet-5-5` at `medium` effort, `maxTurns` 60 (researcher) and 80 (worker). `MAX_PARALLEL` is 3, set through `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`. The environment sets `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1`; options set `agentProgressSummaries: true` and `includePartialMessages: true`. Unprompted progress pings are off.

**Non-goals.** v3's devtools page, trace rows and SDK cost estimate; unprompted progress updates; browser tools on background agents; a double-loop variant of headless routine runs; multiple front sessions per bot.

**SDK version.** The installed `@anthropic-ai/claude-agent-sdk` is 0.3.318 and v3 ran on 0.3.322. Comparing the two `sdk.d.ts` files, the definitions the port depends on are identical apart from comments and whitespace: `SDKTaskStartedMessage`, `SDKTaskProgressMessage` (including `summary`), `SDKTaskNotificationMessage`, `SubagentStopHookInput.last_assistant_message`, `agentProgressSummaries`, `AgentDefinition.background`, `SDKUserMessage.isSynthetic` and `priority`, `PreToolUseHookInput` and `SDKRateLimitEvent`. The files differ elsewhere (comment text and additions to unrelated control requests and options), none of which the port uses. There is no SDK bump for this feature; re-check when the managed CLI version in `harness/cli.ts` is bumped.

**Evaluation.** The routing eval result and manual real-CLI timings are recorded in M7.

**M3 decisions (researcher end to end).** Beyond the spec above:

- The main thread runs as an agent named `front` (`agent: "front"`) whose `disallowedTools` deny `WebSearch`, `WebFetch` and `record_progress`; the session's `tools` hold every agent's built-in tools, because subagents only see what the session has. A deny list rather than an allowlist, since an agent allowlist needs exact MCP names and would couple `loop` to the handoff tool names.
- `Agent`, `SendMessage`, `TaskStop`, `WebSearch`, `WebFetch` and `record_progress` are approved by the front's `canUseTool` wrapper, not by `allowedTools` (which makes the SDK warn that `canUseTool` is shadowed). Nobody answers a card for an agent's web research; this is a deliberate exception to Claudebot's permission rules, as in v3.
- The agents' model and effort follow the bot's `setModel`/`setEffort` through `FrontSession.setAgentSettings`; they are read when the front next opens, so a change applies to agents defined from then on.
- `loop_tasks.status` holds the task's current state (`running`, never `started` or `resumed`); a resume is a second `task_started` for a known task, which keeps its goal and start. `loop_events` holds `progress`, `activity`, `steer` and `report` rows; steer rows are written from M4.
- A report is stored, then emitted (`report{taskId, text}`) and recorded as the bot's message. It is posted once per run of a task whichever of the `SubagentStop` hook and the `task_notification` comes first; when the notification comes first the report waits 5 seconds (`REPORT_WAIT_MS`) for the hook, then falls back to the agent's transcript, then to a placeholder. The same text twice in a row for one task is stored once.
- A stopped agent's notification keeps an `interrupted` task interrupted, as does `reason: "worker_restart"`; neither posts a report.
- Whenever the front's CLI stops (idle close, reconfigure, crash) its running tasks become `interrupted`, and `loop.interruptRunning` does the same for every session at host start, so a dead agent never blocks the mode switch. The 409 check reads `hasActive` (any `queued` or `running` task of the bot, in any session) from the store.
- Replay of a double-loop session merges `loop_events` reports into the session file's messages by timestamp, each before the first message written after it, with the session's `task` rows at their start time. `task_status` is never part of history; a page that connects mid-run gets the current lines from the observer.
- The snapshot a page gets ends with `presence`, after the status lines.
- Presence is `typing` while the front streams its own message (messages from agents are not shown), `working` while any agent runs, else `idle`; a double-loop chat is kept alive while its presence is not `idle`.
- The web shows a task as one row that follows its state and, while it runs, its status line; a report renders as the bot's message with a tooltip naming the task.

**M4 decisions (parallel, steer, cancel, queue).** Beyond the spec above:

- A queued task is a `loop_tasks` row of status `queued` with an app id `q-<8 hex>` and, when it waits for a task, `after_task` (`SCHEMA_V15`). When the front's Agent call that names the id starts, the entry's row is deleted and the agent's row takes its goal and agent type, its start being the agent's; tasks that waited for the entry are pointed at the agent, and the `task` event carries `queuedId` so the page puts the agent in the entry's row. The id is claimed by the Agent call's `name`, `description` or `prompt`, as in v3.
- Which entries are due is computed from the store; what the front was asked to start (`dispatched`, with its attempt count) is memory only. An interrupted task holds a slot, as in v3, and an interrupted blocker is not over, so what waits for it waits for M5.
- `pump()` runs on every task change and on a 5 s timer that exists only while something is queued. A due entry becomes the synthetic message `Start queued task q-… (agent: T): goal` through the chat's host-message path (held while a scheduled run writes the conversation); after 120 s unanswered it is asked again, and after two requests the task becomes `failed` with no report. The timer stops when the chat is released, dropped or shut down; a queue left by an earlier host run is looked at 5 s after its chat opens, and the queue is not pumped at construction.
- A new session cancels the old session's queued tasks, because `hasActive` reads every session of the bot and nothing would ever start them.
- `queue_task` and `cancel_queued` are in the `loop` MCP server and pre-approved with the front's other tools; `queue_task` refuses an unknown `after`, and treats an ended one as `null`.
- A steer is two rows at most: `sent` when the front's `SendMessage` is about to run for a task the store knows (queue ids resolve to the agent they became), and `failed` (with the tool's reason) when the tool answers with an error. The work state lists `instructions sent so far` as sent minus failed. No `ServerEvent` carries steers.
- `TaskStop` needs no rule of its own: the CLI's `stopped` notification cancels the task. (A stop on an `interrupted` task kept it interrupted here; M5 changed that.)
- The work state's running tasks list the status line, the newest eight findings and the steer count; queued and recent tasks keep M3's lines. `foldTasks` (`loop/tasks.ts`) is the pure grouping of the store's tasks into running, queued and ended.
- Findings reach the web on the `task` event itself (`findings`, the newest eight, whole each time, so the latest event replaces the earlier one), with `after` for a queued task and `queuedId` as above; replay builds the same events from the store. No `finding` event.
- The Tasks tab is a web feature module `features/tasks` composed into `BotPanel` through a `tasks` slot in `bot.lazy.tsx`. It reads the `task` rows of the open chat, so it lists what the transcript knows, and it exists only for a bot whose `chatMode` is `double_loop`; `?panel=tasks` on another bot opens the default tab.
- The fake CLI's `loop.json` steps may use `{queued}`, the `q-` id in the user message's text, so a script can answer a queue dispatch.

**M5 decisions (lifecycle and recovery).** Beyond the spec above; the `TaskStop` bullet of M4 is superseded by the last bullet here:

- `FrontSession.idle()` (no turn streaming, none opening, no agent running, no queue entry the front was asked to start and has not answered within the dispatch timeout) is the one test every close the session starts itself waits for: the idle timer, `closeWhenIdle(reason)` (what `chats.reconfigure()` calls for a double-loop chat) and an expiring integration token. A deferred close keeps its first reason and is applied by `settle()`, which runs after every front turn (once the context meter is read), before every `send()` and on the idle timer. `Chat.configStale` is for standard chats only.
- The front reads `integrations.session().expiresAt` whenever it opens, as a standard thread does, and closes for the token when idle. M6 connects the integration servers in that session for the worker; a worker's tokens are never older than the front's session.
- Closes the user asks for (new session, bot delete, mode switch) and host shutdown still close at once. A new session and the mode switch are already refused while agents run (the presence is not idle; `hasActive`), so no running agent is killed by them; an interrupted task left in the old session stays there and is not resumed, because recovery and the work state read the current session only.
- A send error never closes a live front: `send()` throws only before a message is pushed (sign-in, open failure, closed while opening), `frontFailed` no longer forces the presence to idle (it follows the agents) and `release()` keeps a chat whose front is not idle.
- Recovery lives in `FrontSession`, per CLI process: the first message a freshly opened process receives, and `recover()` when a chat is shown (`show()`, which runs at host start through `switchTo` and when a reload rebuilds the chat), is preceded by v3's synthetic "The app restarted. These agents were interrupted: …" message, which lists the session's interrupted tasks, when there are any. `needsRecovery()` says whether it is owed. A process is told once; an idle close with tasks still interrupted, a CLI death or a host restart gives the next process one more notice. A chat that is not shown is not recovered (its tasks stay interrupted), and a chat shown while a scheduled run writes its conversation waits until it is shown again.
- The CLI dying uses the same path as a host start: `onStopped` marks the running tasks interrupted, the presence follows, the error is shown, and the next open or message sends the notice.
- `TaskStop` on an interrupted task cancels it, seen in the `PreToolUse` hook (the CLI answers that the agent is not running and sends no notification), so the stop request itself ends the task; a later `worker_restart` report never moves an ended task back to interrupted.

**M6 decisions (worker, isolation, TaskStop).** Beyond the spec above; the deny list of M3 and the `TaskStop` handling of M3 to M5 are superseded where noted:

- The `worker` agent (`loop/agents.ts`, ported from v3) runs in the background, up to 80 turns, on the bot's agent model and effort. Its tools are `Read`, `Write`, `Edit`, `NotebookEdit`, `Glob`, `Grep`, `Bash` (only when the bot's `isolation.shell` is not `disabled`), one whole-server entry `mcp__<name>` per integration server, `ask_user` and `record_progress`. It has no web tools (the researcher's) and no browser tools; its prompt carries the bot's persona, files-folder note and memory, read when the front opens, so a change reaches new agents when the front next opens.
- File boundary: the workspace (`cwd`, shared by all bots) and the bot's own files folder (`botFilesPath`), the two places a standard bot's persona tells it to write. A PreToolUse path guard (`loop/guard.ts`) refuses an agent's `Read`, `Write`, `Edit`, `MultiEdit`, `NotebookEdit`, `Glob`, `Grep` or `LS` call that names a path outside them (`..`, absolute, `~`, symlinks, a Glob pattern's fixed prefix) with a reason the agent sees, and records the refusal in its activity. It denies outright instead of asking, since an agent's file tools have no business elsewhere; `canUseTool` for agents uses the same roots. `Bash` stays confined by the bot's sandbox profile and gets no guard.
- Shell: a worker's `Bash` is whatever the bot's isolation gives its own `Bash` (sandbox, network allowlist, read denies). With `isolation.shell === "disabled"` (remote mode without a usable sandbox) the session still disallows `Bash`, `PowerShell` and `Monitor`, and the worker has no `Bash` tool and says so in its prompt and description.
- Integrations: the front's session connects the bot's integration MCP servers (leaving out servers named `host`, `loop`, `bots` or `browser`) and merges their disallowed tools; plugins and skills are not given to it. Subagents only see the session's servers, so the worker's `tools` name each as `mcp__<name>` (the CLI 2.1.322 accepts server-level specs in an agent's `tools` and `disallowedTools`; string `mcpServers` on an agent are skipped under `--strict-mcp-config`, so they are not used). Tool approval for integration tools follows the standard rules through the same `canUseTool` (`integrations.decide`).
- The front agent's `disallowedTools` are computed from the agent definitions (`frontAgent`): every tool any agent has, except the front's own (`FRONT_TOOLS`: `Agent`, `SendMessage`, `TaskStop`, `queue_task`, `cancel_queued`, `remember`, `rewrite_memory`, and the handoff tools, which no list names). A tool added to an agent therefore never reaches the front; the session's `tools` is `sessionTools(agents)`, the front's built-ins followed by each agent's. This supersedes M3's three-name deny list.
- `TaskStop` stays available under a disabled shell: the harness drops it from the shell deny list when the launch sets `stopsAgents` (double-loop front), and the PreToolUse hook refuses ids the store does not know (a shell id, a typo) and ids of `queued` entries (`cancel_queued` drops those), so `TaskStop` can stop only this chat's agents. A standard chat's deny list is unchanged. `TaskStop` on an `interrupted` task still cancels it (M5).
- A permission request from an agent (`canUseTool`, `options.agentID` is the task id) becomes the usual approval card whose reason names the task: `<reason>, for the task "<goal>"`; the front keeps answering meanwhile. The worker has no pre-approved tool but `record_progress` (the researcher's web tools stay pre-approved). A question the worker asks with `ask_user` is attributed through the PreToolUse hook, which notes the agent by tool use id, and the handler reads `_meta["claudecode/toolUseId"]` (`HostDelegate.askUser` takes it as a fourth argument): the card reads `Task "<goal>" asks: <question>`; a call with no note is the front's own plain card.
- A card for an agent stopped meanwhile stays until answered (no expiry), and `ProgressAttribution` keeps its name though it now also attributes `ask_user`.
- The front's prompt routes hands-on work to `subagent_type "worker"` and web research to `"researcher"`, and no longer says it cannot run scripts or edit files.

**M7 decisions (tests, smoke, rate limits, docs).** Beyond the spec above:

- The rate limit rides on one ephemeral `ServerEvent`, `rate_limit{status, window?, utilization?, resetsAt?}`, not on the `context` event: the context meter is read after a front turn, while the CLI reports a limit whenever it changes, mid-turn or between turns. `observe.ts` forwards the front's `rate_limit_event` (`rateLimitEvent`), the chat keeps the newest report of each window for the account (the limit is the user's subscription's, so it outlives a new session and a rebuilt chat), broadcasts it to the shown chat and sends the kept ones after `presence` to a page that connects; it is never in the replayed history and only a double-loop chat has a front to report one. `window` is the CLI's `rateLimitType` as a string, so a window a newer CLI adds still parses.
- `utilization` is taken as the used fraction (0 to 1) and `resetsAt` as epoch seconds, which the host turns into milliseconds (a value already in milliseconds is kept). The SDK's type documents neither unit; this is an assumption to confirm against a real CLI run (see Evaluation).
- The web keeps `chat.rateLimits` by window (a reset clears it, a new session keeps it) and `RateLimitMeter` renders beside the context meter for a double-loop bot only: the most pressing window (rejected, then warned, then most used) as the button, every window with its used share and reset on hover. Nothing shows until the CLI reports a limit.
- `smoke:loop-ui` is the browser smoke of the mode on the fake CLI's `loop.json`; it needs `CLAUDEBOT_ASK_APPROVAL` for the worker's approval card, so `startSmoke` takes an `env` option for the host's configuration. A worker's approval is a transcript card, not an item of the Needs you bar, which holds external events only; the smoke asserts the card.
- The routing eval, its usage and cost stay documented in the header of `scripts/eval-loop-routing.ts` and summarised in `AGENTS.md` ("Double-loop chat mode"), with the manual real-CLI scenarios.

## Consequences

- Both modes stay supported: the standard chat and its tests are unchanged, and every `chats.ts` path that touches `busy`, `inbox` or `drain` needs a mode branch.
- A double-loop bot's transcript is no longer rebuilt from the CLI session file alone; `loop_events` is part of what replay reads, and a lost or reset database loses reports.
- Switching modes loses the continuity of the conversation (a new session) and is blocked while tasks run.
- A task that waits on an approval or `ask_user` card holds one of three parallel slots until the user answers.
- Agents cannot use the browser, so browsing work stays with standard mode or the front's handoffs until the browser session has a lock.
- Parallel agents spend the subscription faster; the rate-limit display is the only guard.
