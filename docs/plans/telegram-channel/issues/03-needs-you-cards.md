# 03: Needs-you cards with buttons, answers and in-place edits

**What to build:** Every open needs-you item (an external event of kind `question`, `blocked`, `failed`, `done` or `stopped`) reaches the linked Telegram account once, as a card with buttons and a link to the web UI. A button, or a reply, answers through the same answer path as the web UI, for any bot (not only the one the page shows), and the card is edited in place when the item closes anywhere. See the spec sections "Cards" and "Answering from a channel".

Three seams change:

- **Answer by bot id.** `/api/send` acts on `ctx.chats.open()` (`host-server/api/index.ts`), so only the bot the page shows can be answered. In `host-server/chats.ts`, `openChat(chat).send` holds the logic (pending linked ask first via `pendingAskFor` and `answerAsk`, queue when busy, close the item when the message reaches the bot). Make it callable by bot id (open the chat the way `deliver` does, with `deps.transcript` and `createChat`; `release(chat)` frees it afterwards) and make the `/api/send` route in `host-server/api/chat.ts` use the same function. A channel gets the web UI's four outcomes: `answered`, `sent`, `queued`, `refused`.
- **Buttons in the contract.** `itemActions` in `packages/web/features/chat/model.ts` (question options plus `Answer…`/`Other…`, `Unblock…` and `Status` for `blocked`, `Retry` and `Skip` for `failed`, `Review` for `done`, `Status` for `stopped`) moves to `@claudebot/contract` as a pure function with its tests (`features/chat/model.test.ts`); the web UI imports it from there. A draft-only action has no button on a card; the card says "reply to this message to answer".
- **Items for a channel.** `createEvents` (`events/index.ts`) reports each newly stored item that is not `progress` and not a duplicate to a new collaborator, returns the full content of an open item (kind, source, title, body, options, bot id) and lists every open item across bots. Today its interface has only the counts (`needsYou()`) and the transcript rows (`onChange`).

- [x] A schema step adds `channel_cards` (channel, item kind `event` or `wait`, item id, bot id, message ref, sent at, closed at; unique on channel, kind and item id). A new open item is sent once as a card: title `<source> · <title>`, the body, buttons from the contract function, and a URL button to `<public URL>/bots/<botId>?panel=work`. The public URL is `clientAt.publicUrl` (`host-server/index.ts`); when it is loopback http the card has no URL button
- [x] A restart sends nothing twice. At host start and right after linking, every open item with no `channel_cards` row is sent, oldest first. An item that arrived while Telegram was down is sent once it is back
- [x] A button carries `a:<itemId>:<index>` (at most 64 bytes) and never an answer text. The host reads the option from the stored item. An option button answers like the web chip: `answer` is the option, the message is `<source> · <title>: answer '<option>'`. `Retry`, `Skip`, `Review` and `Status` send their message with the item id. A `Dismiss` button closes the item as `dismissed`
- [x] The outcome of a button is the web UI's: `answered` (a linked ask got the value; no chat message was created), `sent`, `queued` (the card keeps its buttons, and the toast says "queued; the bot is busy"), `refused` (a toast: "already handled"; the card is not edited). A stale index, an item of another bot or an unknown id is refused with a short toast. A second press on the same card changes nothing and runs nothing twice
- [x] The answer from Telegram for a bot the page does not show works, including a held (busy) bot, and goes through the one send function the web route uses; a test runs both routes against the same item and compares outcomes
- [x] When an item leaves `open` by any route (answered in the web UI, dismissed, resolved by its source, answered from Telegram), its card is edited to its outcome ("Handled", "Dismissed", "Resolved by its source") and loses its buttons. A card edited once is never edited again
- [x] A reply to a card answers that card with the reply's text as the answer. A plain message answers the single open card when exactly one is open. With several open and no reply it answers nothing and says to reply to the card. With none open it answers nothing, and no run, session or chat receives the text. The answer goes through the same function as a button, with the item id
- [x] Cards are not tied to the kinds that exist today: an open item of a kind added later (feature 13's `notice`, `.scratch/13-cost-guards/issues/03-auto-pause-after-failures.md`) is sent through the same path as one with title and body, and a kind with no actions in the contract function gets Dismiss only

- [x] A transcript row for an answer given from Telegram reads like the web UI's (the user message and the item's handled state), and `needsYou` counts and the desktop banner update as for any answer
