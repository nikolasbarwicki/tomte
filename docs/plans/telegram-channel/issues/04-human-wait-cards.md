# 04: Human-wait cards: approvals, questions, takeovers

**What to build:** Every open human wait (a tool approval, an `ask_user` question, a takeover, a login approval) reaches the linked Telegram account as a card, and a button or reply answers it through the answer path, so a parked routine run resumes. A card shows the exact input an approval covers; long input is cut with a link, and a cut approval cannot be approved from the phone. See the spec sections "Cards" and "Answering from a channel".

Today these waits are memory-only: `chat.pending` in `host-server/chats.ts` (asks and approvals, shown as `ask` and `approve` events) and `HumanWaits` in `browser/human-waits.ts` (takeover and credential approval, shown as `wait` and `wait_resolved` events with `kind`, `title`, `detail` and `actions: WaitAction[]`). `docs/plans/unattended-parking/issues/01-durable-human-waits.md` moves all of them onto the `human_waits` table and `02-parked-runs.md` makes an unattended approval park the run. This ticket reads open rows and answers them through the `waits` module's interface from 01 (`packages/host/src/waits/`): `list(botId?)` for open waits, `subscribe` for opens and closes, `cards(botId)` for the card events, and `answer(id, value, note?)` to answer one. If a needed operation is missing, add it to that interface here rather than reaching into the table.

Approval values are `allow`, `allow_always` and `deny` (`docs/plans/unattended-parking/issues/07-always-allow-and-deny-note.md`: `allow_always` is labelled "Always allow <tool> for this bot"). The owner's note on a denial is the `note` argument of `answer` from 01, so a reply to an approval card is `answer(id, "deny", text)`. A parked run resumes through `routines.resume(runId, message)` (02), not a bare `deliver()`; the channel only answers the wait.

**Status:** ready-for-agent

- [ ] Each open human wait is sent once as a card (a `channel_cards` row of kind `wait`, from ticket 03), including waits that opened while Telegram or the host was down and waits that survive `restart()`. A wait that is already closed is never sent
- [ ] An approval card shows the tool, the reason and the exact stored input as plain text, with Allow and Deny (and `allow_always`, "Always allow <tool> for this bot", when the wait carries it) as buttons `w:<waitId>:<index>`, an index into the wait's stored actions and never the action's text
- [ ] When the input is longer than the card's budget (about 3000 characters) it is cut with "…" and the web link, and the card offers no action that lets the tool run: only Deny and the link, and it says "Input too long to show here. Open the web UI to approve." A test with a long input proves no Allow button and no "always allow" button, and that a stale Allow callback for that card is refused
- [ ] A reply to an approval card (or a plain message when it is the single open card) denies it with `answer(id, "deny", text)`, so the text is the note the bot receives. An approval is never edited or re-issued with a changed input from Telegram
- [ ] An `ask_user` card shows the question and its options as buttons; a button or a reply answers it and the run or turn resumes with that value. A question linked to an external event that already has a card (ticket 03) gets no card of its own: the event card's buttons already answer it through `pendingAskFor` and `answerAsk`
- [ ] A takeover card shows the reason, a URL button to `<public URL>/bots/<botId>?panel=browser`, and the wait's own actions (I'm done, Skip). A text reply to it is refused with "use the buttons". A login approval card shows its title and detail and its actions
- [ ] The outcome of a press is the web UI's: answered, refused as already handled (a toast, no card edit), or a wait that is gone. When a wait closes by any route (answered on the web, on the phone, cancelled, expired by feature 10's 24-hour expiry), its card is edited to "Answered: <action label>", "Cancelled" or "Expired" and loses its buttons
- [ ] End to end at the host seam with the fake Telegram server and the fake Claude CLI: a routine run that calls an `ask`-policy integration tool parks (status `waiting`), the card arrives, pressing Allow resumes the same session through `routines.resume` without running earlier steps again, and the run ends `succeeded`. The same with Deny and with a reply as the note (the bot receives the note), and with an answer that arrives after a `restart()`
- [ ] A double press, or a press on the phone and the web UI together, resumes the run once. A press on a card whose wait expired is refused and edits the card to "Expired"
- [ ] Host seam tests also cover: an `ask_user` card with options on a bot that is not open; a takeover card's link and Skip; a card for a wait on a bot that is busy. `bun run check` passes
