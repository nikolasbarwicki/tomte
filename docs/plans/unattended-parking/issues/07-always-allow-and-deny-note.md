# 07: "Always allow this for this bot" and a note on Deny

**What to build:** The approval card gets a third button, "Always allow for this bot", which allows this call and stores a rule for that tool and bot. Deny takes an optional note that the bot receives. A bot's rules are listed in its panel and can be removed. This is how repeated approvals stop interrupting a routine, by my explicit choice per tool and with no list the code guesses (ADR-0009). See the spec section "Always allow".

**Blocked by:** 02

**Status:** ready-for-agent

Today `ApproveCard` in `web/features/chat/transcript.tsx` has Deny and Allow, answered through `answer(id, "allow" | "deny")` to `/api/answer` (`host-server/api/chat.ts`). The `approve` event has no `actions` field; the stored wait (ticket 01) has `actions`, which a channel reads. `HumanWaits.answer(id, value, note?)` already carries a note into the bot's message (ticket 01); this ticket adds the route field and the card. `Thread.canUseTool` in `bots/thread.ts` asks in two places: an integration tool whose policy is `ask` (the `integrations.decide` switch) and, only with `askApproval`, Bash and out-of-workspace file access (the `delegate.approve` calls below `approveAll`). `decide` returning `deny` ("Off") must keep winning. Bots keep small tables in their own folder (`bots/activity-store.ts` for `bot_activity`); follow that.

## Comments

- Schema step: `SCHEMA_V18` (`tool_allowances`, primary key on `bot_id` and `tool_name`).
- Where the rule is checked: `createCanUseTool` (`bots/session-kit.ts`) gets `allows(tool)` beside `approveAll`, so the standard thread, a headless routine run and a double-loop front and its agents all read it; it comes from `ThreadEnv.allows(botId, tool)`, wired in the composition root to `allowsTool`. It is read live on every call, so removing a rule takes effect on the bot's very next call without reopening its session. `decide` returning `deny` is the first case of the switch, so Off still wins.
- Where the rule is stored: `WaitsOptions.alwaysAllow(botId, tool)`, called from `finish` when a `tool_approval` closes as answered `allow_always`, so it also happens for a parked run's approval and for an answer delivered by message after a restart. `allow_always` is then handled like `allow` everywhere an approval is read (`isApproved` in `waits/`: in-process claim, `consumeApproval`, the resume text, `chats.askApproval`). The resume text adds one sentence saying the tool is now always allowed.
- Contract: the `approve` event gains required `actions` (the stored wait's actions, built by `approvalActions(tool)` in `waits/`; chats and `parkingDelegate` share it), so the card and the Needs-you bar stay data-driven; `/api/answer` gains optional `note` (max 500 characters, trimmed; empty means none); `ToolAllowances` in `@claudebot/contract/api` is the response of `POST /api/bots/allowances`; the remove route is `POST /api/bots/allowances/remove` (404 for an unknown bot or a tool without a rule). `note` is passed to `waits.answer` for questions too, which already wrote it into the bot's message.
- Web: `ApproveCard` renders the buttons from `actions` (`approvalButtons` in `features/chat/model.ts`, with the answered label `approvalAnswerLabel`: Allowed, Always allowed, Denied) and shows a one-line note input while the card is open, sent only with Deny. The Permissions section sits at the end of the Settings tab of the bot panel and refetches when a card in the open chat adds a rule.
- Deviation: the Permissions section is in the Settings tab (the panel has no tab of its own for it); the section component is in `bot-panel.tsx` as the ticket says.
- An approval that was already open when the host was upgraded has the two old actions only; answering it `allow_always` is refused with 404. It can still be answered Allow or Deny.
- Tests: `host-server/always-allow.test.ts` (host seam, fake CLI `approve.json`: Always allow runs this call and a later call with other input has no card; plain Allow stores nothing; Deny with a note reaches the bot; a rule of one bot does not apply to another; Off wins over a rule; removing a rule asks again; deleting the bot removes its rules, seen by a bot that reuses the id; chat-hosted and headless routine runs: Always allow on a parked approval resumes the run and the next run never parks), the card labels in `features/chat/model.test.ts`.
- Needs-you bar (ticket 03): the approval row's buttons now come from the `approve` event's `actions` (`requestOf` in `model.ts`), so "Always allow <tool> for this bot" shows there too; `APPROVE_ACTIONS` is deleted. The row has no Deny note (the card has it), and Enter on a request row still only scrolls to the card. Covered in `model.test.ts`.

- `smoke:answer-ui` and `smoke:needs-you-ui` (after the rebase): both passed. `smoke:answer-ui` does not touch the approval card.
