# 02: Parked runs: approvals and questions park, answers resume

**What to build:** A routine run that meets a tool approval or an `ask_user` question parks instead of denying. The run gets the new `waiting` status, its turn ends, and my answer resumes the same session with a message, so earlier steps do not run again. A park expires after 24 hours and fails the run. An occurrence that comes due during a park is skipped. This is the tracer bullet for the whole feature: a routine calls an `ask`-policy tool, the run shows `waiting`, I approve in the UI, the run finishes. See the spec section "Parking".

**Blocked by:** 01

**Status:** ready-for-agent

Today `headlessDelegate` (`bots/index.ts`) denies every approval and answers every question with a canned text. A headless run uses it directly (`runHeadless` in `routines/index.ts`). A chat-hosted routine turn reaches it through `hooks.unattended()` in `host-server/threads.ts`. `routine-turns.ts` picks between the two. `createRoutines` keeps `running` in memory, `fire()` skips on it (`routines/index.ts`, `running.has(id)`), and `interruptStaleRuns` in `routines/store.ts` marks leftover `running` rows `interrupted`. A `waiting` row must be left alone by it.

One thing differs from ADR-0009's wording: it says the answer goes "through `deliver()`". `deliver()` alone starts an ordinary chat turn that the run does not own, so the run's status, output and unattended handling would be lost. Resume through the routine executor instead: `routines.resume(runId, message)` calls the same `execute` path with the resume message as the prompt, in the same session. Cost guards (`.scratch/13-cost-guards/issues/04-parked-time.md`) hook into where a run enters `waiting` and where it leaves it, so keep those two places single and named.

- [ ] `RunStatus` gains `waiting` in `packages/contract/src/events.ts`. A schema step (the next free `SCHEMA_Vn`) rebuilds `routine_runs` with the wider status CHECK, as `SCHEMA_V12` did for `external_events`: copy rows with their rowids, drop, rename, make the index `routine_runs_by_routine` and the `UNIQUE (routine_id, scheduled_for)` again. `human_waits` rows are untouched. Every consumer handles the value: `RUN_STATUS` in `web/features/routines/routine-item.tsx` (badge "Waiting for you"), `routines/store.ts` (`finishRun`'s status type), `routines/index.test.ts`
- [ ] `RoutineJob` carries `runId` and `trigger`. The chat row's trigger no longer comes from `job.prompt.includes('trigger="manual"')` in `chats.ts`. `waits.open` attaches the run id and session id of the bot's current unattended turn through a `context(botId)` collaborator that `routine-turns.ts` and `chats.ts` provide (they know headless and chat-hosted runs). An attended turn gives none
- [ ] One `parkingDelegate` replaces `headlessDelegate` for headless and chat-hosted routine turns. `approve` opens a `tool_approval` wait and denies with a message that tells the bot the request was sent to the owner and to end its turn. `askUser` opens a `question` wait (with its options) and returns at once with text that says the answer will arrive as a message. `headlessDelegate` is deleted. The prompt in `routines/index.ts` (`prompt()`) no longer says nobody can be asked: it says a request to the owner parks the run and the answer arrives as a message
- [ ] The turn-end rule in `createRoutines.run()`: a turn that succeeded while the run has an open wait sets the run to `waiting` (it leaves `running`, keeps its row and `session_id`, and its `output` stays null); a turn that succeeded while every wait of the run is answered but not yet delivered continues the run at once with their messages; a turn that failed fails the run and cancels its waits. Answering while the bot is still finishing its turn therefore never parks
- [ ] When the last open wait of a `waiting` run is answered, `routines.resume(runId, message)` sets the run `running` again and executes the message in the same session, in the bot's chat when it has one, headless otherwise. Several answered waits are one message. A denial carries the owner's note. If the bot's chat is busy, the resume waits for its turn to end (as `routine-turns.ts` already queues a job)
- [ ] An answer that arrives after `restart()` resumes the run. `reconcile()` leaves `waiting` runs alone, and the session resumes from disk (`getSessionInfo`)
- [ ] A park expires when its wait expires (24 hours, from ticket 01), whatever started the run, manual or scheduled. The run becomes `failed` with "approval expired" (`routines.expire`), the bot is told in a host message that nothing was approved and not to retry, and a chat row tells the owner. The bot's reply is a chat message, not the run's output
- [ ] `fire()` also asks the run table: a routine with a `waiting` run records the occurrence as `skipped` with "previous run is waiting for you" (the existing "previous run still in progress" stays for `running`), including a catch-up from `reconcile()`. `testRun` throws `Conflict` while the routine is parked
- [ ] A new session on a parked bot cancels the run's waits and fails the run with "session ended while waiting for you". Deleting the routine or the bot cancels its waits and removes the parked run with the routine
- [ ] The Routines panel shows `waiting` for the run, and a run that resumed shows `running` then its final status (`routine-item.tsx`)
- [ ] `docs/roadmap.md` item 1 says what shipped and points to ADR-0009 for what it replaced (no allow and block lists, 24 hours, resume as a message)
- [ ] Host-seam tests with the fake CLI's `approve.json` and `ask.json` (prior art: `browser/routines.test.ts`, which runs each case chat-hosted and headless; `routines/index.test.ts` for the fake clock): a routine calls an `ask`-policy tool and the run shows `waiting`; Allow resumes it and it finishes `succeeded`, with the fake CLI having received one resume message in the same session and no repeat of the first prompt; Deny with a note reaches the bot and the run finishes; an unattended `ask_user` parks and its answer reaches the bot; the answer given while the first turn still runs does not park; the same after `restart()`; 24 hours later (moved clock) the run is `failed` with "approval expired" and the bot is told; an occurrence while parked is `skipped` with the new text; a manual run is refused. Each runs chat-hosted and headless. `bun run check` passes
