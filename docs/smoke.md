# Browser smokes

Unit and host-seam tests passed while the real answer workflows were broken, so the answer path (ADR-0007 events, ADR-0008 relay), the double-loop chat mode (ADR-0011) and the transcript's scrolling also have smokes that drive the built web UI in a real browser. They are scripts, not part of `bun run check`: they need Chrome and a web build.

| Command                      | What it runs                                                                                                                                                                                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `bun run smoke:answers`      | The end-to-end round trip (below): the real `tomte-notify`, the real UI, a fake `herdr`.                                                                                                                                                                                              |
| `bun run smoke:answer-ui`    | Needs you `Answer…` → edit → Send: the draft, the item's close, a failed and a queued send, replaced and emptied drafts.                                                                                                                                                              |
| `bun run smoke:needs-you-ui` | Needs you chips, keyboard triage and free text while the bot waits on a question about the item; idle and busy bots; a turn that died; a second page racing the first; an open wait (the bot's own question): a bar row with the card's buttons that Enter and `e` do not answer.     |
| `bun run smoke:blocked-ui`   | A `blocked` report from the sender: Needs you, Work, `Unblock…` and `Status`.                                                                                                                                                                                                         |
| `bun run smoke:loop-ui`      | The double-loop chat mode on the fake CLI's `loop.json` (below): toggle, never-blocking sends, tasks, report, approval, rate limits.                                                                                                                                                  |
| `bun run smoke:scroll-ui`    | The transcript following streamed replies (below): wheel turns at the end, scrolling up, the scroll-to-end button, a send while scrolled up, a reload.                                                                                                                                |
| `bun run smoke:channels-ui`  | The Channels page against a fake Telegram Bot API (below): token rejected and accepted, the link code and `t.me` link, linking through the fake server, a stranger ignored, the linked state, a routine's result sent to the phone, an `@Name` message answered on the phone, Unlink. |
| `bun run smoke:ui`           | The seven above in that order, with one web build. It stops at the first failing smoke and exits with that smoke's status; nothing after a failure runs and nothing is reported as passed.                                                                                            |

## Prerequisites

- Google Chrome (or Chromium). macOS's `/Applications/Google Chrome.app` is the default; `CHROME_PATH` names another binary. Playwright drives it headless in a fresh profile; no browser download is involved.
- `bun install` has been run. Each smoke runs `vite build` of `packages/web` into its own run directory (`smoke:ui` builds once and shares it through `SMOKE_WEB_DIST`).
- No network, model, keychain, Herdr, OMP or Tomte app is needed, and none is touched.

## The round trip (`smoke:answers`)

One fresh run directory under the OS temp folder holds everything: a temporary data root with an in-memory database and secrets, the fake Claude CLI (`packages/host/src/testing/fake-claude.ts`), the web build, a `relay.json` whose only adapter `herdr` runs a fake `herdr` executable, and that executable's log. The fake appends `{ "argv": [...], "exit": N }` to a JSON-lines file for every call and exits with the status the smoke sets. The adapter's arguments are `agent prompt {agent} {message} --session {session}`, the shape of `herdr agent prompt <agent> "<answer> (<question id>)" --session <session>`. The reports are posted by the real `tomte-notify` (`packages/notify/src/main.ts`) as a subprocess with the bot's events URL and token in its environment, a reply target and a question id.

| Flow                                                                                              | Proven in the browser and in the recorded argument lists                                                                                                                                                                                                                                                                             |
| ------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. A report, then `Answer…` → edit → Send                                                         | The report shows in Needs you, in Work and in the transcript; Send is accepted as an answer to that item; both badges and the bar clear; one call `agent prompt coord "<answer> (Q-1)" --session default`; the item stays handled and delivered after a reload.                                                                      |
| 2. A transcript ask chip for an ask the bot raised about the report; 3. free text on such an ask  | The ask receives the value, the item closes on the page and after a reload, one call per answer, with an explicit session (`--reply-session`) and with the default one.                                                                                                                                                              |
| 4. An ordinary ask, answered while an unrelated question is open                                  | The unrelated question stays open and nothing is relayed.                                                                                                                                                                                                                                                                            |
| 5. A Needs-you answer (free text, and an option chip) while the bot holds a genuinely pending ask | The host resolves the ask; no chat message is created or queued; the draft's `<source> · <title>: ` prefix is not part of the relayed text; one call each.                                                                                                                                                                           |
| 6. A busy bot                                                                                     | The answer is reported as queued, the item and badges stay open, the page shows no relay result and the fake `herdr` is not called until the answer reaches the bot; then exactly one call.                                                                                                                                          |
| 7. `blocked`                                                                                      | Needs you, Work "Blocked", `Unblock…` → Send closes it; with no question id the message is the answer alone.                                                                                                                                                                                                                         |
| 8. A failing relay                                                                                | The fake exits 3: the page says "Reply not delivered" with the exit status, also after a reload; after Retry there is exactly one more call, it succeeds, and a Retry replayed afterwards runs nothing.                                                                                                                              |
| 9. Duplicates                                                                                     | A double click and two raw requests at once (a second device): exactly one is accepted and the fake is called once; the second tab sees the item close; a late replay is 409, a replayed ask answer 404, a repeated report `ok (duplicate)`.                                                                                         |
| 10. Injection                                                                                     | An answer with quotes, newlines, `$(touch …)`, backticks, `;`, `&&`, `\|`, `$HOME`, `*` and a line starting with `-` arrives as one argument, byte for byte, and the canary files do not exist (they are in the run directory, never in `/tmp`). The sender and the events route refuse a reply target or session with shell syntax. |
| 11. An adapter kind that is not configured; an item without a target                              | The first shows its failure and runs nothing; the second runs nothing and shows no relay line.                                                                                                                                                                                                                                       |

The smoke ends by printing every recorded argument list.

## The double-loop chat mode (`smoke:loop-ui`)

The host runs with `TOMTE_ASK_APPROVAL` on (`startSmoke(name, { env })`) and the fake CLI plays the front's long-lived query from one `loop.json`: per user message it streams the front's text, starts, progresses, ends or stops background agents through the host's real PreToolUse and SubagentStop hooks and its in-process `loop` MCP server, and asks the host for an agent's tool approval. Steps that wait for a file (`host.allow(name)`) let the smoke say when an agent ends. The model is never called.

| Flow                                                | Proven in the browser and on the host                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. The toggle                                       | A standard bot has no rate-limit indicator, and its Tasks section says background tasks need double-loop chat; the Double loop card in the model chip's popover and its confirm dialog switch it, starting a new session; the popover then calls the model and effort the background tasks', and picking Opus is saved in `bot.json` and shown on the chip. |
| 2. Two messages a second apart                      | Both answered `sent`, none queued; the composer stays enabled; the presence line says "typing…" while the front's turn is open.                                                                                                                                                                                                                             |
| 3. Rate limits                                      | The front's `rate_limit_event` shows beside the context meter as the most pressing window, with every window and its reset on hover.                                                                                                                                                                                                                        |
| 4. A research task, a second one, a steer, a cancel | The Tasks section shows the task running with its status line moving and a finding; the transcript shows no task rows and none of the front's tool calls, and the presence line says "working on 1 task…"; two run in parallel; the steer is counted in the front's next work state; the cancelled task moves to Recent.                                    |
| 5. A mode switch while a task runs                  | `/api/bots/chat-mode` answers 409 "stop the running tasks first"; the chat mode cards in the model chip's popover are disabled meanwhile.                                                                                                                                                                                                                   |
| 6. A queued task                                    | It waits for its blocker, nothing is asked of the front; when the blocker ends the app sends the front a synthetic "Start queued task q-…" message, the agent replaces the queue entry and later reports.                                                                                                                                                   |
| 7. The report                                       | Posted once as the bot's message with the task in its tooltip, however many signals announce it.                                                                                                                                                                                                                                                            |
| 8. A worker's approval                              | The card "Allow Bash?" names the task and stays open while the front answers another message; allowing it lets the agent continue and report. While open it is also a row of the Needs you bar and a count on the sidebar (an open human wait, ADR-0009); Enter there never answers it.                                                                     |
| 9. A page reload, and a chat rebuilt from disk      | A session file shaped like the real CLI's (work state appended, app messages marked by origin) is written; after a reload and after leaving the bot and coming back, every report is shown once, the typed messages are back (task rows stay out of the transcript), the Tasks section lists the four tasks and no `<work_state>` text is on the page.      |
| 10. Leaving double-loop mode once nothing runs      | The One thread card goes back; the Tasks section asks for double-loop chat again and the rate-limit indicator goes.                                                                                                                                                                                                                                         |

## The transcript's scrolling (`smoke:scroll-ui`)

The fake CLI streams long replies word by word from `loop.json`. While one streams, a `ResizeObserver` created after the page's own reads where the last row ends on every resize, so the smoke sees what gets painted, not the layout between a new word and the follow. The scroller is `packages/web/features/chat/scroller.tsx`.

| Flow                                         | Proven in the browser                                                                                                      |
| -------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 1. A short reply, then a long streamed one   | Each ends with its last line in view, and every painted frame of the stream keeps it in view.                              |
| 2. Wheel turns down while already at the end | Following goes on. (They produce no scroll event; the previous scroller took any wheel turn as leaving the end and froze.) |
| 3. Scrolling up while a reply streams        | The view stays where the reader put it, the stream goes on under the fold, the scroll-to-end button shows and resumes it.  |
| 4. A message sent while scrolled up          | The view jumps to the end and follows the reply.                                                                           |
| 5. A reload                                  | The page opens at the end.                                                                                                 |

## The Channels page (`smoke:channels-ui`)

The host's Telegram adapter is pointed at `packages/host/src/testing/fake-telegram.ts` (`HostServerOptions.telegram.baseUrl`, passed through `startSmoke("channels-ui", { timing })`), a loopback Bot API with real long-poll behaviour that records every call. `api.telegram.org` is never contacted and the token is the fake `123:fake-token`. The smoke plays Telegram: it sends updates to the fake and reads what the host sent back.

| Flow                          | Proven in the browser and on the fake server                                                                                                                                                                                                                     |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1. No token                   | The page says "No bot token yet" and Link account is disabled.                                                                                                                                                                                                   |
| 2. A token Telegram rejects   | The page shows the refusal, the token is not stored, and nothing polls.                                                                                                                                                                                          |
| 3. A token Telegram accepts   | The page shows "Running as @bot", the field is empty again, the token is nowhere in the page, it is in the secrets store, and the host long polls with the configured timeout.                                                                                   |
| 4. Link account               | The dialog shows the code and a link `https://t.me/<bot>?start=<code>`.                                                                                                                                                                                          |
| 5. A stranger, then the owner | A stranger's `/start` with something that is not a code gets no call back at all; the owner's `/start <code>` links, and the confirmation arrives in the owner's chat.                                                                                           |
| 6. A routine's result         | In the routine form the checkbox "Send the result to my phone" starts off, shows "Needs a linked channel (Channels page)" and is enabled; a routine saved with it on sends the owner's chat "Digest: ok" when Run now finishes, and editing it shows the box on. |
| 7. `@Name` from the phone     | A message `@planner what is new?` from the owner reaches the bot with the name taken off, the bot's reply arrives in the owner's chat as "Planner\n\nok" (name first), and a plain message with no open card gets the hint naming the newest bot.                |
| 8. Linked, then Unlink        | The page shows Linked with the account's name; Unlink (with its confirm dialog) clears it, the bot token stays and the bot keeps running.                                                                                                                        |

## Failures and artifacts

A failed check throws, the smoke exits non-zero (and `smoke:ui` exits with the same status), and the **run directory is kept**; its path is the last line printed. It holds `checks.log` (every step and check), `page-console.log` (console, page errors and failed requests of every page), `host.log` (what the host wrote to stderr), `failure-page<N>.png` for every open page, `shots/` (screenshots taken at key steps), `error.txt`, and the smoke's own files: for `smoke:answers`, `herdr-argv.jsonl`, `relay.json` and the fake. A passing smoke removes its run directory and nothing else: it never touches a process or a file it did not start or create. `SMOKE_KEEP=1` keeps the directory of a passing run too, with the same logs.

The harness shared by the smokes is `scripts/smoke-kit.ts`; add a new browser smoke on top of it instead of repeating the build, host and browser setup.

## What they do not cover

- No Electron shell, tray, desktop notification, login item or OS dialog: the page is served by the host's client listener and driven in plain headless Chrome.
- No real `herdr`, OMP, coordinator or model: the relay runs a fake program, the bot is the fake Claude CLI. That an actual agent receives and understands the prompt is not proven. That the real front routes a message to the right action is what the manual `eval:loop-routing` measures; the real CLI's message shapes and timings are checked by hand (AGENTS.md, "Double-loop chat mode").
- Remote mode and the Origin/token boundaries are covered by the host tests, not here. Timeouts and a host that dies mid-relay (delivery unknown) are covered by `packages/host/src/events/relay*.test.ts`.
- The sender is run as a Bun subprocess by path with the route in its environment. Its config-file and project-routing modes are covered by `packages/notify` tests.
- Only desktop Chrome at 1400×900; no mobile layout.
