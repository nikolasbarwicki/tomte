# Glossary

- **Bot**: a persistent agent in claudebot with its own settings, memory and sessions.
- **Harness**: the agent runtime a bot runs on (Claude Code today; Codex and OpenCode later).
- **Engine**: the browser automation runtime (`agent-browser` daemon plus Chrome) that the host drives.
- **Browser session**: one bot's browser: an engine session named after the bot, with its own cookies, storage, tabs and saved login state.
- **Browser tools**: the MCP tools exposed to bots at the browser endpoint.
- **Browser endpoint**: the host's Streamable HTTP MCP route that serves the browser tools.
- **Snapshot**: a text accessibility view of the current page with element references (refs).
- **Live view**: the user's real-time view of a bot's browser in the web UI.
- **Takeover**: a period during which the user, not the bot, controls a bot's browser.
- **Credential entry**: a stored website login (label, site origin, username, password) in the claudebot vault.
- **Grant**: the user's permission for one bot to use one credential entry.
- **Human wait**: anything that needs the user before the bot can continue (takeover, credential approval).
- **Handoff**: a task one bot gives another, with a brief, messages, a status and a result; an A2A task between claudebot bots.
- **Requester**: the bot that creates a handoff and receives its result.
- **Assignee**: the bot a handoff is given to; it does the work in its own session.
- **Brief**: the self-contained instructions in a handoff (goal, context, constraints, deliverable, done criteria); the assignee sees nothing else of the requester's conversation.
- **Agent card**: a bot's public description for other bots (id, name, purpose, status), as listed by `list_bots`.
- **Contract**: the Zod schemas, derived types and data the host shares with the web app (server events and the models they carry, HTTP-only request and response shapes, avatars), kept in the `@claudebot/contract` package (`packages/contract/`); it imports nothing else local.
- **Composition root**: `packages/host/src/host-server/index.ts`, the one place that constructs the features, passes each its collaborators, and starts and stops them.
- **Local mode**: the host runs on the user's own machine; it defaults to a free loopback port and a public URL that is that loopback URL.
- **Remote mode**: the host runs on a Linux server (it is Linux-only, [ADR-0006](docs/adr/0006-remote-mode-is-linux-only.md); on any other OS `--mode remote` is refused at startup and a Mac runs local mode) and users reach it through the public URL, the origin that users and OAuth providers use. It still binds loopback by default; a non-loopback bind needs an HTTPS public URL or `--allow-plain-http`. It defaults to file secrets (which need `--secrets-key-file`), headless Chrome, no reveal in the file manager, and shell isolation for every bot.
- **Host info**: what `GET /api/host-info` returns without a device token: host version, API version, mode, the Claude sign-in state (remote mode only) and the capabilities (reveal, headed browser, browser sandbox). The UI loads it once at startup and treats an unknown capability as unavailable, so it hides "Show in Finder", "Open folder" and the headed-browser setting when the host cannot do them. In remote mode the host launches Chrome headless whatever a bot's stored setting says, and refuses to turn the setting on.
- **Data root**: the one directory that holds all host state: the database, bot directories, user memory, plugins and skills, and the managed Claude CLI and browser engine. It defaults to the OS application-data directory (`~/Library/Application Support/claudebot` on macOS, `$XDG_DATA_HOME/claudebot` or `~/.local/share/claudebot` on Linux) and is set with `--data-root` or `CLAUDEBOT_DATA_ROOT`.
- **Claude config directory**: where the Claude CLI keeps its sign-in and session history. In remote mode it is `claude/` in the data root, which the host sets as `CLAUDE_CONFIG_DIR` for every CLI child, and the CLI children get an allowlisted environment (`PATH`, `HOME`, `USER`, `SHELL`, `LANG`, `TERM`, `TMPDIR` and what the host sets for the CLI), so `ANTHROPIC_API_KEY` and other host variables never reach a bot. The user signs in once with `host auth-login`; a run that starts while signed out fails naming that command. In local mode the CLI keeps its default `~/.claude` and children get the host's whole environment.
- **Workspace directory**: `workspace/` in the data root. Every bot's Claude CLI runs there, whichever directory the host was started from, so Claude Code's session files for all bots live under that one directory.
- **Agent listener**: the host's loopback socket for bots, on `127.0.0.1` and a free port. It serves the browser endpoint, the bots endpoint and the credential exchange, with the checks of ADR 0001; the MCP configs written for each harness point at it.
- **Client listener**: the host's socket for people, bound to the address and port from `HostConfig` (loopback unless a deployment sets another address under the rule above). It serves the web UI, `/api/*` with the event stream, live view, takeover input, wait answers and `/oauth/callback`, and never the agent listener's routes.
- **Secrets key file**: the file of exactly 32 raw bytes that holds the key for the encrypted secrets file (`secrets.enc` in the data root), named by `--secrets-key-file` or `CLAUDEBOT_SECRETS_KEY_FILE`. The key is read only from this file, never from the environment. The host refuses to start with the file backend when the file is missing or not 32 bytes. Create one with `head -c 32 /dev/urandom > <path>; chmod 600 <path>`. Losing it loses every secret in the file; switching backends migrates nothing.
- **Device token**: the secret that identifies one paired device (a browser, a script, later the desktop app) to the client listener. It is 32 random bytes; the host keeps only its SHA-256 digest. The device sends it as `Authorization: Bearer <token>` or as the `claudebot_session` cookie, and the user revokes it per device. See ADR 0005.
- **Pairing code**: a single-use code, 12 base32 characters in groups of four, that a user creates with `host pair` or from the Devices page and that a new device exchanges for a device token. It expires after 10 minutes, and 10 failed attempts invalidate every outstanding code. See ADR 0005.
- **OAuth redirect URL**: the public URL plus `/oauth/callback`, the one address providers send the browser back to after an integration sign-in. A dynamically registered OAuth client records the redirect URL it registered, and the next connect registers a new client when that differs from the current one (access and refresh tokens stay valid until then). A client stored before the URL was recorded is judged by the `redirect_uris` in its stored client information; one with neither registers again. A static client (Google, or a user-supplied client ID and secret) is never re-registered: the user registers the current redirect URL with the provider, and the integration's card shows it.
