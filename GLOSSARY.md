# Glossary

- **Bot**: a persistent agent in claudebot with its own settings, memory and sessions.
- **Harness**: the agent runtime a bot runs on (Claude Code today; Codex and OpenCode later).
- **Engine**: the browser automation runtime (`agent-browser` daemon plus Chrome) that the host drives.
- **Browser session**: one bot's browser: an engine session named after the bot, with its own cookies, storage, tabs and saved login state.
- **Browser tools**: the MCP tools exposed to bots at the browser endpoint.
- **Browser endpoint**: the host's Streamable HTTP MCP route that serves the browser tools.
- **Snapshot**: a text accessibility view of the current page with element references (refs).
- **Live view**: the user's real-time view of a bot's browser in the web UI.
- **Takeover**: a period during which the user, not the bot, controls a bot's browser.
- **Credential entry**: a stored website login (label, site origin, username, password) in the claudebot vault.
- **Grant**: the user's permission for one bot to use one credential entry.
- **Human wait**: anything that needs the user before the bot can continue: a tool approval, a takeover, an `ask_user` question or a credential approval. It is a row in the `human_waits` table (kind, bot, run id, session id, payload, expiry), so it survives a restart, and the web UI, every channel and the expiry check read that table. See [ADR 0009](docs/adr/0009-unattended-runs-park-on-durable-human-waits.md).
- **Handoff**: a task one bot gives another, with a brief, messages, a status and a result; an A2A task between claudebot bots.
- **Requester**: the bot that creates a handoff and receives its result.
- **Assignee**: the bot a handoff is given to; it does the work in its own session.
- **Brief**: the self-contained instructions in a handoff (goal, context, constraints, deliverable, done criteria); the assignee sees nothing else of the requester's conversation.
- **Agent card**: a bot's public description for other bots (id, name, purpose, status), as listed by `list_bots`.
- **Contract**: the Zod schemas, derived types and data the host shares with the web app (server events and the models they carry, HTTP-only request and response shapes, avatars), kept in the `@claudebot/contract` package (`packages/contract/`); it imports nothing else local.
- **Composition root**: `packages/host/src/host-server/index.ts`, the one place that constructs the features, passes each its collaborators, and starts and stops them.
- **Local mode**: the host runs on the user's own machine; it defaults to a free loopback port and a public URL that is that loopback URL.
- **Remote mode**: the host runs on a Linux server (it is Linux-only, [ADR-0006](docs/adr/0006-remote-mode-is-linux-only.md); on any other OS `--mode remote` is refused at startup and a Mac runs local mode) and users reach it through the public URL, the origin that users and OAuth providers use. It still binds loopback by default; a non-loopback bind needs an HTTPS public URL or `--allow-plain-http`. It defaults to file secrets (which need `--secrets-key-file`), headless Chrome, no reveal in the file manager, and shell isolation for every bot.
- **Host info**: what `GET /api/host-info` returns without a device token: host version, API version, mode, the Claude sign-in state (remote mode only) and the capabilities (reveal, headed browser, browser sandbox). The UI loads it once at startup and treats an unknown capability as unavailable, so it hides "Show in Finder", "Open folder" and the headed-browser setting when the host cannot do them. In remote mode the host launches Chrome headless whatever a bot's stored setting says, and refuses to turn the setting on.
- **Data root**: the one directory that holds all host state: the database, bot directories, user memory, plugins and skills, and the managed Claude CLI and browser engine. It defaults to the OS application-data directory (`~/Library/Application Support/claudebot` on macOS, `$XDG_DATA_HOME/claudebot` or `~/.local/share/claudebot` on Linux) and is set with `--data-root` or `CLAUDEBOT_DATA_ROOT`.
- **Claude config directory**: where the Claude CLI keeps its sign-in and session history. In remote mode it is `claude/` in the data root, which the host sets as `CLAUDE_CONFIG_DIR` for every CLI child, and the CLI children get an allowlisted environment (`PATH`, `HOME`, `USER`, `SHELL`, `LANG`, `TERM`, `TMPDIR` and what the host sets for the CLI), so `ANTHROPIC_API_KEY` and other host variables never reach a bot. The user signs in once with `host auth-login`; a run that starts while signed out fails naming that command. In local mode the CLI keeps its default `~/.claude` and children get the host's whole environment.
- **Workspace directory**: `workspace/` in the data root. Every bot's Claude CLI runs there, whichever directory the host was started from, so Claude Code's session files for all bots live under that one directory.
- **Agent listener**: the host's loopback socket for bots, on `127.0.0.1` and a free port. It serves the browser endpoint, the bots endpoint and the credential exchange, with the checks of ADR 0001; the MCP configs written for each harness point at it.
- **Client listener**: the host's socket for people, bound to the address and port from `HostConfig` (loopback unless a deployment sets another address under the rule above). It serves the web UI, `/api/*` with the event stream, live view, takeover input, wait answers and `/oauth/callback`, and never the agent listener's routes.
- **Secrets key file**: the file of exactly 32 raw bytes that holds the key for the encrypted secrets file (`secrets.enc` in the data root), named by `--secrets-key-file` or `CLAUDEBOT_SECRETS_KEY_FILE`. The key is read only from this file, never from the environment. The host refuses to start with the file backend when the file is missing or not 32 bytes. Create one with `head -c 32 /dev/urandom > <path>; chmod 600 <path>`. Losing it loses every secret in the file; switching backends migrates nothing.
- **Device token**: the secret that identifies one paired device (a browser, a script, the desktop app) to the client listener. It is 32 random bytes; the host keeps only its SHA-256 digest. The device sends it as `Authorization: Bearer <token>` or as the `claudebot_session` cookie, and the user revokes it per device. See ADR 0005.
- **Pairing code**: a single-use code, 12 base32 characters in groups of four, that a user creates with `host pair` or from the Devices page and that a new device exchanges for a device token. It expires after 10 minutes, and 10 failed attempts invalidate every outstanding code. See ADR 0005.
- **Sidecar**: the host started by the desktop app as a child process with `--sidecar` (local mode only). The app writes it a launch token on stdin and holds the pipe open; the host prints one JSON ready line with its client URL, and stops gracefully when the pipe ends. See [ADR 0005](docs/adr/0005-agent-and-client-listeners-and-device-auth.md).
- **Launch token**: the 43-character base64url secret the desktop app writes to a sidecar's stdin. The host registers it as the device "This computer", replacing the device an earlier launch registered, and the app sets it as the `claudebot_session` cookie in its own window. It is a device token with no pairing code. See [ADR 0005](docs/adr/0005-agent-and-client-listeners-and-device-auth.md).
- **Connection profile**: a host the desktop app can show besides this computer's sidecar: a name, an origin, and the device id and device token the host issued when the app paired with a pairing code. The token is stored encrypted with `safeStorage` in `profiles.json`; forgetting a profile revokes its device on the host. The built-in profile `local` is the sidecar and is never stored. See [ADR 0005](docs/adr/0005-agent-and-client-listeners-and-device-auth.md).
- **OAuth redirect URL**: the public URL plus `/oauth/callback`, the one address providers send the browser back to after an integration sign-in. A dynamically registered OAuth client records the redirect URL it registered, and the next connect registers a new client when that differs from the current one (access and refresh tokens stay valid until then). A client stored before the URL was recorded is judged by the `redirect_uris` in its stored client information; one with neither registers again. A static client (Google, or a user-supplied client ID and secret) is never re-registered: the user registers the current redirect URL with the provider, and the integration's card shows it.
- **Deploy kit**: `deploy/`, what turns a systemd Linux server into a remote-mode host: `install.sh`, the `claudebot.service` unit, a `Caddyfile` and `README.md`, the self-hoster's guide. The unit receives the secrets key as a systemd credential.
- **External event**: one report an outside process (a script, a coordinator running coding agents, CI) posts to a bot at `POST /api/bots/<botId>/events`: a kind (`question`, `blocked`, `failed`, `done`, `stopped` or `progress`), a sender-chosen key that dedupes retries per bot, an event source, a title and optionally a body, suggested answers and a work snapshot. `blocked` means the sender cannot go on until someone unblocks it: it starts `open` like a question and carries no suggested answers, its source reads "Blocked" in Work (after a source with an open question, before one with an open failure), and its Needs-you buttons are `Unblock…` (a draft that answers it) and `Status`. Every kind except `progress` is delivered to the bot as untrusted text and starts `open`; `progress` is stored as `info` and never wakes the bot. See [ADR 0007](docs/adr/0007-external-events-route-and-event-token.md).
- **Event source**: the sender an external event names: an id the sender chooses and a label the user sees (for example one feature's coordinator). The host keeps each source's label, last event time and latest work snapshot per bot.
- **Notify sender**: `claudebot-notify`, the command-line client in `packages/notify/` that posts one external event: `<progress|question|blocked|completed|failed> <task_id> <session_id> "<message>" [question_id]`, the argument order of `notify-grok`. It reads the bot's URL and token from the environment or a config file, never from the command line, maps `completed` to `done`, files the report under an event source per project and task, and derives the dedupe key from everything it reports, so a retry is a duplicate and a changed message is a new event. See `docs/notify.md`.
- **Work snapshot**: the step and the items (a label, an optional group and summary, and a state of `queued`, `running`, `review`, `needs_you`, `done` or `failed`) an event source last reported. An event that carries one replaces the previous snapshot.
- **Needs-you item**: an external event that is `open`: it waits for the user to answer it, dismiss it, or for its source to resolve it. An open human wait is listed beside it and is delivered the same way to a channel.
- **Answer (to a needs-you item)**: a message sent with the item's id (`eventId` on `/api/send`), from a Needs-you chip or from the composer after `Answer…`/`Other…` prepared a draft. The host alone decides where it goes and answers `outcome`: `answered` when the bot has a pending **linked ask** for that item (the ask receives the chip's option, or the typed text, and no chat message is created; queued answers to the item are cancelled), `sent` when the bot is idle (the turn starts with the message), `queued` when the bot is busy and no ask is pending. The item is closed as `acted` only when the ask is resolved or the message reaches the bot, never on queueing. A refused send (409: the item is not open for the open bot, e.g. another device handled it first, or an answer to it is already queued), a failed or cancelled one, and a message without an id, close nothing. Dismissing is the only other way a person closes an item.
- **Linked ask**: an `ask_user` question the bot raised about one external event by passing that event's id as `event_id` (the wrapper shows the bot the id). The host links it only when the event belongs to that bot, is still open and was delivered into the bot's current session; otherwise the ask stays ordinary. Answering a linked ask (a chip or free text) resolves the ask and then closes the event as `acted`. A linked ask whose turn died before the answer is dropped (its card is marked expired and offers no answers), so a late answer closes nothing; the item stays open and its next answer is an ordinary one.
- **Reply target**: the optional `reply` of an external event, `{ kind, agent, session? }`, naming where the user's answer to that event goes back to. `kind` names an adapter in the operator's relay configuration; `agent` and `session` are names (letters, digits, `.` `_` `:` `-`, never a leading dash). It is data for the host: the bot is never shown it and it names no program. The event may also carry a structured `questionId`, a name of the same shape, which the relay puts after the answer.
- **Answer relay**: after the user's answer to an event that has a reply target is accepted (the item closes as `acted`), the host runs the operator's fixed adapter for that target's kind, once, with an argument list and no shell, so the sender's agent receives the answer. The adapter and its arguments come from the relay configuration (`relay.json` in the data root, or `--relay-config` / `CLAUDEBOT_RELAY_CONFIG`), never from an event. Queued input is not an answer and relays nothing until it is delivered. The relay's state, `pending`, `relayed` (the adapter exited 0) or `failed` (with a reason; a Retry runs it again), shows beside the item in the transcript and in the Work timeline. See `docs/relay.md` and [ADR 0008](docs/adr/0008-answer-relay-hook.md).
- **Event token**: the secret that authorizes posting external events to one bot, 32 random bytes kept in the secrets backend and given to that bot's Claude CLI as `CLAUDEBOT_EVENTS_TOKEN` (with the route's URL as `CLAUDEBOT_EVENTS_URL`). It is no device token: on any other route it fails. The user can rotate it. See [ADR 0007](docs/adr/0007-external-events-route-and-event-token.md).
- **Parked run**: a routine run in the `waiting` run status because it has an open human wait. To **park** a run is to end its turn at that wait instead of denying the request. The answer resumes the same session with a message, so earlier steps do not run again. A park expires after 24 hours, and the run then fails with "approval expired". Occurrences that come due while a run is parked are skipped. See [ADR 0009](docs/adr/0009-unattended-runs-park-on-durable-human-waits.md).
- **Channel**: an adapter that delivers needs-you items and routine results to the owner outside the web UI, and routes the owner's answers back through the answer path. Telegram is the first. See [ADR 0010](docs/adr/0010-channels-deliver-needs-you-items.md).
- **Channel link**: the stored binding between a channel and the owner's account on it, made when the owner sends the channel's bot a one-time code shown in the web UI. Updates from any other account are ignored. See [ADR 0010](docs/adr/0010-channels-deliver-needs-you-items.md).
- **Run usage**: a run's token counts, `total_cost_usd` and the time it spent parked, stored on the run row beside `started_at` and `finished_at`. On a Claude plan, `total_cost_usd` is an estimate at API prices, not money spent.
